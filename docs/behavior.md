# Engine behavior notes

## Status

Status: reference implementation. The outputs are not OPEN ratings, and no OPEN rating is live. Do not use this engine to rate real players.

The engine was evaluated on one club's closed pool: 1,601 doubles matches among 189 players. A forthcoming report describes the evaluation. Under the rule for changing defaults, fixed before that evaluation ran, parameter set `v1` did not pass the gain bar. So the `Config()` defaults remain placeholders, and `v1` is a named set that a caller loads explicitly with `Config.published("v1")` ([parameters.md](parameters.md#why-config-is-not-v1)).

Ratings are provisional. They come from one club's closed pool. Ratings from pools that share no players are not comparable ([What a rating means](model.md#what-a-rating-means)). Parameters are retuned on a published schedule ([parameters.md](parameters.md#schedule), issue #48).

This is a transparent, configurable rating engine. It is not a reproduction of any proprietary rating algorithm. It supports ratings seeded from a verified snapshot of a standard external rating system, independently maintained OPEN ratings, unregistered player records, doubles categories that also feed the overall doubles rating, match-source weighting, game format weighting, inactivity-based uncertainty, rolling partner/opponent diversity, scale calibration, and deterministic historical replay.

This page holds the engine's published behavior notes and the requirements the backend must meet, moved here from the `engine.py` module docstring, the public docstrings, and the README. [`docs/model.md`](model.md) states the rating math. Many public docstrings name the section here that holds their edge cases.

## Stability

From 1.0.0, the engine follows strict Semantic Versioning. A breaking change to anything this section lists as covered needs a new major version. Before 1.0.0, a minor release may break it, and the changelog marks each break. `tests/api_surface.txt` records the public surface, and a test fails when the code no longer matches it. The file also records a few details this section leaves out, such as the `ledger_order` key type and the `Config` defaults, so that a change to them is deliberate.

Covered:

- Every name in `open_engine.__all__`, which the README's "Public API" section lists.
- The parameters of every public function, constructor, and method: their names, order, kind (positional or keyword-only), and defaults. The defaults of `Config` fields are the exception (see "Rating values" below).
- The fields of each public dataclass and their order, the members, values, and properties of each public enum, the error class hierarchy, and `LedgerConflictError.match_ids`. Each failure these notes document keeps its error class.
- The `RatingEngine` attributes `cfg`, `players`, `processed_match_ids`, `possible_duplicates`, `calculated_as_of`, and `replay_info`. They are for reading. Writing to them, or to the objects they hold, is unsupported: it skips validation and the mark that lets a snapshot resume.
- The ledger rules:
  - the order `ledger_order` gives ([Ledger order](#ledger-order)), but not the shape of its key;
  - every row passed in is validated, including rows after `as_of`;
  - rows that repeat a `match_id` count once only when they are the same match, and any other repeat raises `LedgerConflictError`;
  - the result does not depend on the order rows arrive in;
  - resuming from a checkpoint equals a full replay of the same ledger and seeds, or raises one of the errors [Replay and resume](#replay-and-resume) names (for example `LedgerConflictError` or `SnapshotError`), except for the limits that section lists.
- Published parameter sets. The values of a set this release publishes, such as `v1`, never change under its label. Retuning publishes a new label, such as `v2`. `Config.published` and `Config.from_parameter_set` check a set's values against the parameter fingerprint published for its label, so a set cannot change under the same label ([parameters.md](parameters.md#a-published-set-never-changes)).

Not covered:

- Snapshots. A snapshot is a cache that a replay can rebuild, and the ledger is the source of truth. A minor release may raise `snapshot_version`. A snapshot of an older version then raises `SnapshotError`, and a full replay rebuilds it ([Snapshots and checkpoints](#snapshots-and-checkpoints)).
- Rating values. A minor release may change default `Config()` values when parameters are retuned, so the same ledger can give other ratings. The changelog records each change, and `parameter_fingerprint()` and `fingerprint()` show it. `params_version` shows it only when the caller sets a published label. `Config.version` defaults to the package version, so it changes in every release.
- Additions in a minor release: new exports, new optional keyword parameters, new `Config` fields at the end of `Config` (each changes every `fingerprint()` and, unless it is added to the version labels, every `parameter_fingerprint()`), new fields at the end of an output dataclass, and new `RejectionReason` members. Code that reads a `RejectionReason` should handle a value it does not know.
- Changing engine objects in place. `RatingEngine.player()` returns the engine's own `Player` record, and `RatingEngine.state()` returns the engine's own `RatingState` when the player has one stored in that format, not copies. They are live views of engine state, as are the objects in `players`, and later calls change them. `Player` and `RatingState` are mutable dataclasses, but changing one the engine holds in place is unsupported: it skips validation and the mark that lets a snapshot resume, and a release may change what such a change does. A `MatchResult` is new output for each call, so changing one changes no engine state.
- Stored `Config.to_dict()` output. `Config.from_dict` takes exactly the keys of its own version, so a dict stored under another version can raise `ConfigError`. Keep the ledger and rebuild the config, as with a snapshot.
- Error message text, `repr` output, names reached only through `open_engine.engine`, `open_engine.winprob`, or a private module, and pickles made by another version. Keep the ledger: a full replay rebuilds the state under any version.

## Input types

Every public entry point takes exact input types for each argument it checks, with three carve-outs: Config(...) numbers, mappings, and allowed_game_formats, seed state numbers, ExternalRatingSnapshot numbers, and snapshot numbers are read once and converted to plain values; matches and seed_players may be any iterable, read once into a list before any row is checked; and output dataclasses are not inputs.

A subclass, or an object whose `__class__` only claims the type, raises the entry point's OpenEngineError subclass before any state changes: a subclass can give a check one value and rating another, or run caller code while it is read.

A plain date in these notes means exactly a date: a datetime or a date subclass is not one. An enum argument must be one of its enum's members, compared by identity: an object of the enum's own type that is not a member is rejected, and so is a str equal to a member's value. Numbers are exactly int or float (a bool is rejected where a number is expected), flags exactly bool, teams in `predict_point_share` exactly a tuple or list, a config None or exactly a Config (`reliability` takes no None), and a game format exactly a GameFormat; a Config or GameFormat must also hold nothing in its instance `__dict__` but its own fields. A GameFormat's field values are checked again, by type and by GameFormat's own rules, each time an entry point reads it. An entry point that takes a Config builds a fresh copy from its stored field values, checked again as Config(...) checks them, and uses only that copy (see [Config validation](#config-validation)).

Match.played_at, when set, must be exactly a datetime (not a subclass) that includes a time zone and falls on played_on in that zone. Its tzinfo must be exactly datetime.timezone or exactly zoneinfo.ZoneInfo (standard library C code that runs no caller code; its offsets come from its tz data, the tz database or the file given to ZoneInfo.from_file), with an offset that is exactly a timedelta of less than a day. On a Python build that uses the pure Python zoneinfo fallback, ZoneInfo instances have a `__dict__` and are rejected. A played_at without a time zone, any other tzinfo, a subclass of either included, and a timezone built from a timedelta subclass raise InvalidMatchError: the engine reads only the UTC instant and offset, so convert one with `played_at.astimezone(timezone(timedelta(seconds=played_at.utcoffset().total_seconds())))`, which gives plain values with the same instant and offset, and so the same ledger digest, so a stored ledger digest and a checkpoint still match. `astimezone` keeps a `datetime` subclass, so rebuild one first with `datetime(played_at.year, played_at.month, played_at.day, played_at.hour, played_at.minute, played_at.second, played_at.microsecond, tzinfo=played_at.tzinfo, fold=played_at.fold)`. A row with a `ZoneInfo` takes its offset from the machine's tz data, so a different tzdata version can change the ledger order and the ledger digests.

### `reliability` arguments

Raises EvaluationError unless state is exactly a RatingState whose rd is exactly an int or float that is finite as a float, rd_as_of None or exactly a date, and partners and opponents exactly dicts with exactly str keys and exactly date values; ConfigError unless cfg is exactly a Config with only its fields (it is rebuilt from its field values, see [Config validation](#config-validation), so a rewritten value it rejects raises too); and ReferenceDateError unless as_of is exactly a date. An rd too large to inflate for inactivity raises EvaluationError too, instead of OverflowError.

## Config validation

fingerprint() identifies the exact config behind published ratings: it hashes every field, version and params_version included. parameter_fingerprint() hashes every field but those two version labels, so it identifies the parameter values alone. The fields that change no rating but are not version labels, such as the reliability label settings, are still in it. The same values under another package version or another params_version give the same parameter fingerprint, and a change to any other field changes it. A release that adds, removes, or renames a Config field, or changes how a value is written in the payload, changes every parameter fingerprint even when no value changes. Both are 16 lowercase hex characters.

Mapping fields are stored as read-only copies whose values must be finite numbers, and allowed_game_formats as a frozenset of (scoring type, whole number) pairs. Keys and pairs are stored as their own types: a ScoringType or MatchType key given as its exact str value becomes the enum member (a str subclass, or a non-member object of the enum's type, raises ConfigError; each key is read once), and an int subclass becomes the plain int of its own value (not what its `__int__` returns). An allowed_game_formats pair's scoring type must be a member or exactly a str naming one (a str subclass or any other object raises ConfigError, before any of its own code runs), and its points a whole number (as defined below) of at least 1. Changing the dict or set a config was built from does not change the config, and changing the config's own raises TypeError. Two configs are equal exactly when their fingerprint payloads are equal, so equal configs share a fingerprint and a hash, and a Config can be a dict key or a set member. to_dict() and from_dict() store and load a config. `Config.from_dict` takes exactly a `dict`. So a key or points value always gives the same fingerprint as the plain enum member or int.

Every field is checked when the config is built, and any failure raises ConfigError. A number is an int or a float, never a bool, that is finite as a float: not NaN or infinite, and not an int too large to convert. A whole number is an int that is also a number. Where a number is allowed, an int or float subclass is accepted, and where a whole number is required (the whole-number fields, game_length_weights keys, and allowed_game_formats points), an int subclass is. Each is converted to the plain int or float of its own value (`int.__int__` or `float.__float__`) before any range or cross-field check, and stored that way, so for an exact Config the range checks, fingerprint(), and rating code read that plain value. A value whose `__class__` claims int or float while its real type is neither is rejected.

Config itself can be subclassed, but a subclass's own methods, such as an overriding `__post_init__`, could store other values, so every entry point that takes a config (RatingEngine, RatingEngine.from_snapshot, replay, prequential_predictions, evaluate, fit_scale, fit_win_calibration, and reliability) raises ConfigError for a subclass, for any other object that is not None (a falsy one included), and for an exact Config whose instance `__dict__` holds anything but its fields.

An exact Config can still be rewritten with `object.__setattr__` after it was built, so each of those entry points builds a fresh Config from the given one's stored field values and uses only that copy. Every check and the plain-value conversion run again: a rewritten value Config would reject raises ConfigError, and an int or float subclass becomes its plain value.

Each stored value is read by its real type alone, so no caller code runs while the copy is built. A mapping field must hold exactly a dict, or exactly the read-only copy a Config stores holding exactly a dict, with keys that are enum members or exact strs (game length keys real ints) and values that are numbers; allowed_game_formats must be exactly a frozenset or set of real tuple pairs, each a ScoringType member or exact str and a real int; and a scalar field an exact bool, an exact str, None, or a real int or float. Anything else raises ConfigError.

RatingEngine.cfg is that copy and is never the given object. For a Config that was not rewritten, the copy is equal to it and has the same fingerprint. For a rewritten one it can differ, since the rewritten object's own methods read what it holds, not its real values. Compare configs with == or fingerprint(), not is. The engine trusts its own stored copy: rewriting it after the call is outside the threat model. A caller's Config rewritten while replay or an evaluation function reads matches and seed_players is rebuilt too, since those build the copy after they read them.

fingerprint(), to_dict(), and == called on a rewritten Config itself read its rewritten values. fingerprint(), to_dict(), and from_dict() use the fields of Config itself, not of the instance or a subclass, so a subclass's extra fields do not change the fingerprint. So a built config always gives plain JSON, and fingerprint(), ==, and hash() never raise. The rules:

- version is exactly a str. params_version is None or exactly a str, checked right after version, and then has the form `v<N>`, where N is a positive whole number in ASCII digits with no leading zero: `v1` and `v12` pass, and `v0`, `v01`, `1`, `V1`, and `v1` with a trailing space or newline raise ConfigError. The three flags are exactly bools.
- Other scalar fields are numbers, except the day counts, the repeat, carry, verified match, and connectivity counts, and diversity_target, which are whole numbers. connectivity_reliability_cap and the two gap filters are None or a number. A float such as `7.0` is rejected.
- min_rating, max_rating, and default_rating are each at most `2**511` in magnitude, min_rating < max_rating, and default_rating lies between them. Within that range, team sums, rating gaps, and `imbalance` stay finite.
- Mapping values are numbers greater than 0, with exactly one key for every scoring type or match type. game_length_weights keys are whole numbers of at least 1, one for the points of every allowed format, and no two keys name the same length.
- allowed_game_formats is a set or frozenset by its real type (an object whose `__class__` only claims one is rejected before any of its code runs; a set or frozenset subclass is read once). Its entries are checked in passes, each over every entry: every entry is a tuple of two items, then no scoring type is a non-member ScoringType, then each pair's scoring type and points type, then the points minimum (the pair rule above). So the message never depends on set order or the hash seed. A tampered allowed_game_formats rebuilt by an entry point raises the first problem the rebuild's own checks find, in sorted message order; a pair those checks pass (for example points of 0) is caught afterwards, by the checks above. The points check runs after the checks of game_length_weights' own keys and values and each mapping field's "must be a mapping" and "values must be finite numbers" checks, and before the key and positive-value checks of scale_by_scoring, win_calibration_by_scoring, and match_weights, and before the check that every allowed format has a game length weight. A missing game length weight names the shortest such game length.
- 0 <= k_min <= k_max, and the largest K, k_min + (k_max - k_min) * 1.0 as player_k computes it (it can round just above k_max), times the largest match weight times max_information_multiplier is finite in floats. A self-reported match's step weight can be an exact int product: when the self-reported match weight, max_information_multiplier, and self_reported_repeat_factor are all ints, and information_multiplier can return max_information_multiplier itself. The check counts it as reachable when, for some (scoring, points) in allowed_game_formats, game_length_weights[points] * (1.0 + game_count_bonus * (sys.maxsize - 1)) is not below it (sys.maxsize is the most games len() can report). No real match has that many games, so the check can reject a config whose multiplier no real match reaches. When it is reachable, the self-reported weight times the multiplier must convert to a float, the largest K times that float must be finite, and with an int rd_shrink_per_match, rd_shrink_per_match times the exact product must convert too.
- 0 < rd_min < rd_max <= `2**511`, and rd_max - rd_min is greater than 0 as computed (an int and a float that are equal once converted are rejected). The three seed RDs lie within rd_min..rd_max. rd_shrink_per_match >= 0, and rd_growth_per_day is from 0 to `2**511`.
- Some bounds apply to ints only, because exact int arithmetic raises OverflowError where float arithmetic goes to inf: an int rd_growth_per_day is at most `2**500`, an int game_count_bonus at most `2**511`, and the exact self-reported step weight rule above. A float `game_count_bonus` has no upper bound beyond being finite.
- win_weight is from 0 to 1, game_count_bonus >= 0, max_information_multiplier >= 1, self_reported_repeat_factor is in (0, 1], and established_reliability_threshold and connectivity_reliability_cap are from 0 to 100.
- replay_interval_days, diversity_window_days, and self_reported_repeat_window_days are from 1 to 3,652,058 (the days from date.min to date.max, which timedelta holds), and import_reliability_max_age_days from 0 to that. A window that reaches back before date.min from a match or reference date stops at date.min instead of raising OverflowError. diversity_target, self_reported_max_repeats, and the three connectivity counts are at least 1; import_reliability_carry_matches and established_min_verified_matches at least 0.
- The gap filters are None or at least 0.

`Config.from_parameter_set(data)` loads a published parameter set from the parsed JSON of a `src/open_engine/params/v<N>.json` file (see [Maintenance and parameter versioning](parameters.md)). It trusts the label only when it names a set this release publishes, the recorded fingerprint is the one published for it, and the values hash to it. So a file cannot pass other values off as a published set or relabel one, and publishing a new set needs an engine release that adds it. It raises ConfigError, checking in this order:

1. data is not exactly a dict.
2. A key is not exactly a str.
3. params_version, parameter_fingerprint, or parameters is missing. The message names every missing one, sorted. Other keys are allowed and not read.
4. params_version, then parameter_fingerprint, is not exactly a str. Config accepts a None label, so this check keeps a file with a null label from loading as an unlabelled config.
5. parameters is not exactly a dict, has a key that is not exactly a str, or holds version or params_version.
6. parameter_fingerprint is not exactly 16 lowercase hex characters. The message does not show the value.
7. params_version does not have the form `v<N>`. The message does not show the value.
8. params_version is not a set this release publishes. The message names the sets it publishes.
9. parameter_fingerprint is not the one published for that label. The message names the label, the recorded fingerprint, and the published one.
10. `Config.from_dict` fails on the parameters with version set to the running package version and params_version set to the file's label. So from_dict's key and value checks apply unchanged.
11. The built config's `parameter_fingerprint()` differs from the recorded one. The message names the label, the recorded fingerprint, and the computed one.

It returns the config, with version the running package version and params_version the file's label.

`Config.published(label)` loads a set this release publishes from the file the package ships, and `Config.published_sets()` lists the labels in order. `published` raises ConfigError, checking in this order:

1. label is not exactly a str.
2. label is not in `published_sets()`. The message names the sets this release publishes and does not show the label. Only a label in the table is used to find a file.
3. The packaged file is missing, cannot be read, or is not JSON. The message names the label.
4. Any check of `Config.from_parameter_set` above, on the packaged file's parsed JSON.

It returns what `from_parameter_set` returns for that file.

## Errors

Every error the engine raises on purpose is an `OpenEngineError`, which is a `ValueError`. Each class, with what raises it:

- `OpenEngineError`: base class for every error the engine raises on purpose.
- `ConfigError`: a `Config` value is not valid, a `cfg` is not `None` or exactly a `Config` holding only its fields (`RatingEngine`, `RatingEngine.from_snapshot`, `replay`, the evaluation functions, the fits, and `reliability`, where `None` is not allowed), or a `GameFormat` is not valid when it is checked outside a match: by `GameFormat.validate`, the win probability functions, or `RatingEngine.predict_win_probability`.
- `InvalidMatchError`: a match, its teams, its scores, its `played_at`, or its `GameFormat` is not valid. `record`, `replay`, and `prequential_predictions` (and so `evaluate`, `fit_scale`, and `fit_win_calibration`) raise it for a match that is not exactly a `Match` (a subclass raises), before any state changes. `ledger_order` raises it for one too, and all of them raise it for a `Match` whose instance `__dict__` holds anything but its own fields.
- `InvalidSeedError`: an external or replay seed cannot initialize a rating. `RatingEngine.add_player`, `replay`, and `prequential_predictions` (and so `evaluate`, `fit_scale`, and `fit_win_calibration`) raise it for a seed that breaks the [Seed rules](#seed-rules). `replay` also raises it for a seed dated after `as_of` (see [Replay and resume](#replay-and-resume)), and `prequential_predictions` for one dated after its last completed ledger match (see [Prequential predictions](#prequential-predictions)). `RatingEngine.seed_external_rating` raises it when the rating format, `replace_unplayed_seed`, the snapshot or one of its fields, an existing rating, or the player's OPEN matches do not allow the seed (see [External seeds](#external-seeds)). `seed_provisional_rating` raises it for a rating format that is not a `RatingFormat`, before it checks the player id (see [Provisional states](#provisional-states)).
- `PlayerError`: a player identity, account link, or external identity is not valid. `RatingEngine.state` and `player_summary` raise it, after the player id checks, for a `rating_format` that is not a `RatingFormat` member. Once its rating format and snapshot fields pass their checks, `seed_external_rating` raises it for a blank player id or one that is not exactly a `str`, and once any existing rating and the player's OPEN matches in that format also allow the seed, for a snapshot external identity that cannot be linked (it is already linked to another player, or the player already has a different id from that source). `link_account` and `attach_external_id` raise it for a blank or whitespace-only value, a value that is not exactly a `str` (a subclass included), and for an account or identity already linked elsewhere. `attach_external_id` also raises it for a source that starts with the reserved prefix `open_` (see [Seed rules](#seed-rules)). `add_player` raises it for a seed whose account or external identity another player already holds, and `replay` and `prequential_predictions` raise it when two seeds share a player id, an `account_user_id`, or an external identity (the same source and external id). `replay(from_snapshot=...)` raises it for a seed whose player is already in the snapshot, or whose account or external identity a player in the snapshot holds.
- `UnknownPlayerError`: a `PlayerError` for a player id with no player record. `RatingEngine.player`, `RatingEngine.state`, and `RatingEngine.player_summary` raise it instead of creating the player. A player is created by `add_player`, `seed_provisional_rating`, `seed_external_rating`, `link_account`, `attach_external_id`, or a counted `record` (and so `replay`). An id named only in uncounted rows, or in rows after a replay's `as_of`, has no player record.
- `EvaluationError`: an evaluation, fit, or win probability cannot be computed. `fit_scale` and `fit_win_calibration` raise it, before any prediction work, when `low` is not less than `high`, `tolerance` is not finite and greater than 0, or `2 * low`, `2 * high`, or `(high - low) * 14` is not finite, so `low` and `high` must be finite and not near the float limit. `prequential_predictions`, `evaluate`, `fit_scale`, and `fit_win_calibration` raise it, naming the argument, for a `score_from` or `anchor` that is not `None` and not a plain `date` (a str, a datetime, or any other type), in both modes and for an empty ledger too, when no other argument fails first. `prequential_predictions` checks them first, before `mode` and before it reads the ledger. Then `mode` must be exactly `"live"` or `"scheduled"`, `scoring` `None` or exactly a `ScoringType` (the fits need a `ScoringType`), and `burn_in_matches` exactly an `int`. The fits check that `low`, `high`, and `tolerance` are exactly an `int` or `float` before anything else, and build no trial config before every argument passes (a `fit_scale` `low` of 0 or less then raises `ConfigError` from the trial config; `fit_win_calibration` builds no trial config). An int too large for a float raises it there too. The math functions (`expected_point_share`, the win probability functions) and `reliability` raise it for a number that is not exactly an `int` or `float` or not finite as a float, and for a value that passes but is too large to compute with (a game format long enough to overflow a float, a rating difference too large to divide, or an RD too large to inflate), instead of `OverflowError`; `expected_point_share` raises it for a `scale` of 0 or less, after its type and finiteness checks; `match_win_probability` raises it for a `best_of` too large to compute, `predict_win_probability` for a bad `best_of` before any prediction work, and `reliability` for a state that is not exactly a `RatingState` with exact field types and exact `str` keys in `partners` and `opponents`.
- `ReferenceDateError`: no usable reference date to measure inactivity and reliability at. `RatingEngine.player_summary` raises it when it gets no `as_of` and the engine was never replayed, or an `as_of` that is not a plain date (a datetime or a date subclass is not one), before it checks the player id. `replay` raises it for an `as_of` that is not a plain date, before any other check, and `reliability` for one too.
- `LedgerConflictError`: ledger rows share a `match_id` but differ. Its `match_ids` lists them.
- `SnapshotError`: a snapshot cannot be loaded or resumed from. `RatingEngine.from_snapshot` raises it for a malformed snapshot, one taken under another `Config`, or one holding a state the engine cannot produce, and `RatingEngine.to_snapshot` for state that could not load back. `replay(from_snapshot=...)` raises it for a snapshot not from a replay, one with live updates or any other change since its replay, an `as_of` before the checkpoint date, a row on or before the checkpoint date that the checkpoint did not see, a seed for a player named in a row the checkpoint saw, or, with `whole_ledger=True`, a row the checkpoint saw that is missing from the ledger. It also raises it for `whole_ledger=True` without `from_snapshot`.

## Ledger order

`replay` and `prequential_predictions` sort the ledger the same way whatever order the rows arrive in, so the result never depends on input order.

- Matches sort by `played_on` first, the calendar date at the venue. The rules below apply within one `played_on` date.
- On one day, matches without a `played_at` come first, by `sequence` and then `match_id`.
- Matches with a `played_at` follow, by the moment they were played in UTC (the UTC instant of `played_at`), then `sequence`, then `match_id`. A match at 21:00 at UTC-5 comes after one at 22:00 UTC on the same day.
- `played_at` follows the rules in [Input types](#input-types): it must include a time zone and fall on `played_on` in that zone, and a different tzdata version can change the order of rows with a `ZoneInfo`.
- Every row passed in is validated, including rows after `as_of`. An invalid row raises `InvalidMatchError` wherever it sits, for example one with a `played_at` without a time zone or a blank player id. A row with an invalid game format raises `InvalidMatchError` too. It is a `ValueError`.
- Rows that repeat a `match_id` count once when they are the same match: every field matches in type and value, recursively, so each member of a tuple, list, set, or frozenset must match in type too (so `3` and `3.0` differ), with `played_at` at the same moment and the same UTC offset. Any other repeat raises `LedgerConflictError`, a `ValueError` whose `match_ids` lists every conflicting id. This covers rows after `as_of` too.

## Match fields

status is the last field. Its rules, and how `record` and `replay` treat a match that is not completed, are in [Match status](#match-status).

The match must be a Match itself, not a subclass: record, replay, and prequential_predictions (and so evaluate, fit_scale, and fit_win_calibration) and ledger_order raise InvalidMatchError for a subclass before they change any state or call its validate, and Match.validate raises it for a subclass that does not override it. A subclass could return one value to validation and another to rating. The same calls raise it for a Match whose instance `__dict__` holds anything but its own fields, which could hide a method validate calls.

`Match.validate` checks the type of status, rating_format, match_type, game_format, team_a, team_b, confirmed_by, played_on, played_at, sequence, and best_of before it reads any of them, each exactly (a subclass, or an object whose `__class__` only claims the type, is rejected), and raises `InvalidMatchError` naming the field:

- `match_id`, every team player id, and every member of `confirmed_by` must be exactly a non-blank `str` (a subclass raises, with the message for a blank id).
- `status` must be a `MatchStatus`, `rating_format` a `RatingFormat`, and `match_type` a `MatchType`, so a str such as `"tournament"` raises even though it equals a member's value.
- `team_a` and `team_b` must be exactly tuples, and `confirmed_by` exactly a set or frozenset.
- `games` and each game in it must be exactly a tuple or list, for every status, and each score exactly an int (a subclass of any of these is rejected).
- `sequence` and `best_of` must be exactly ints (not a `bool`, a float, or an int subclass).
- `played_on` must be exactly a `date`, and `played_at` `None` or a datetime that follows the rules in [Input types](#input-types).
- `game_format` must be exactly a `GameFormat` holding only its fields. Inside it, `scoring` must be a `ScoringType` (a str such as `"rally"` raises), `points_to` and `win_by` exactly ints, and `cap` exactly an int or `None`; a `bool`, a float, or an int subclass is not accepted as an int.

The `GameFormat` rules are those of `GameFormat.validate`, which raises `ConfigError` for the same values when it is called directly. `Match.validate` calls it through the class, so a subclass's own `validate` never runs, and raises `InvalidMatchError` with the same message for a `ConfigError` that call raises.

## Match status

`Match.status` says how a match ended. It is a `MatchStatus` and defaults to `COMPLETED`. A status that is not a `MatchStatus` member, such as the plain text `"forfeit"` or `None`, raises `InvalidMatchError`. [Match fields](#match-fields) gives the type rules for `games`.

- `COMPLETED`: at least one game and a decided winner. Nothing changes for these matches.
- `FORFEIT`: the match was not played, so it must have no games.
- `RETIRED`: a player stopped, for example through injury, before a winner was decided.
- `INCOMPLETE`: the match stopped for another reason, such as time or weather.

A retired or incomplete match records zero or more finished games, each valid in its game format, and no decided winner. So in a best of 1 it has no games. A partial game in progress, such as `(7, 4)` to 11, is not recorded.

A match that is not completed is never rated: `record` validates the match, then checks the match_id before the status (a processed or reserved match_id gets DUPLICATE_MATCH_ID), and otherwise returns `RejectionReason.MATCH_NOT_COMPLETED`. It changes no rating, count, or content key, and is not marked processed, but like any rejected match it reserves its match_id (see [Match ids, rejections, and resubmission](#match-ids-rejections-and-resubmission)), so a forfeit relabeled as completed needs a new match_id live.

`replay` accepts such a row: it counts toward `ReplayInfo.matches_considered`, not `matches_counted`. A full replay gives each player the same rating states as a full replay of the ledger without those rows. Like any rejected row, a checkpoint tracks the row's digest and players, so resume raises SnapshotError for a new seed for a player named only in such a row. Replacing the row with a completed one under the same match_id is an edited row: on or before a checkpoint date it needs a full replay (resume raises LedgerConflictError when given it). In one ledger, a non-completed row and a completed row with the same match_id conflict (LedgerConflictError), so replace the row instead. `prequential_predictions` (and so `evaluate`, `fit_scale`, and `fit_win_calibration`) never predicts a match that is not completed, and takes its seed date limit and default anchor from completed rows only.

Rating a retirement on its finished games would change how ratings move, so it is not done; it would need a declared Config parameter backed by out-of-sample evaluation.

## Match ids, rejections, and resubmission

`record` validates every match first. A valid match whose `match_id` was already processed or reserved returns a result that is not counted, with `RejectionReason.DUPLICATE_MATCH_ID`, and changes nothing, instead of raising, unless its `as_of` is invalid (not a plain date, or earlier than `played_on`), which raises `InvalidMatchError` first. Every other match that `record` does not count, whatever its RejectionReason, reserves its match_id: it is not marked processed and moves no rating, count, or content key, but every later `record` call for a match with that id that does not raise returns DUPLICATE_MATCH_ID, with the same content or not.

That matches replay, where a match_id names one row: a second, different row with it is a LedgerConflictError, and an identical one collapses into the first. So a corrected resubmission needs a new match_id, live and in the ledger. Keep the rejected row in the ledger as it was.

Resubmit only after a rejection that comes from the row itself (GAME_FORMAT_NOT_ACCEPTED, SELF_REPORTED_UNCONFIRMED, MATCH_NOT_COMPLETED): for example a self-reported match resubmitted after confirmation, or a match corrected to an accepted game format. Under the same Config, replay never counts a row rejected for one of those, in any order. The other rejections depend on engine state, seeds, or other rows, so a row rejected live can count in a replay, and a copy of it under a new match_id could then count too. Do not resubmit those. For POSSIBLE_DUPLICATE, the ledger already holds a row with the same content. A replay under a different Config (a new allowed_game_formats or self_reported_requires_both_teams) can count rows rejected for game format or confirmation, so after such a change, review resubmitted rows before the replay.

A match rejected as a possible duplicate is also recorded in possible_duplicates. A match rejected for BEFORE_IMPORTED_BASELINE, SINGLES_RATING_GAP, or DOUBLES_PARTNER_GAP is also recorded, with its players and format, in seed_sensitive_rejections (see [Snapshot schema and checks](#snapshot-schema-and-checks)), and so is a counted category match whose overall doubles update is rejected for one of those, under doubles. A live reservation, and each of these records, clears the snapshot's resumable mark. A match with the same content as an earlier counted match under another match_id is flagged or, by config, rejected (see [Likely duplicates](#likely-duplicates)).

## Recording a match

Leave `as_of` unset for live processing (labeled provisional until the next replay). replay() passes a fixed as_of for authoritative rebuilds. `as_of` only labels the update as part of a replay and must not be earlier than the match date; the update itself does not depend on it. An as_of that is not a plain date (a datetime or a date subclass is not one), or one earlier than played_on, raises InvalidMatchError right after the match is validated, before any check that rejects the match. What `record` does with a match_id it has already considered, and what a rejected match reserves and records, is in [Match ids, rejections, and resubmission](#match-ids-rejections-and-resubmission). A match that is not completed is never counted (see [Match status](#match-status)). Live results apply in arrival order, so a match can be late (see [Late live matches](#late-live-matches)).

A match with the same content as an earlier counted match (same played_on, teams, and scores; see `MatchResult.possible_duplicate_of` in [Match results](#match-results)) goes through the other checks by default and, if it counts, has possible_duplicate_of set. With Config.reject_content_duplicates it is not counted, with RejectionReason.POSSIBLE_DUPLICATE. That check runs after the match_id and game format checks and before the self-reported checks, so a rejected duplicate never enters the self-reported log.

## Match results

reason is None when the match counted. deltas lists the rating changes. frozen and clamped list the players whose change was not fully applied. imbalance is the mean team A delta plus the mean team B delta, from the unrounded changes, rounded to 5 places. Each delta is rounded on its own, so imbalance can differ from the same sum of the rounded deltas by up to 1.5e-5. imbalance is in team-average units, so a match adds team_size * imbalance to the pool's total rating (twice the value in doubles). It is 0.0 for a match that did not count. When both teams have the same mean K and no player is clamped or frozen, the changes cancel in exact arithmetic, so imbalance is 0.0 except for float rounding, which shows at the fifth place only at very large ratings or steps (see [K and imbalance](#k-and-imbalance)). It can be nonzero when the teams' mean K differ, a player is clamped or frozen, or that rounding shows. A value of 0.0 does not mean nothing was clamped or frozen: read clamped and frozen for that. parent holds the overall doubles update for a category match, with its own imbalance.

late is True for a counted match dated before a player's last match in this rating format, or before the date that player's rating in this format already reflects (for a category rating copied from overall doubles). Frozen players count. Live recording applies matches in arrival order, so the backend should check late and, for a category match, parent.late, and schedule a replay when either is True. It compares dates only, so a match on the same date as a player's last match is not late. It is False for a match that did not count. parent has its own value, measured against the overall doubles dates. A late category match leaves its rd_as_of at the date that player's rating already reflects, so later live category matches dated before that date are late too.

possible_duplicate_of is the match_id of the earliest counted match the engine has seen with the same content: the same played_on, the same two teams (either side may be team A, in any player order), and the same game scores read from the same side. Other fields, the match_id and rating format included, are left out. It is None when there is no such earlier match. Only a counted match and a match rejected with RejectionReason.POSSIBLE_DUPLICATE (under Config.reject_content_duplicates) carry it; it is None on every other result and on parent. A real rematch on the same date with the same scores is flagged too, so it is a signal for the backend to check, not proof. Processing order alone decides which report is the copy, so the flagged or rejected one can be the stronger report (see [Likely duplicates](#likely-duplicates)). A category copy of a doubles match also reaches overall doubles through parent, whose possible_duplicate_of is None, so read this top-level field. Do not show it to whoever submitted the match: it names another report.

## Likely duplicates

The same match can be reported twice under different match ids. Two matches have the same content when they have the same `played_on`, the same two teams as sets of players (either side may be team A), and the same game scores in order, read from the same side. The match_id, match type, rating format, game format, best_of, played_at, sequence, and confirmed_by are left out, since two reports of one match often disagree on labels. The later match in processing order is the possible duplicate: arrival order live, ledger order in a replay, so a replay gives the same answer whatever order rows arrive in. Under the default `Config.reject_content_duplicates=False` it is not rejected for this: it goes through the other checks and, if it counts, its MatchResult has `possible_duplicate_of` set to the match_id of the first counted match with that content. With True it is not counted, with `RejectionReason.POSSIBLE_DUPLICATE` and `possible_duplicate_of` set.

Only counted matches are compared against, so a third copy points to the first, and a match that was rejected for any reason is not a target. A real rematch on the same date between the same teams with the same scores looks the same: the default flags it, and True does not count it, so keep the default where that matters and let the backend confirm. Reports that disagree on the date are not caught. RatingEngine.possible_duplicates maps each match flagged or rejected as a copy to the match_id it repeats, live and after a replay. An entry never clears: a counted copy's match_id is processed, and a rejected copy's match_id is reserved (see [Match ids, rejections, and resubmission](#match-ids-rejections-and-resubmission)).

Which report wins is set by processing order alone. With True, the report that survives is the first one to count in processing order (arrival order live; in a replay, ledger order as in the ledger order note: untimed rows on a date first, by sequence then match_id, then timed rows by the UTC instant of played_at, then sequence and match_id), whatever its match type, rating format, or game format. So a weaker or relabeled copy (for example an untimed self-report of a timed tournament match, or a mixed doubles copy of a doubles row) can count while the stronger report is rejected, a category copy that counts first can keep the other row from updating its rating format, and live recording and a replay can keep different rows. Under the default the same order decides which report is flagged, so the flagged row can be the stronger one. Use True only when the backend trusts who files reports; otherwise resolve flags in the backend.

Under the default, a category copy of a doubles match can count twice in overall doubles: once directly and once through its `parent` update. `parent` has `possible_duplicate_of` None, so read the top-level field.

## Late live matches

Live recording applies matches in arrival order. Only a replay gives play order. A live match is late when it is dated before a player's last match in its format, or before the date that player's rating in that format already reflects (for a category rating copied from overall doubles). It still counts, but it never moves last_played, rd_as_of, or a partner or opponent date back, and its MatchResult has `late` set to True. The backend should check `late` and, for a category match, `parent.late`, and schedule a replay when either is True. The engine stores dates, not times, so two matches on the same date that arrive out of played_at order are not flagged. Because dates never move back, a future-dated live match holds every date of its players at that future date until the next replay (see [Backend requirements](#backend-requirements)).

## K and imbalance

Each player moves by their own K (from their RD after inactivity): `sign * K * effective_weight * surprise`. A partner's or opponent's uncertainty never changes a player's step. Team average movement is not always zero-sum. Every MatchResult reports the net as `imbalance` (mean team A delta plus mean team B delta). When both teams have the same mean K and nothing is clamped or frozen, the changes cancel in exact arithmetic, so imbalance is 0.0 except for float rounding (reason 4). It can be nonzero for these reasons:

1. Unequal K: the team with the higher mean K moves more.
2. `clamped`: part of a player's change was not applied. A player is listed when the new rating, after the clamp to the rating floor and ceiling, differs from the float sum of the old rating and the raw change by more than 1e-12, or when the applied change differs from the raw change by at least 5e-6, half a unit in the fifth place, where it can show in deltas and imbalance. A loss that meets neither rule is not listed. That includes a range cut that float rounding of the sum absorbs before the clamp: such a cut is listed only under the 5e-6 rule. Rounding drops that much only at very large magnitudes: with the old and new rating both below 2**34 (about 1.7e10) in magnitude it cannot, and in a measured sweep with steps up to 1 the first such loss came at ratings of 2**36 (about 6.9e10).
3. `frozen`: the match is on or before a player's imported baseline date. The imported rating already reflects that match, so that player's rating is used for the expectation but does not move. Their teammates move by their own K only, so the team moves less.
4. Float rounding that is not listed. A rounding loss under 5e-6 is not listed in `clamped`, but the losses of several players can add up: with equal K and nothing listed, imbalance was measured at plus or minus 1e-5 for singles ratings near 2**36 in magnitude. Float rounding of the steps themselves can also show at the fifth place, when steps are far larger than the default config gives (K, match weights, or information multipliers many orders of magnitude above the defaults).

It is also 0.0 when the result matched the expectation, or when clamps or freezes on both teams cancel. So an imbalance of 0.0 does not mean nothing was clamped or frozen: read `clamped` and `frozen` for that.

Because team movement is not zero-sum, matches between high-K and low-K players can add rating to the pool or remove it. Colluding accounts can exploit this: a new account can gain rating by beating a low-K account again and again, or lose rating faster on purpose. `imbalance` is a per-match value in team-average units, so a match adds `team_size * imbalance` to the pool's total rating (twice the value in doubles). Each replay totals it per rating format in `ReplayInfo.net_rating_created`, from the unrounded changes, a category match adding to its own format and, when category_feeds_parent is on and its parent update counts, to doubles. The backend should store and monitor that total. Between replays it can add `team_size * imbalance` of each live MatchResult (and its parent); that running total is approximate, since imbalance is rounded to 5 places, and the next replay gives the exact total. The engine reports the total but does not limit it.

## Match performance

Match performance is team A's share of all points across the match's games, blended with the match result by Config.win_weight: `(1 - win_weight) * point_share + win_weight * (1 if A won else 0)`. The default win_weight is 0.0, pure pooled point share. So a team can win and still lose rating when it wins by less than its expected share (a 5.0 team beating a 4.0 team 11-9 in doubles). It can also happen when it wins a best of 3 (or 5) with fewer total points. There is no floor on a winner's change, other than the rating range (min_rating to max_rating). For one engine state, raising a team's point share by changing only the match's game scores, with the same number of games and the same result, never gives that team a worse change. Longer games and more games can carry more weight (up to Config.max_information_multiplier), so across game formats and game counts a slightly wider winning margin can still cost more rating. win_weight = 1.0 scores the result only, so a winner never loses rating. Values between 0 and 1 make a rating loss less likely. Only values close to 1 rule it out, and how close depends on the rating range and scale and on the lowest point share a winner can have. The default is a declared choice, not a validated one. It changes only when out-of-sample evaluation shows another value predicts better.

## Provisional and authoritative ratings

Authoritative ratings come from scheduled replays (see `Config.replay_interval_days`). Live updates between replays are provisional and are labeled with the count of live updates since the last recalculation, including the live updates a category rating copied when it was derived from overall doubles (`RatingState.inherited_live_updates`). A replay gives the same ratings as recording the same ledger live in ledger order: the replay date labels the result but never changes an update. Inactivity widens RD (`inflated_rd`) but never shrinks or discounts an old match's update.

## Imported ratings and reliability display

PlayerSummary.reliability is always OPEN-earned. An imported external reliability is shown separately, in PlayerSummary.imported_reliability, only until OPEN-earned reliability exceeds it or the carry limits in Config are reached; otherwise that field is None. It is not carried before its capture date, measured at the same reference date as reliability (see [Reference dates](#reference-dates)), so an unplayed import captured after the last replay is not shown by default; replay rejects such seeds. An external reliability never sets OPEN RD: an imported seed's RD is always Config.external_seed_rd.

## Seed rules

These rules apply to the seeds that `RatingEngine.add_player`, `replay`, and `prequential_predictions` take, except where a rule says only `add_player` checks it. The paragraphs after the list describe `add_player`.

Seed rules, checked for the seed and every rating state:

- The seed is a Player with a str id that is not blank or whitespace only, its ratings are a dict, every key is a RatingFormat, and every value is a RatingState. Its external_ids are a dict of str to str with no blank or whitespace-only source or id, and its account_user_id is None or a str that is not blank or whitespace only. The seed must be exactly a Player and each state exactly a RatingState, and every str and dict here, the provenance strs below, and partners and opponents must be exactly str and dict, not a subclass.
- rating, rd, initial_rating, and an imported reliability are ints or finite floats (not bool), the counts are ints, partners and opponents are dicts, dates are dates, initial_source is a str, and initial_external_player_id and initial_evidence_reference are each a str or None. An int or float subclass in rating, rd, initial_rating, or an imported reliability, and an int subclass in a count, is accepted, and is checked and stored as the plain int or float of its own value (`int.__int__` or `float.__float__`). A value whose `__class__` claims int or float while its real type is neither is rejected. The caller's Player and RatingState are not changed.
- initial_source is not blank or whitespace only, and neither is an initial_external_player_id or initial_evidence_reference that is set.
- No external_ids source starts with "open_", the prefix reserved for provenance the engine writes. The prefix is matched exactly, so "OPEN_x" or " open_x" is not reserved. An initial_source that starts with it has no imported reliability, initial_external_player_id, or initial_evidence_reference, and is one of two names. "open_provisional" (RatingState's default) has no initial_source_date, so a dated seed must set its own initial_source. In a category format, "open_parent:" plus that format's parent's value (doubles) needs Config.category_feeds_parent on, a doubles state in the same seed, an initial_source_date when that doubles state has one and none when it has none (the two dates may differ: the engine creates a derived state only at the player's first category match, with the doubles date, and then refuses a doubles reseed, and a doubles reseed refreshes an unplayed derived state a seed or snapshot holds; but a seed or snapshot made before that refresh existed, or built by a caller, can hold another date), and an RD of at least Config.category_seed_rd. An undated one also needs a played doubles state, which a seed cannot have, so such a seed is always rejected. A seed taken from an engine with category_feeds_parent on is rejected by one with it off when it holds an "open_parent:" state. These rules do not check the rating or the date against the doubles state's, so a seed can still claim a derived state with any rating in range, and an "open_provisional" seed can carry any rating in range.
- An initial_external_player_id that is set is linked in the seed's own external_ids under initial_source, so the uniqueness check below covers it. Since the seed must be exactly a Player, each state exactly a RatingState, and these ids exactly str and dict, a seed cannot carry another player's external identity as its provenance.
- No matches, last_played, partners, opponents, or live updates: matches_played, verified_matches_played, live_updates_since_replay, and inherited_live_updates are 0.
- rating and initial_rating are within Config.min_rating and Config.max_rating.
- A provisional state (no initial_source_date) has RD new_player_rd, no rd_as_of, and no imported reliability.
- An imported state, or a category state derived from one, has RD external_seed_rd or max(external_seed_rd, category_seed_rd), rd_as_of equal to initial_source_date, and an imported reliability that is None or between 0 and 100.

Played states are rebuilt through replay instead.

- The seed has no state in the format of an update record rejected for BEFORE_IMPORTED_BASELINE, SINGLES_RATING_GAP, or DOUBLES_PARTNER_GAP that names the seed's id, nor, under Config.category_feeds_parent, in that format's parent, as seed_external_rating refuses. Only add_player checks this, after the other seed rules and the duplicate id check and before the account and external identity uniqueness checks: replay and prequential_predictions add their seeds before any row, and resume refuses a seed for any player in a row its checkpoint considered.

add_player has no reference date, so it does not check that initial_source_date is in the past: replay rejects a seed dated after its as_of, and prequential_predictions one dated after its last match. Under Config.category_feeds_parent, an unplayed category state in a seed fixes where that category starts (see [External seeds](#external-seeds)).

Raises InvalidSeedError for a seed that breaks these rules (a seed that is not exactly a Player (a subclass included), or has a blank id or one that is not a str (a str subclass included), is checked before the duplicate id), and PlayerError if the id exists, or if another player already holds the seed's account_user_id or one of its (source, external id) pairs, with the messages link_account and attach_external_id use. Nothing changes when either is raised.

## External seeds

These notes cover `RatingEngine.seed_external_rating`.

The external rating is an initial condition, not a live dependency. Once OPEN matches exist, external refreshes cannot overwrite the rating. That holds in every rating format: it refuses to replace a category state derived from overall doubles (initial_source "open_parent:" plus the parent's value; an import through this method cannot take that name, since a source that starts with "open_" is rejected), and it refuses to seed a format in which a counted OPEN update included the player, even one in which the player was frozen, with or without a stored state in that format. For overall doubles, that includes the doubles update of a category match. Under category_feeds_parent, it also refuses to seed overall doubles when a counted category match included the player, whatever the player's state in that category is: a new doubles seed could change whether that match's doubles update counts, or the state a replay starts the category from. Otherwise a new seed rating or date could change a counted match, so live ratings and a replay could disagree. Without replace_unplayed_seed=True it never replaces a stored state. It also refuses to seed a player named in an update record rejected for BEFORE_IMPORTED_BASELINE, SINGLES_RATING_GAP, or DOUBLES_PARTNER_GAP (a match's own update, or the doubles update of a counted category match; see seed_sensitive_rejections in [Snapshot schema and checks](#snapshot-schema-and-checks)) when the seed's format is that update's format or, under category_feeds_parent, its parent. Those reasons read the players' ratings or dates, and a replay adds every seed before any row, so a new seed could make the replay count an update live rejected. This holds with or without replace_unplayed_seed, and for a player with no record yet. A rejection for another reason is not recorded and blocks no seed. A backend that needs a new seed for such a player rebuilds with a full replay from the corrected seeds. A category format with no stored state, no counted match, and no such rejected update can still be seeded, even when the player has an overall doubles rating. Under category_feeds_parent, a successful seed of overall doubles also replaces each of the player's stored category states that is unplayed and derived from overall doubles (initial_source "open_parent:doubles") with the state a category match would start from right after the seed: the new rating and date, with an RD of at least Config.category_seed_rd. Other category states, imported or provisional, are not changed. Such a stored derived state comes from a seed (add_player, replay seeds) or a loaded snapshot: seed_provisional_rating does not store one. An unplayed category state that a seed (add_player, replay seeds) or a loaded snapshot holds fixes where that category starts: it does not follow later changes to the doubles state from matches, and an "open_provisional" one does not follow a later doubles seed either (only an unplayed "open_parent:doubles" one is refreshed by a doubles reseed). A replay without that seed can then differ from live recording. The seed's RD is always Config.external_seed_rd: an external reliability is kept for display (imported_reliability), never turned into OPEN RD. There is no reference date here, so a snapshot captured in the future is accepted; the next replay with an earlier as_of rejects the seed.

rating_format must be exactly a RatingFormat (a str is not converted), replace_unplayed_seed exactly a bool (0, 1, and None are rejected), snapshot must be exactly an ExternalRatingSnapshot (not a subclass), and the snapshot is checked before anything changes: captured_on is exactly a date (not a datetime or a date subclass), source is a str that is not blank or whitespace only and does not start with "open_" (the prefix reserved for provenance the engine writes, matched exactly), external_player_id is None or a str that is not blank or whitespace only, evidence_reference is None or a str that is not blank or whitespace only (each of these strs exactly a str, not a subclass; the same evidence reference may be used for many seeds), rating is an int or finite float (not bool) within the rating bounds, and reliability is None or an int or finite float (not bool) between 0 and 100. An int or float subclass rating or reliability is checked and stored as the plain int or float of its own value, and a value whose `__class__` only claims int or float is rejected; the caller's snapshot is not changed. An external_player_id links the (source, external_player_id) pair to the player, and None links nothing. So every state seeded here passes the [Seed rules](#seed-rules).

Raises InvalidSeedError when the rating format, replace_unplayed_seed (not exactly a bool), the snapshot or a checked snapshot field, the existing rating, or the player's OPEN matches (counted, or rejected for a reason a seed can change) do not allow the seed. Once the rating format and snapshot fields pass their checks, it raises PlayerError when player_id is blank or not a str (a str subclass included). Once any existing rating and the player's OPEN matches also allow the seed, it raises PlayerError when the snapshot's external identity is already linked to another player, or when the player already has a different id from that source. Every check runs before anything changes, so a failed call creates no player.

## Provisional states

These notes cover `RatingEngine.seed_provisional_rating`.

The player's state in a format. Stores a new unplayed state if it is missing, except in a category format under Config.category_feeds_parent.

Creates an empty player record for an unknown player_id. A state the player already has in the format is returned as stored. For a format the player has none in, it builds the starting state the player's first match in that format would use if played now, as state does. In singles and overall doubles, and in a category format (mixed, men's, or women's doubles) while category_feeds_parent is off, it stores that state and returns the stored object. In a category format while category_feeds_parent is on, it returns the state without storing it: that state starts from the player's overall doubles state, and a stored copy would not follow later changes to doubles, so live recording and a replay of the same matches could disagree. The returned object is then a new copy each call, not engine state, and changing it changes nothing; the engine state is unchanged apart from the player record created for an unknown id.

Raises InvalidSeedError when rating_format is not exactly a RatingFormat (a str is not converted), before it checks the player id, and PlayerError for a player_id that is blank or not exactly a str (a subclass is rejected). Both are checked before anything changes, so a failed call creates no player.

## Reference dates

player_summary measures inactivity, RD, and reliability at a reference date. With no as_of, it is the later of the last replay date (calculated_as_of) and the player's last match. So a stale player is measured at the replay date and loses reliability from RD and variety as replays move forward (with the connectivity cap set, connectivity can still change; see [Network connectivity](#network-connectivity)), and a player with live matches since is measured at their last match. Players in one engine can be measured at different dates. With no as_of on an engine that was never replayed, it raises ReferenceDateError, as it does for an as_of that is not a plain date. An as_of earlier than the player's last match does not rebuild past state: RD and partner variety stay as of the stored state. `reliability` takes as_of as a required argument. The engine never reads the wall clock.

## Established

PlayerSummary.established is True when OPEN-earned reliability, as displayed (rounded to 1 place), is at least Config.established_reliability_threshold (60 by default) and the state has at least Config.established_min_verified_matches (3 by default) counted tournament, league, or recreational verified matches (RatingState.verified_matches_played). Self-reported matches never count toward that minimum, and neither does a match in which the player was frozen. So while the minimum is above 0, a player with fewer counted verified matches in the format than the minimum is not established at any reliability. A category state derived from overall doubles starts its count at 0, as it starts matches_played at 0. With a minimum of 0 the rule is reliability alone.

Imported reliability never counts toward established, and established is measured at the same reference date as reliability, so it lapses with inactivity unless the connectivity cap is set and connectivity changes (see [Network connectivity](#network-connectivity)).

Under the defaults, a new player with no imported rating, playing one match a week with varied partners and opponents, becomes established after about 10 to 13 tournament, league, or recreational verified matches (10 tournament, 11 league, or 13 recreational verified matches of one game, fewer for best of 3), and after about twice as many against the same players. Self-reported matches raise reliability past the threshold after about 20 to 25 with varied players (never against the same players, because repeat matches are discounted and then rejected), but such a player is established only once they also have the minimum of counted verified matches. A player seeded from a recently captured imported rating starts at a lower RD (Config.external_seed_rd) and is established after about 3 to 4 tournament, league, or recreational verified matches. RD grows from the capture date, so an older import gives less of a head start, and a very old one none. The imported rating and its reliability value do not change the count.

A rating that is not established is what external rating systems usually call provisional. That is different from OPEN's provisional live updates between replays and from the open_provisional initial source. The threshold is a label only, and so is the minimum: neither changes any rating, prediction, evaluate, prequential_predictions, fit_scale, or fit_win_calibration output. Evaluation has its own eligibility rule: it scores a match only when every participant has an imported baseline or at least burn_in_matches OPEN matches. That rule is separate from PlayerSummary.established. With Config.connectivity_reliability_cap set, the counts above are for a player whose network connectivity is connected (see [Network connectivity](#network-connectivity)).

## Network connectivity

Network connectivity (PlayerSummary.connectivity, a NetworkConnectivity): RD and variety cannot see whether a player's partners and opponents ever play anyone outside their own group, so a closed pool that plays only itself could reach full variety, low RD, and established on its own private scale.

player_summary measures it per rating format, at the reference date, over Config.diversity_window_days, from the partners and opponents stored in each rating state (no other data, so a snapshot or a resume carries it and it needs no snapshot field).

Two players with a state in the format are in contact when either one's state lists the other with a date in the window. A group is a set of players linked by contact, and it is a main network when it has at least half as many players as the largest group, so two separate networks of similar size are each a main network. The label depends on group sizes alone.

Two players in contact are tied when they share at least Config.connectivity_min_shared_contacts (4) contacts and each of them is in contact with those shared players on at least Config.connectivity_min_contact_days (3) distinct dates. A pool is a set of players linked by ties; a player with no tie is a pool of one. The pool's fringe is every player outside it in contact with it whose own contacts are all in the pool or in contact with it, such as a drop-in who met only the pool. Its outside players are the other players in contact with it. A player is connected when they have a contact in the window, their group is a main network, and either the pool with its fringe holds more than half the group, or the pool has at least Config.connectivity_min_outside_players (8) outside players on at least connectivity_min_contact_days distinct contact dates with them.

connectivity is always reported. When Config.connectivity_reliability_cap is set (it is None, off, by default), a player who is not connected has PlayerSummary.reliability at most the cap, shown rounded down to 1 place, so with a cap below the established threshold they are not established. The cap is off by default because the rule can be gamed through group sizes (the limits below) and can cap players in a real but smaller network; it waits for out-of-sample review of real ledgers. The cap changes the displayed reliability only: `reliability()` gives the value from RD and variety, and no rating, RD, K, prediction, evaluate, prequential_predictions, fit_scale, or fit_win_calibration output reads either. connectivity is built for every summary, with the cap on or off.

Limits: a pool in a main network that with its fringe holds more than half its group is that group's own scale, which no ledger can place on another, so a club in a main network that outnumbers the players it met is not capped and can leave them capped; pools that play each other but not the rest of their group count each other's players as outside players; accounts the backend has not verified can pose as outside players if they also play players the pool never met, and a cluster of accounts more than twice the size of a real network makes that network no longer a main network; drop-in accounts, or one match between two closed groups, can make a closed group large enough to be a main network or to hold more than half its group; a player whose only contacts are a closed group can count its members as outside players when they have not tied with that player (for example when the group plays so densely that every contact keeps one last date); a single match between two real networks can make the smaller one no longer a main network; a state keeps only the last date per contact, so repeated contact with the same player counts one date; contacts leave the window as the reference date moves on, so connectivity can change with no new match, and a player can become connected (with the cap set, reliability then rises up to the value from RD and variety) when the groups that outnumbered theirs drop out of the window; and, as for variety, an as_of earlier than the stored state does not rebuild past contacts.

A summary for a format the player has no state in is measured as if the starting state RatingEngine.state returns were stored: a player with no contacts, so not connected. The result for one format and reference date is rebuilt after each state change (the engine keeps the 16 most recent), which costs about the sum over players of their contacts times their contacts' contacts.

### `NetworkConnectivity` fields

Measured over Config.diversity_window_days at the summary's reference date, from the partners and opponents stored in each rating state. Two players with a state in the format are in contact when either one's state lists the other with a date in the window. A group is a set of players linked by contact. A group is a main network when it has at least half as many players as the largest group, so two separate networks of similar size are each a main network.

Two players in contact are tied when they share at least Config.connectivity_min_shared_contacts contacts and each of them is in contact with those shared players on at least Config.connectivity_min_contact_days distinct dates. A pool is a set of players linked by ties; a player with no tie is a pool of one. The pool's fringe is every player outside the pool who is in contact with it and whose own contacts are all in the pool or in contact with it: a drop-in who met only the pool and its other contacts. The pool's outside players are the other players outside it in contact with it, and outside_days counts the distinct contact dates between the pool and them.

connected is True when the player has a contact in the window, their group is a main network, and either the pool with its fringe holds more than half the group's players, or the pool has at least Config.connectivity_min_outside_players outside players on at least Config.connectivity_min_contact_days outside days. When it is False and Config.connectivity_reliability_cap is set (it is None by default), PlayerSummary.reliability is at most that cap. It is a label only and changes no rating. The rule can be gamed through group sizes; see the limits above.

## Player summaries

These notes cover `RatingEngine.player_summary`.

as_of sets the reference date that inactivity and reliability are measured at. With no as_of, it is the later of calculated_as_of (the last replay date) and the player's last_played. So a stale player is measured at the replay date, and a player with live matches since at their last match. Players in one engine can be measured at different dates by default. A late live match never moves last_played back. The engine never reads the wall clock.

An as_of earlier than the player's last match does not rebuild past state: RD and partner variety stay as of the stored state.

connectivity is measured at the same reference date over every player's stored state in the format (see [`NetworkConnectivity` fields](#networkconnectivity-fields)), and when Config.connectivity_reliability_cap is set, reliability is at most the cap when it is not connected. The result for one format and date is cached until the next state change through the engine's own methods, for the 16 most recent dates; changing objects the engine returns directly is not tracked.

imported_reliability is not carried when the import's capture date is after the reference date. So an unplayed import captured after the last replay is not shown by default until the next replay or an explicit as_of.

live_updates_since_recalculation labels the provisional movement in the rating: the state's own live updates since the last replay, plus, for a category state derived from overall doubles, the parent's live updates already in the rating it copied (see [`PlayerSummary` fields](#playersummary-fields)).

It never changes engine state; it only fills a private cache of connectivity results, derived from the stored states. For a known player with no state in the format, it reports the starting state the player's first match in that format would use if played now (see state), without storing it.

Raises ReferenceDateError when as_of is None and the engine was never replayed, or when as_of is not a plain date (a datetime is not one). These checks come first. After those checks, it raises `PlayerError` for a blank player id or one that is not exactly a `str`, and `UnknownPlayerError` for a player id with no player record. Then it raises PlayerError for a rating_format that is not exactly a RatingFormat.

### `PlayerSummary` fields

reliability is always OPEN-earned. imported_reliability is the imported external reliability, rounded to 1 place, while it is carried, otherwise None. It is carried when it was captured on or before the reference date (player_summary's as_of, else the later of the engine's calculated_as_of and the player's last_played), is fresh, is within the carry match limit, and is higher than the earned value. It is shown separately and never replaces or converts into reliability.

When Config.connectivity_reliability_cap is set (None, off, by default), reliability is at most the cap while connectivity.connected is False (see [`NetworkConnectivity` fields](#networkconnectivity-fields)). connectivity is always reported.

established is True when reliability (as displayed, rounded to 1 place) is at least Config.established_reliability_threshold and the state's verified_matches_played (counted tournament, league, and recreational verified matches) is at least Config.established_min_verified_matches. Self-reported matches never count toward that minimum. Imported reliability never counts toward established, and established is measured at the same reference date as reliability, so it lapses with inactivity unless the connectivity cap is set and connectivity changes. A recently captured imported rating can reach the threshold in fewer OPEN matches because of its lower starting RD; see [Established](#established) for counts. It is a label only and changes no rating. A rating that is not established is what external rating systems usually call provisional. That is different from OPEN's provisional live updates between replays and from the open_provisional initial source. Evaluation's eligibility rule (an imported baseline or at least burn_in_matches OPEN matches) is a separate rule from established.

live_updates_since_recalculation counts the live updates since the last replay that are in the state's rating: the state's own live_updates_since_replay plus its inherited_live_updates, which for a category state derived from overall doubles is the parent's live count when the state was derived. It is 0 right after a replay.

config_version, params_version, and parameter_fingerprint name the engine's config: its `Config.version`, its `Config.params_version` (None means the config is not a published parameter set), and its `parameter_fingerprint()`. params_version and parameter_fingerprint, after connectivity, are the last two fields. They are provenance and change no rating. A summary is not stored in a snapshot, so they need no snapshot change.

## Replay and resume

These notes cover `replay`.

Run on the published schedule (Config.replay_interval_days). Same ledger, seeds, config and as_of always produce the same result, whatever order the ledger rows arrive in. Every row is validated, even after as_of, and rows that repeat a match_id count once or raise LedgerConflictError as [Ledger order](#ledger-order) describes.

Raises ReferenceDateError for an as_of that is not a plain date (a str, a datetime, a date subclass, None, or any other type). It checks this first, before whole_ledger, from_snapshot, the ledger rows, and the seeds. Then it raises SnapshotError for a whole_ledger that is not exactly a bool (an int, str, or None is a usage error of the resume API, not a ledger flag), and ConfigError unless cfg is None or exactly a Config with only its fields, before matches, seed_players, and from_snapshot are read. It reads matches and seed_players once each, into lists, before any row or seed is checked. Only after reading them is cfg rebuilt from its field values (see [Config validation](#config-validation)), so a rewritten value it rejects raises ConfigError too, even one rewritten while those iterables were read, and the result's cfg, replay_info fingerprint, and snapshots come from that copy.

Raises InvalidSeedError for a seed that is not an unplayed imported or provisional state that follows the [Seed rules](#seed-rules), or whose initial_source_date is after as_of, and PlayerError when two seeds share a player id, an account_user_id, or a (source, external id) pair.

from_snapshot resumes from a checkpoint: the to_snapshot() output (or json.loads of its text) of an earlier replay under the same cfg (see [Snapshots and checkpoints](#snapshots-and-checkpoints)), as in `replay(matches, seeds, cfg=cfg, as_of=later, from_snapshot=snapshot)`. Only rows dated after the checkpoint date are recorded. Rows dated on or before it are not recorded again: each must be a row the checkpoint considered, unchanged. matches may hold the whole ledger or only the rows dated after the checkpoint, and seed_players holds only seeds not in the checkpoint. The result equals a full replay to as_of of the ledger and seeds the rows come from (the checkpoint's seeds plus seed_players).

whole_ledger=True (keyword only, with from_snapshot) promises that matches holds the whole ledger, so pass it whenever you pass the whole ledger: resume then also checks for checkpointed rows that are missing (see the list below). whole_ledger=True without from_snapshot raises SnapshotError.

Resume checks every row first and raises instead of giving a different result:

- SnapshotError for a malformed snapshot or one taken under another Config (see [Snapshot schema and checks](#snapshot-schema-and-checks)), a snapshot not from a replay, one with live updates or any other change since its replay (its `resumable` mark is false), an as_of before the checkpoint date, a row dated on or before the checkpoint date that the checkpoint did not consider (compared by a digest that mirrors the ledger's duplicate rule), or a seed for a player named in a row the checkpoint considered (even when every such row was rejected, so the player is not in the snapshot).
- LedgerConflictError for a row dated on or before the checkpoint date that differs from the row the checkpoint considered under its match_id, or a row dated after it that reuses one of those ids.
- PlayerError for a seed whose player is already in the snapshot, or whose account_user_id or (source, external id) pair a player in the snapshot holds.
- SnapshotError, with whole_ledger=True, for any row the checkpoint considered that is missing from matches (a row voided or deleted on or before the checkpoint date), naming every missing id, sorted.

The rows are checked in this order: LedgerConflictError for changed or reused rows, then SnapshotError for rows not in the checkpoint, then (with whole_ledger) SnapshotError for checkpointed rows that are missing.

Resume detects every row it is given that disagrees with the checkpoint. It cannot detect a seed that was withdrawn or corrected after the checkpoint, with or without `whole_ledger`. It cannot detect a late (backdated) row on or before the checkpoint date that you leave out, so given only the newer rows it cannot see one. Without `whole_ledger=True`, it also cannot detect a row on or before the checkpoint date that was removed (voided) from the ledger, or an edited one that you leave out. A void, an edit, or a late row on or before the checkpoint date, and a seed withdrawn or corrected after the checkpoint, each need a full replay. Resume raises for such an edited or late row when you pass it, and for a void when you pass `whole_ledger=True`, but the fix is still a full replay. Store a match before the replay that covers its date.

## Snapshots and checkpoints

`RatingEngine.to_snapshot()` returns the engine's whole state (schema version 9) as plain JSON data, and `RatingEngine.from_snapshot(snapshot, cfg)` builds the engine back, from the dict or from `json.loads` of its text, after validating every key, type, and range and checking the config version and fingerprint, and replay_info's params_version and parameter fingerprint, against cfg (see [`RatingEngine.to_snapshot`](#ratingengineto_snapshot), [`RatingEngine.from_snapshot`](#ratingenginefrom_snapshot), and [Snapshot schema](#snapshot-schema)). A snapshot of a replay is a checkpoint, which `replay(..., from_snapshot=snapshot)` resumes from (see [Replay and resume](#replay-and-resume)).

Take the checkpoint snapshot right after the replay, before any other call on the engine. Every engine method that changes state makes the snapshot one resume refuses, by setting its `resumable` mark, which replay sets, to false: a live match, a seed, an account or external id link, a new player, or a new rating state. Reads (`player`, `state`, `player_summary`, the predictions, and `to_snapshot`) change nothing, so they keep the snapshot resumable. So does `seed_provisional_rating` for a player that already has a record when it stores nothing: for a player with a stored state in that format, and in a category format while `category_feeds_parent` is on. Changing objects the engine returns or its public attributes (for example `players`, rating states, or `processed_match_ids`) directly is not tracked, and makes the snapshot unsafe to resume.

A stored snapshot sets every rating when it is loaded. Give it the same write protection as the ratings themselves. `from_snapshot` checks its shape and the engine's invariants (its rules), not that it is authentic.

## Snapshot schema and checks

### `RatingEngine.to_snapshot`

json.dumps(snapshot, allow_nan=False) works with no custom encoder, and RatingEngine.from_snapshot rebuilds the engine from it, or from json.loads of its text. Every dict is emitted with sorted keys and every list in a fixed order, so the same state always gives the same text. Numbers keep their type: an int stays an int.

[Snapshot schema](#snapshot-schema) lists the keys.

To use the snapshot as a checkpoint, and to store it, see [Snapshots and checkpoints](#snapshots-and-checkpoints).

The snapshot is checked with the rules from_snapshot applies, so state that could not load back (a value of the wrong type, a rating out of bounds) raises SnapshotError naming the field instead of being returned.

### `RatingEngine.from_snapshot`

cfg must be the Config the snapshot was taken under (default Config()): its version and fingerprint must equal the snapshot's, and its params_version and parameter_fingerprint() must equal replay_info's. Each is checked against the given config, never taken from the snapshot. cfg must be None or exactly a Config with no attributes beyond its fields, or it raises ConfigError before the snapshot is read. The engine keeps a copy of cfg rebuilt from its field values (see [Config validation](#config-validation)), and the fingerprint check reads that copy.

The whole snapshot is validated before anything is built: exactly a dict for every object and exactly a list or tuple for every list (another container type, a dict subclass included, is rejected), exactly a bool for resumable, exactly the schema's keys at every level, snapshot_version 9, dates as YYYY-MM-DD text, non-blank str ids with no repeated player or match id (ids, external_ids sources and ids, and provenance strs exactly str, not a subclass), RatingFormat values as format keys, ratings within min_rating and max_rating, RD within rd_min and rd_max, an imported reliability between 0 and 100, nonnegative int counts no larger than `2**63 - 1` (an int or float subclass where a number is allowed, or an int subclass for a count, is checked and stored as the plain int or float of its own value, except net_rating_created, which must be exactly a float), replay_info present exactly when calculated_as_of is and consistent with it (its config_version and config_fingerprint equal to the snapshot's, its params_version null or exactly a str equal to cfg's, its parameter_fingerprint exactly a str equal to cfg's, and its net_rating_created a finite float, not a negative zero, so a resume continues from the exact value a full replay had, for every RatingFormat, 0.0 for every format when matches_counted is 0 and for a format in which no player has a played state), self-reported matchups of two disjoint teams of the format's size, content keys and ledger digests of 64 lowercase hex characters, content keys that each name a different processed match id, possible duplicates that each name another match that is a content_keys value and whose own id is not one, a possible duplicate id that is a processed match id under the default config and is not one under reject_content_duplicates (and, in a resumable snapshot, is a ledger_digests id under either config, since a replay records a copy only for a row it considered; a live snapshot can hold a rejected id that no replay saw), reserved match ids with no repeats and none in processed_match_ids (and, in a resumable snapshot, each a ledger_digests id), every possible_duplicates key a reserved id under reject_content_duplicates, every ledger_digests id processed or reserved, and a bool resumable that is false without a replay.

Each seed_sensitive_rejections entry has a RatingFormat value as rating_format and, as players, exactly twice that format's team size of non-blank str ids, sorted with no repeats. Its match_id is a reserved id that is not a possible_duplicates key, or a processed id with rating_format doubles under category_feeds_parent whose every named player is in players, one of them with a played category state that has one other named player as a partner and the other two as opponents. With no gap rule for its format (max_singles_rating_gap for singles, max_doubles_partner_gap for the others), every named player has a state with an initial_source_date there or, with none stored, under category_feeds_parent in a category format, an overall doubles state with one. In a resumable snapshot every named player is in ledger_player_ids.

Every state must be one an engine release can produce: initial_rating within the rating bounds; an unplayed state with RD new_player_rd, external_seed_rd, or at least category_seed_rd, and no partners, opponents, or live updates; matches_played 0 exactly when last_played is null; live updates and verified matches no more than matches played; no player their own partner or opponent; an imported reliability only with an initial_source_date; a nonzero inherited_live_updates only on a category state derived from its parent (category_feeds_parent on, initial_source "open_parent:" plus the parent's value) with a parent state, no more than the parent state's live updates, the parent's initial_source_date, and no imported reliability, external player id, or evidence reference; while such a state is unplayed, also an RD of at least category_seed_rd and an rd_as_of that is set and no later than the parent state's. This engine no longer creates an unplayed state with a nonzero inherited_live_updates (issue #112); these rules accept one as an earlier release's seed_provisional_rating stored it, so its snapshots still load.

Every partner, opponent, and self-reported team member is a player in the snapshot. Each state's matches_played - verified_matches_played (its self-reported updates) is at most the self-reported log dates in its format that name the player, plus, for doubles under category_feeds_parent, those in the category formats. For a state with no initial_source_date, and for every state of a resumable snapshot counting only log dates after its initial_source_date, an overall doubles count under category_feeds_parent with max_doubles_partner_gap set is at least the logged doubles matches, since the gap can reject a category match's doubles update; every other such count equals the logged matches in its format, plus, for doubles under category_feeds_parent, the logged category matches. A snapshot that is not resumable does not record when each seed was set, so for a state with an initial_source_date there only the upper bound is checked. For each self-reported log entry's latest date, every named player has a baseline dated on or after it (the state's initial_source_date in the entry's format or, with no state stored there, under category_feeds_parent in a category format, the overall doubles state's), or a played state in that format whose last_played is on or after it and that records every teammate in partners and every player of the other team in opponents, each dated on or after it; and at least one named player has no baseline on or after it, since a match that froze every player is not counted or logged. So a snapshot that changes only verified_matches_played from what the engine wrote does not load, with the two limits above: a snapshot that is not resumable, and an overall doubles state under the gap rule, where relabeling a self-reported update that reached doubles from a category match still loads. For example, a log entry moved to a player with no baseline on or after its latest date and no state in its format played on or after that date does not load, and neither does a resumable snapshot where a played state's initial_source_date is on or after its last_played or any of its partners or opponents dates.

These rules check only the latest dates the state keeps: last_played and the latest date with each partner and opponent. A snapshot edited in several fields can still load, for example: one that is not resumable where a played state gets an initial_source_date before every logged date that moved it and verified_matches_played raised to match (with an external initial_source, or an "open_parent:" one dated with its parent; a dated "open_provisional" state does not load, issue #97), since such a snapshot does not record when each seed was set relative to the logged matches; the dated-state edits the resumable rules below reject, in a snapshot that is not resumable, since those rules apply only to resumable snapshots; in a resumable snapshot, a state dated on or after an earlier match that moved it, with verified_matches_played raised to match, when its last_played and every partner and opponent date are still after the new date (for example, because it met the same partners and opponents again later), since those maps keep only the latest date; a log name swapped to a player who later played in that format with the same teammates and opponents, on or after the entry's latest date, with the verified counts adjusted to match, since the links keep only the latest date; a whole log entry deleted with the named players' verified counts raised, since the snapshot does not tie a match id to its match type; and edits that also rewrite the partner and opponent names or dates to match.

Identities follow the seed and link rules: account_user_id is null or a non-blank str, every external_ids source and id is a non-blank str, and no two players hold the same account or the same (source, external id) pair. No external_ids source starts with "open_". Every state's initial_source is a non-blank str, and one that starts with "open_" follows the reserved-name rules in [Seed rules](#seed-rules), checked under cfg (an "open_parent:" state may also be played, and is then undated only with a played parent state, with no RD rule). Every state's initial_evidence_reference is null or a non-blank str, and its initial_external_player_id is null or a non-blank str that the same player's external_ids links under initial_source.

A resumable snapshot also holds no date after calculated_as_of, no played state with an initial_source_date whose last_played, or any partner or opponent date, is on or before that date (a replay adds every seed before any row, and a row on or before a state's date freezes it), no nonzero live_updates_since_replay or inherited_live_updates, no processed match id without a ledger digest, and no player with a played state missing from ledger_player_ids, and its replay_info counts equal the number of ledger digests and processed match ids.

Raises SnapshotError naming the first bad value. The engine shares no state with the snapshot.

### Snapshot schema

Schema, version 9. Dates are `YYYY-MM-DD` text. Every object has exactly these keys, and `from_snapshot` rejects a missing key, an unknown key, a value of the wrong type or out of range, or a state the engine cannot produce: [`RatingEngine.from_snapshot`](#ratingenginefrom_snapshot) lists every check, and [Snapshots and checkpoints](#snapshots-and-checkpoints) says what they do not cover.

- `snapshot_version`: `9`. A version 1, 2, 3, 4, 5, 6, 7, or 8 snapshot does not load. Run a full replay to make a new one. Version 9 adds `params_version` and `parameter_fingerprint` to `replay_info`. Version 8 added `seed_sensitive_rejections`. Version 7 added no key: `reserved_match_ids` now holds the id of every match `record` rejected, not only those not completed. Version 6 added `verified_matches_played` to each state and `net_rating_created` to `replay_info`. Version 5 added `reserved_match_ids`. Version 4 added `inherited_live_updates` to each state. Version 3 added no key: it marked that each row digest in `ledger_digests` covers `Match.status`.
- `engine_version`: the package version that wrote it. Informational, not checked.
- `config_version`, `config_fingerprint`: of the `Config` it was taken under. `from_snapshot` checks both against the copy it rebuilds from the `Config` it is given (issue #122).
- `calculated_as_of`: the date of the last replay, or `null`.
- `replay_info`: `null` when `calculated_as_of` is, otherwise `as_of`, `config_version`, `config_fingerprint`, `params_version` (a str or `null`), `parameter_fingerprint`, `matches_considered`, `matches_counted`, and `net_rating_created` (rating format value to a finite float, one key for every format, sorted). Store the snapshot so these values stay JSON floats: a store that rewrites `0.0` as `0` makes the snapshot fail to load ([`RatingEngine.from_snapshot`](#ratingenginefrom_snapshot) lists the checks).
- `players`: sorted by `id`. Each has `id`, `account_user_id` (text or `null`), `external_ids` (source to id), and `ratings` (rating format value to state). A state has every `RatingState` field: `rating`, `rd`, `matches_played`, `last_played`, `rd_as_of`, `initial_rating`, `initial_source`, `initial_source_date`, `initial_source_reliability`, `initial_external_player_id`, `initial_evidence_reference`, `live_updates_since_replay`, `partners`, `opponents` (these two map a player id to a date), `inherited_live_updates`, and `verified_matches_played`. `inherited_live_updates` is the parent's live count when a category state was derived from overall doubles ([`RatingEngine.from_snapshot`](#ratingenginefrom_snapshot) lists the checks on each state).
- `processed_match_ids`: sorted.
- `reserved_match_ids`: sorted. The `match_id` of each match `record` considered and did not count, for any reason other than `DUPLICATE_MATCH_ID`. A later `record` call for a match with one of these ids gets `DUPLICATE_MATCH_ID`, unless it raises first (for example for an `as_of` earlier than the match date). No id repeats or is also in `processed_match_ids`. Under `reject_content_duplicates=True` every `possible_duplicates` key is a reserved id, since a rejected copy reserves its `match_id`. In a resumable snapshot every id is also a `ledger_digests` id, since a replay reserves only a row it considered. In any snapshot, live or resumable, every `ledger_digests` id is processed or reserved, since a replay counts or reserves every row it considers and no id is ever freed.
- `self_reported_log`: sorted by format, then teams. Each entry has `rating_format`, `teams` (two sorted lists of player ids), and `dates` in the order they were recorded.
- `content_keys`: sorted by key. Each key is the SHA-256 digest of a counted match's content (its date, its two teams, and its game scores), and each value is the `match_id` of the first match counted with that content (see `MatchResult.possible_duplicate_of` in [Match results](#match-results)). Later matches with the same content are checked against it.
- `possible_duplicates`: sorted by key. The `match_id` of each match flagged or rejected as a possible duplicate, to the `match_id` it repeats (its `possible_duplicate_of`). An entry never clears. [`RatingEngine.from_snapshot`](#ratingenginefrom_snapshot) lists the checks on its keys and values.
- `ledger_digests`: `match_id` to the SHA-256 digest of every row a replay considered, kept across resumes. Resume uses them to check rows dated on or before the checkpoint.
- `ledger_player_ids`: sorted ids of every player named in those rows, counted or not. Resume refuses a seed for one of them.
- `seed_sensitive_rejections`: sorted by `match_id`. Each update `record` rejected for `BEFORE_IMPORTED_BASELINE`, `SINGLES_RATING_GAP`, or `DOUBLES_PARTNER_GAP`, live or in a replay, as `players` (the sorted ids of the match's players) and `rating_format` (the format of the rejected update: the match's own, whose `match_id` is reserved, or `doubles` for the doubles update of a counted category match, whose `match_id` is processed). `seed_external_rating` and `add_player` refuse a seed for a named player in that format or, under `category_feeds_parent`, its parent. An entry never clears.
- `resumable`: `true` only while the engine is exactly what a replay produced. Resume refuses a snapshot where it is `false`.

## Prequential predictions

These notes cover `prequential_predictions`, and so `evaluate`.

A match is eligible when every participant is established in its rating format (imported baseline, or at least `burn_in_matches` OPEN matches), its scoring equals `scoring` when given, it is played on or after `score_from` when given, and its status is MatchStatus.COMPLETED (a forfeit, retired, or incomplete row is recorded, which changes no rating, but never predicted). Only matches that `record` counts are kept. This "established" is not `PlayerSummary.established`.

"live" records every match live in one engine, in ledger order. "scheduled" mirrors production: replay dates are `anchor + k * cfg.replay_interval_days` (anchor defaults to the first completed match date). A match on day d is predicted from replay(matches on or before s, as_of=s) for the largest replay date s strictly before d, and matches in that window are then predicted and recorded live in ledger order.

Every seed is validated up front, in both modes, by the seed rules (see [Seed rules](#seed-rules)), and a seed whose initial_source_date is after the last completed ledger match raises InvalidSeedError. A ledger with no completed match has no seed date check and gives no predictions. A repeated seed id, or two seeds that share an account_user_id or a (source, external id) pair, raise PlayerError, as add_player does. A seed captured mid-ledger is accepted: scheduled replays before its date freeze it as usual.

A score_from or anchor that is not None and not a plain date (a str, a datetime, a date subclass, or any other type) raises EvaluationError naming the argument, before the ledger is read, in both modes and for an empty ledger too. Then, also before the ledger is read, mode must be exactly the str "live" or "scheduled", scoring None or exactly a ScoringType, and burn_in_matches exactly an int (a bool or a subclass is rejected), or it raises EvaluationError; and cfg must be None or exactly a Config with only its fields, or it raises ConfigError. It reads matches and seed_players once each, into lists, before any row or seed is checked. Only then is cfg rebuilt from its field values (see [Config validation](#config-validation)), so a rewritten value it rejects raises ConfigError too, even one rewritten while those iterables were read.

## Calibration fits

Calibrate the expectation scale on match history with `fit_scale(...)`. The expectation scale and the K factor together set how sharp predictions are, and in a closed pool they also set the rating spread. Run `fit_scale` with `mode="scheduled"` and a `score_from` date that skips immature ratings, then check `at_bound` and `profile` on the result: a fit that sits on a search edge or has a flat error profile is not identified. `RatingEngine.predict_win_probability` assumes points are independent, which tends to make match win probabilities overconfident. Calibrate them with `fit_win_calibration` and store the result in `Config.win_calibration_by_scoring`.

### `fit_scale`

The search compares unrounded MSE, so ties at the 6-decimal precision of EvaluationReport.mse do not decide the fit.

Coarse grid first, then golden-section search around the best grid point. Publish the returned ScaleFit alongside the config that adopts it. Raises EvaluationError, before any prediction work, unless low < high, tolerance is finite and greater than 0, and 2 * low, 2 * high, and (high - low) * 14 are finite; low, high, and tolerance must each be exactly an int or a float (a bool or a subclass is rejected), checked first. Then the other arguments (not matches and seed_players) are checked as prequential_predictions checks them, in the same order, for an empty ledger too, and scoring must be exactly a ScoringType (None is rejected), all before any trial config is built. A scoring that is not None and not a ScoringType member is rejected with the other arguments, before the check that cfg is None or exactly a Config with only its fields. A scoring of None is rejected after that cfg check and before cfg is rebuilt from its field values, so it raises EvaluationError ahead of a ConfigError for a rewritten cfg value. A trial config is built from the fields of Config itself, with the trial scale for scoring, and Config's own check that scales are positive raises ConfigError for a low of 0 or less. The first trial config, at scale low, is built after cfg is rebuilt and before any row or seed is checked, so that ConfigError comes ahead of a bad row or seed. A trial never goes through dataclasses.replace.

### `fit_win_calibration`

Uses the raw win probabilities computed with cfg's scale, so fit the scale first. Predictions without a modeled win probability (win_by not 1 or 2) are skipped. Same search as fit_scale: coarse grid, then golden section. Raises EvaluationError when no prediction remains, and, before any prediction work, for the same low, high, and tolerance as fit_scale. Then it checks the other arguments (not matches and seed_players) as fit_scale does, in the same order, for an empty ledger too: a scoring that is not None and not a ScoringType member is rejected before cfg's type check, and a scoring of None after it and before cfg is rebuilt. It builds no trial config, so a low of 0 or less raises no ConfigError, and the rows and seeds are checked as prequential_predictions checks them.

## Backend requirements

- Persist the match ledger and player identities in a database. This module's in-memory dictionaries are an engine, not a persistence layer.
- Do not show `possible_duplicate_of` (or possible_duplicates) to whoever submitted the match. It reveals another report's match_id and that those players played that result on that date.
- Verify a match's status as you verify its scores. A status other than completed keeps a match from moving any rating, so a team could report a loss as a forfeit, retirement, or unfinished match to avoid it. The engine cannot tell; the backend must. The engine does not record which team forfeited or retired, so the backend stores that.
- Set match_type from organizer, league, or club provenance, and never let whoever submits a match choose a verified type (tournament, league, or rec_verified). match_type sets a match's weight and decides whether it counts toward PlayerSummary.established, so a self-reported match relabeled as verified would let players report their way to established. The engine cannot tell; the backend must.
- Assign match_ids in the backend. A party that can choose a match_id can submit a match that gets rejected under it first (for example one that is not completed or not confirmed), and then the real match with that id never counts live (replay raises LedgerConflictError for the pair). DUPLICATE_MATCH_ID does not say whether the id was counted or reserved.
- Give a corrected resubmission a new match_id, keep the rejected row in the ledger, and resubmit only after the rejections [Match ids, rejections, and resubmission](#match-ids-rejections-and-resubmission) allows.
- Require verified identity and authorized evidence before importing an external rating. An external refresh can never overwrite an OPEN-earned rating once OPEN matches have been processed.
- Show `params_version` with every published rating, and keep its `parameter_fingerprint` with it, as `PlayerSummary` gives them. Load a published parameter set with `Config.published` (which goes through `Config.from_parameter_set`) rather than setting `params_version` by hand: it checks the label and the values against the sets this release publishes, while a label set by hand proves nothing. A new set needs an engine release that adds it. When a new set goes live, rebuild authoritative ratings with a full replay of the whole ledger, and publish the shift by percentile first (see [Maintenance and parameter versioning](parameters.md#existing-ratings-when-a-set-changes)).
- Store each replay's `ReplayInfo` (as_of date, config version, config fingerprint, params_version, parameter fingerprint, counts, net_rating_created) for auditability. Identify a published rating by the engine version, `params_version`, and the parameter fingerprint; the config fingerprint gives exact provenance. Take the engine version from the installed package (`open_engine.__version__` of the pinned release), not from `config_version`: that is `Config.version`, which a caller can set to any str without changing the parameter fingerprint. A `params_version` is self-asserted, since any config can carry any label. The label alone proves nothing: trust it only when the parameter fingerprint equals the one published for that set. Watch net_rating_created for a pool that grows or shrinks: colluding accounts with different K can create rating, and the engine does not cap it.
- Reject a match whose `played_on` is after the date it was submitted. The engine never reads the clock, so it cannot tell. A future-dated live match, by typo or on purpose, holds last_played, rd_as_of, and partner and opponent dates at that future date for every player in it until the next replay: RD stops growing, reliability is held up, and player_summary's default reference date jumps ahead. A later honest match with those players that counts in the same rating format comes back with `late` set to True. For a category match, `parent.late` covers the overall doubles rating.
- To avoid replaying the whole ledger every time, persist the snapshot of each scheduled replay and resume the next one from it, as [Replay and resume](#replay-and-resume) and [Snapshots and checkpoints](#snapshots-and-checkpoints) describe: take the snapshot right after the replay, store a match before the replay that covers its date, pass the whole ledger with `whole_ledger=True`, and run a full replay for a void, an edit, a backdated row, or a seed withdrawn or corrected after the checkpoint (the checkpoint already holds the old seed). A snapshot does not replace the ledger: keep the ledger as the source of truth and run a full replay when in doubt.
- Protect stored snapshots from writes as you protect the ratings themselves (see [Snapshots and checkpoints](#snapshots-and-checkpoints)).
