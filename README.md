# OPEN rating engine

[![OpenSSF Scorecard](https://api.scorecard.dev/projects/github.com/openpickleball/engine/badge)](https://scorecard.dev/viewer/?uri=github.com/openpickleball/engine)

The reference rating engine for [OPEN](https://github.com/openpickleball), the Open Pickleball Evaluation Network.

> **Project status:** This engine is a demonstration. Its methods have not been validated on real match data, its outputs are not OPEN ratings, and its API may change without notice. Do not use it to rate real players. OPEN is in early development, and no OPEN rating is live.

## Technology

The engine is a Python package (`openpickleball-engine`, imported as `open_engine`) with no runtime dependencies. It requires Python 3.11 or later.

A standard external rating system is the intended source of imported ratings, which seed a player's starting rating. An imported reliability is shown separately from OPEN-earned reliability. The engine uses none of that system's code or internals, and it is not a reproduction of any proprietary rating algorithm.

## Quick start

```python
from datetime import date
from open_engine import Match, MatchType, RatingEngine, RatingFormat

engine = RatingEngine()
result = engine.record(
    Match(
        match_id="league-2026-10-29-court-3-match-7",
        team_a=("alice", "carol"),
        team_b=("bob", "dave"),
        games=((11, 8), (9, 11), (11, 7)),
        played_on=date(2026, 10, 29),
        rating_format=RatingFormat.DOUBLES,
        match_type=MatchType.LEAGUE,
        best_of=3,
    )
)
print(result.counted, result.reason, result.deltas)

summary = engine.player_summary("alice", RatingFormat.DOUBLES, as_of=date(2026, 10, 29))
print(summary.rating, summary.reliability, summary.imported_reliability)
```

`result.reason` is `None` when the match counted and a `RejectionReason` when it did not. Live recording applies matches in arrival order. A match dated before a player's last match in that rating format, or before the date that player's rating in that format already reflects (for a category rating copied from overall doubles), still counts, but no stored date moves back, and it is late. Check `result.late` and, for a category match, `result.parent.late`. Schedule a replay when either is `True`: only a replay gives play order. Dates are compared, not times, so a same-day match is never late. Reject a match whose `played_on` is after the date it was submitted. The engine never reads the clock, so a future-dated match would hold its players' dates at that future date until the next replay: their RD would stop growing and their reliability would stay high. `player_summary` returns a `PlayerSummary`. Its `reliability` is always OPEN-earned. `imported_reliability` is an imported external reliability while it is carried, shown separately, and `None` otherwise. `live_updates_since_recalculation` labels the provisional movement in the rating: the state's own live updates since the last replay, plus, for a category state derived from overall doubles, the parent's live updates already in the rating it copied (`RatingState.inherited_live_updates`). It is 0 right after a replay. `player_summary` measures inactivity and reliability at `as_of`. With no `as_of`, it uses the later of the last replay date and the player's last match, so a stale player is measured at the replay date and a player with live matches since at their last match. On a live engine that was never replayed, pass `as_of` or it raises `ReferenceDateError`. It also raises `ReferenceDateError` for an `as_of` that is not a plain date. After those checks, it raises `PlayerError` for a blank player id or one that is not exactly a `str`, and `UnknownPlayerError` for a player id with no player record. For a known player with no rating in the format, it reports the starting state that format's first match would use if played now (a category rating derived from overall doubles where that applies), without storing it. An `as_of` earlier than the player's last match does not rebuild past state: RD and partner variety stay as of the stored state. The engine never reads the wall clock. `established` is `True` when `reliability` (as displayed, rounded to 1 place) is at least `Config.established_reliability_threshold`, 60 by default, and the rating has at least `Config.established_min_verified_matches` counted tournament, league, or recreational verified matches, 3 by default (`RatingState.verified_matches_played`). Self-reported matches never count toward that minimum, and neither does a match in which the player was frozen, so a player with fewer counted verified matches in the format than the minimum is not established at any reliability. A category rating derived from overall doubles starts its count at 0. A minimum of 0 leaves the reliability rule alone. Imported reliability never counts toward `established`, and `established` lapses with inactivity like `reliability`, unless the connectivity cap is set and connectivity changes (see below). Under the defaults, a new player with no imported rating, playing one match a week with varied partners and opponents, becomes established after about 10 to 13 tournament, league, or recreational verified matches (10 tournament, 11 league, or 13 recreational verified matches of one game, fewer for best of 3), and after about twice as many against the same players. Self-reported matches raise reliability past the threshold after about 20 to 25 with varied players (never against the same players, because repeat matches are discounted and then rejected), but such a player is established only once they also have the minimum of counted verified matches. A player seeded from a recently captured imported rating starts at a lower RD (`Config.external_seed_rd`) and is established after about 3 to 4 tournament, league, or recreational verified matches. RD grows from the capture date, so an older import gives less of a head start, and a very old one none. The imported rating and its reliability value do not change the count. A rating that is not established is what external rating systems usually call provisional, which is different from OPEN's provisional live updates between replays and the `open_provisional` source. The threshold and the minimum are labels only: they change no rating and no `evaluate` output. Evaluation's eligibility rule (every participant has an imported baseline or at least `burn_in_matches` OPEN matches) is a separate rule from `established`. With `Config.connectivity_reliability_cap` set, the match counts above are for a player whose network connectivity is connected.

A `match_id` names one match. Once `record` has considered a `match_id`, counted or not, every later `record` call for a match with that id that does not raise returns `RejectionReason.DUPLICATE_MATCH_ID`, whatever the new match holds. This matches `replay`, where a second, different ledger row with the same `match_id` raises `LedgerConflictError`. So a corrected resubmission needs a new `match_id`, and the rejected row stays in the ledger as it was. Resubmit only after a rejection that comes from the match itself: `GAME_FORMAT_NOT_ACCEPTED`, `SELF_REPORTED_UNCONFIRMED`, or `MATCH_NOT_COMPLETED`, for example a self-reported match sent again after both teams confirm it, or a match corrected to an accepted game format. Under the same `Config`, a replay never counts a match rejected for one of those, in any order. The other rejections depend on engine state, seeds, or other rows, so a match rejected live can count in a replay, and a copy of it under a new `match_id` could then count too. Do not resubmit those. For `POSSIBLE_DUPLICATE`, the ledger already holds a match with the same content. A replay under a different `Config` (a new `allowed_game_formats` or `self_reported_requires_both_teams`) can count matches rejected for game format or confirmation, so after such a change, review resubmitted matches before the replay. A live rejection other than `DUPLICATE_MATCH_ID` sets the snapshot's `resumable` to `false`.

RD and variety cannot see whether a player's partners and opponents ever play anyone outside their own group, so a closed pool that plays only itself could look reliable on its own private scale. `PlayerSummary.connectivity`, a `NetworkConnectivity`, says whether the player's pool connects to the wider network. It is measured per rating format at the summary's reference date over `Config.diversity_window_days`, from the partners and opponents stored in each rating state. Two players with a state in the format are in contact when either one's state lists the other with a date in the window. A group is a set of players linked by contact. It is a main network when it has at least half as many players as the largest group, so two separate networks of similar size are each a main network. The label depends on group sizes alone. Two players in contact are tied when they share at least `Config.connectivity_min_shared_contacts` contacts (4 by default) and each of them is in contact with those shared players on at least `Config.connectivity_min_contact_days` distinct dates (3 by default). A pool is a set of players linked by ties, and a player with no tie is a pool of one. The pool's fringe is every player outside it in contact with it whose own contacts are all in the pool or in contact with it, such as a drop-in who met only the pool. Its outside players are the other players in contact with it. A player is connected when they have a contact in the window, their group is a main network, and either the pool with its fringe holds more than half the group, or the pool has at least `Config.connectivity_min_outside_players` outside players (8 by default) on at least `connectivity_min_contact_days` distinct contact dates with them. `connectivity` is always reported. When `Config.connectivity_reliability_cap` is set (it is `None`, off, by default), a player who is not connected has `reliability` at most the cap, shown rounded down to 1 place, so with a cap below the established threshold they are not established. The cap is off by default because the rule can be gamed through group sizes (see the limits) and can cap players in a real but smaller network. It waits for out-of-sample review of real ledgers. It is a label: no rating, RD, prediction, or `evaluate` output changes. Limits: a pool in a main network that with its fringe holds more than half its group is that group's own scale, which no ledger can place on another, so a club in a main network that outnumbers the players it met is not capped and can leave them capped. Pools that play each other but not the rest of their group count each other's players as outside players. Accounts the backend has not verified can pose as outside players if they also play players the pool never met, and a cluster of accounts more than twice the size of a real network makes that network no longer a main network, so verify identities. Drop-in accounts, or one match between two closed groups, can make a closed group large enough to be a main network or to hold more than half its group. A player whose only contacts are a closed group can count its members as outside players when they have not tied with that player, for example when the group plays so densely that every contact keeps one last date. A single match between two real networks can make the smaller one no longer a main network. A state keeps only the last date per contact, so repeated contact with one player counts one date. Contacts leave the window as the reference date moves on, so connectivity can change with no new match: a player can become connected (with the cap set, reliability then rises up to the value from RD and variety) when the groups that outnumbered theirs drop out of the window. The measure needs no snapshot field, so a snapshot and a resume carry it. It is built for every summary, with the cap on or off, and rebuilt for a format and reference date after each state change (the engine keeps the 16 most recent), which costs about the sum over players of their contacts times their contacts' contacts.

Check `result.possible_duplicate_of` too. It names an earlier counted match with the same date, the same two teams, and the same game scores, under another `match_id`, so the same match may have been reported twice. By default that match is not rejected for this, so it counts unless another check rejects it. `Config(reject_content_duplicates=True)` rejects it instead, with `RejectionReason.POSSIBLE_DUPLICATE`. A real rematch on the same day with the same scores looks the same, so the default only flags it. After a replay, `engine.possible_duplicates` maps each flagged or rejected match to the match it repeats. An entry never leaves it.

Processing order alone decides which report is the copy: arrival order live, and ledger order in a replay, as described in "Ledger order": within a date, untimed matches come first by `sequence` then `match_id`, then timed matches by the UTC instant of `played_at`, then `sequence` and `match_id`. Match type, rating format, and game format play no part. So with `reject_content_duplicates=True` a weaker or relabeled copy can count while the stronger report is rejected: for example an untimed self-report of a timed tournament match, or a mixed doubles copy of a doubles match. A category copy that counts first can keep the other row from updating its rating format, and live recording and a replay can keep different rows. Under the default, the flagged row can be the stronger one. Use `reject_content_duplicates=True` only when the backend trusts who files reports. Otherwise resolve flags in the backend. Under the default, a category copy of a doubles match can count twice in overall doubles, once directly and once through `result.parent`. `result.parent.possible_duplicate_of` is `None`, so read the top-level field. Do not show `possible_duplicate_of` to whoever submitted the match: it names another report and tells them those players played that result.

Authoritative ratings come from `replay(ledger, as_of=...)`. Calibrate the expectation scale on match history with `fit_scale(...)`. The expectation scale and the K factor together set how sharp predictions are, and in a closed pool they also set the rating spread. Run `fit_scale` with `mode="scheduled"` and a `score_from` date that skips immature ratings, then check `at_bound` and `profile` on the result: a fit that sits on a search edge or has a flat error profile is not identified. `RatingEngine.predict_win_probability` assumes points are independent, which tends to make match win probabilities overconfident. Calibrate them with `fit_win_calibration` and store the result in `Config.win_calibration_by_scoring`.

See [`examples/`](examples) for a fuller example.

These are the public names, all importable from `open_engine`. The API may change in any 0.x release.

Names not listed here are internal, including everything reached only through `open_engine.engine` or `open_engine.winprob`. They can change or disappear in any release.

Rating:

- `RatingEngine`: holds players and matches, records matches, and predicts outcomes. Its `predict_point_share` and `predict_win_probability` methods give team A's expected point share and calibrated match win probability. `to_snapshot` saves its whole state as JSON-safe data, and `from_snapshot` loads it back (see "Snapshots and checkpoints"). Its `possible_duplicates` attribute maps the `match_id` of each match flagged or rejected as a possible duplicate to the `match_id` it repeats, live and after a replay. An entry never clears: a counted copy's `match_id` is processed, and a rejected copy's `match_id` is reserved, so neither can count again.
- `replay`: rebuilds authoritative ratings from seeds and the match ledger as of a date. With `from_snapshot`, it resumes from a checkpoint instead of starting over. Add `whole_ledger=True` when passing the whole ledger, so resume also catches a row voided on or before the checkpoint date.
- `ledger_order`: the sort key that sets the order of play in a ledger.
- `reliability`: OPEN-earned reliability (0 to 100) for one rating state, from RD and partner and opponent variety. `PlayerSummary.reliability` also applies the network connectivity cap when `Config.connectivity_reliability_cap` is set.
- `expected_point_share`: team A's expected share of points from two team ratings and a scale.

Inputs:

- `Config`: every rating parameter, with a fingerprint for provenance. Its mapping fields are read-only copies, and a config is hashable. Equal configs have the same fingerprint and hash. `Config.to_dict()` and `Config.from_dict()` store and load one with the same fingerprint.

- `MatchStatus`: how a match ended: completed, forfeit, retired, or incomplete (see "Match status").
- `GameFormat`: how each game is scored (scoring type, points to, win by, cap).
- `RatingFormat`: the rating pool (singles, doubles, and the doubles categories).
- `MatchType`: how a match was organized and verified, which sets its weight.
- `ScoringType`: side-out or rally scoring.
- `Player`: a player record with ratings by format and linked identities.
- `RatingState`: one player's rating in one format, with uncertainty and provenance.
- `ExternalRatingSnapshot`: a verified external rating, used only as a seed.

Results:

- `MatchResult`: what `record` did with a match, including the rating changes.
- `RejectionReason`: why a match was not counted. `MATCH_NOT_COMPLETED` covers every status other than completed.
- `PlayerSummary`: a player's rating, reliability, established flag, network connectivity, and provenance in one format.
- `NetworkConnectivity`: whether a player's pool connects to the main network in one format, with the pool size, fringe, outside players and dates, and the size of the player's group behind it.
- `ReplayInfo`: the date, config version, config fingerprint, and match counts of a replay, and `net_rating_created`, the net rating its counted updates added to each rating format's pool.

Evaluation and calibration:

- `prequential_predictions`: predicts each match from ratings that have not seen it.
- `PrequentialPrediction`: one such prediction.
- `evaluate`: scores prequential predictions of point share.
- `EvaluationReport`: error and calibration bins from `evaluate`.
- `fit_scale`: fits the expectation scale for one scoring type.
- `ScaleFit`: the result of `fit_scale`.
- `fit_win_calibration`: fits the win probability calibration for one scoring type.
- `WinCalibrationFit`: the result of `fit_win_calibration`.

- `match_win_probability`: probability of winning a best-of-N match from a point win probability.
- `calibrate_win_probability`: applies a fitted calibration to a win probability.

- `OpenEngineError`: base class for every error the engine raises on purpose.

It also raises it for `whole_ledger=True` without `from_snapshot`.

## Config values

`Config` checks every field when it is built and raises `ConfigError` for any value it rejects. A number here is an `int` or a `float`, never a `bool`, that is finite as a float: not NaN or infinite, and not an int too large to convert. A whole number is an `int` that is also a number. An `int` or `float` subclass is accepted in any number field, mapping value, `game_length_weights` key, or `allowed_game_formats` points value, and `Config` stores the plain `int` or `float` of its own value (`int.__int__` or `float.__float__`) before any check, so the checks, the fingerprint, and rating code all read that plain value. The fingerprint covers the fields of `Config` itself, so a subclass's extra fields do not change it. So a built config always gives plain JSON, and its fingerprint, `==`, and `hash` never raise.

- `version` is exactly a `str` (not a subclass). `self_reported_requires_both_teams`, `reject_content_duplicates`, and `category_feeds_parent` are bools.
- The day counts, `diversity_target`, `self_reported_max_repeats`, `import_reliability_carry_matches`, `established_min_verified_matches`, and the three connectivity counts are whole numbers. A float such as `7.0` is rejected. Every other scalar field is a number, except `connectivity_reliability_cap`, `max_singles_rating_gap`, and `max_doubles_partner_gap`, which are `None` or a number.
- `min_rating`, `max_rating`, and `default_rating` are each at most `2**511` in magnitude (about 1.3e154), `min_rating` is less than `max_rating`, and `default_rating` lies between them. Within that range, team sums, rating gaps, and `imbalance` stay finite.
- `scale_by_scoring`, `win_calibration_by_scoring`, and `match_weights` have exactly one key for every scoring type or match type. A key given as the enum's str value, such as `"rally"`, is stored as the enum member, and `allowed_game_formats` pairs are stored as a `ScoringType` and a plain `int` of the value's own int value. So a key or points value always gives the same fingerprint as the plain enum member or int. Their values, and the values of `game_length_weights`, are numbers greater than 0. `game_length_weights` keys are whole numbers of at least 1, with one for the points of every allowed game format, and no two keys name the same length.
- `0 <= k_min <= k_max`, and the largest K, `k_min + (k_max - k_min) * 1.0` as the engine computes it (it can round just above `k_max`), times the largest match weight times `max_information_multiplier` is finite in floats. A self-reported match's step weight is an exact int product when the `SELF_REPORTED` match weight, `max_information_multiplier`, and `self_reported_repeat_factor` are all ints and that match's information multiplier is `max_information_multiplier` itself. So when those three are ints, the check tests whether a match could get there, allowing up to `sys.maxsize` games. It counts the multiplier as reachable when, for some `(scoring, points)` in `allowed_game_formats`, `game_length_weights[points] * (1.0 + game_count_bonus * (sys.maxsize - 1))` is not below `max_information_multiplier` (`sys.maxsize` is the most games `len()` can report). No real match has that many games, so the check can reject a config whose multiplier no real match reaches. When it is reachable, the weight times the multiplier must convert to a float, and the largest K times it must be finite. With an int `rd_shrink_per_match`, `rd_shrink_per_match` times that product must convert to a float too.
- `0 < rd_min < rd_max <= 2**511`, and `rd_max - rd_min` is greater than 0 as computed, so an int and a float that are equal once converted are rejected. `new_player_rd`, `external_seed_rd`, and `category_seed_rd` lie from `rd_min` to `rd_max`. `rd_shrink_per_match` is at least 0, and `rd_growth_per_day` is from 0 to `2**511`.
- Some bounds apply to ints only, because exact int arithmetic raises `OverflowError` where float arithmetic goes to infinity: an int `rd_growth_per_day` is at most `2**500`, an int `game_count_bonus` is at most `2**511`, and the exact self-reported step weight rule above applies. A float `game_count_bonus` has no upper bound beyond being finite.
- `win_weight` is from 0 to 1, `game_count_bonus` is at least 0, `max_information_multiplier` is at least 1, and `self_reported_repeat_factor` is greater than 0 and at most 1. `established_reliability_threshold` and `connectivity_reliability_cap` are from 0 to 100.
- `replay_interval_days`, `diversity_window_days`, and `self_reported_repeat_window_days` are from 1 to 3,652,058, the number of days from `date.min` to `date.max`, which `timedelta` holds. `import_reliability_max_age_days` is from 0 to that. A window that reaches back before `date.min` from a match or reference date stops at `date.min` instead of raising `OverflowError`. `diversity_target`, `self_reported_max_repeats`, and the three connectivity counts are at least 1. `import_reliability_carry_matches` and `established_min_verified_matches` are at least 0.
- `max_singles_rating_gap` and `max_doubles_partner_gap` are `None` or at least 0.

## Ledger order

`replay` and `prequential_predictions` sort the ledger the same way whatever order the rows arrive in.

- Matches sort by `played_on` first, the calendar date at the venue. The rules below apply within one `played_on` date.
- On one day, matches without a `played_at` come first, by `sequence` and then `match_id`.
- Matches with a `played_at` follow, by the moment they were played in UTC, then `sequence`, then `match_id`. A match at 21:00 at UTC-5 comes after one at 22:00 UTC on the same day.
- `played_at` must include a time zone and fall on `played_on` in that zone.
- Every row passed in is validated, including rows after `as_of`. An invalid row raises `InvalidMatchError`, for example one with a `played_at` without a time zone or a blank player id. A row with an invalid game format raises `InvalidMatchError` too. It is a `ValueError`.
- Rows that repeat a `match_id` count once when they are the same match: every field matches in type and value (so `3` and `3.0` differ), with `played_at` at the same moment and the same UTC offset. Any other repeat raises `LedgerConflictError`, a `ValueError` whose `match_ids` lists every conflicting id. This covers rows after `as_of` too.

## Match performance

A match moves ratings by how the result compared with the expectation.

- Performance is team A's share of all points across the match's games, blended with the match result by `Config.win_weight`. The default, 0.0, uses point share only.
- So a team can win and still lose rating. That happens when it wins by less than expected, such as a 5.0 team beating a 4.0 team 11-9 in doubles. It can also happen when a team wins a best of 3 (or 5) with fewer total points.
- There is no floor on a winner's change, other than the rating range (`min_rating` to `max_rating`).
- For one engine state, raising a team's point share by changing only the match's game scores, with the same number of games and the same result, never gives that team a worse change. Longer games and more games can carry more weight (up to `Config.max_information_multiplier`), so across game formats and game counts a slightly wider winning margin can still cost more rating.
- `win_weight = 1.0` scores the result only, so a winner never loses rating. Values between 0 and 1 make a rating loss less likely. Only values close to 1 rule it out, and how close depends on the rating range and scale and on the lowest point share a winner can have.
- The default is a declared choice, not a validated one. It changes only when out-of-sample evaluation shows another value predicts better.

## Match status

`Match.status` says how a match ended. It is a `MatchStatus` and defaults to `COMPLETED`. A status that is not a `MatchStatus` member, such as the plain text `"forfeit"` or `None`, raises `InvalidMatchError`.

- `COMPLETED`: at least one game and a decided winner. Nothing changes for these matches.
- `FORFEIT`: the match was not played, so it must have no games.
- `RETIRED`: a player stopped, for example through injury, before a winner was decided.
- `INCOMPLETE`: the match stopped for another reason, such as time or weather.

A retired or incomplete match records zero or more finished games, each valid in its game format, and no decided winner. So in a best of 1 it has no games. A partial game in progress, such as `(7, 4)` to 11, is not recorded. `games` must be exactly a tuple or list for every status.

`Match.validate` also checks the type of other `Match` fields, and raises `InvalidMatchError` naming the field. The match itself must be exactly a `Match`, not a subclass. `match_id`, every team player id, and every member of `confirmed_by` must be exactly a non-blank `str` (a subclass raises, with the message for a blank id). `rating_format` must be a `RatingFormat` and `match_type` a `MatchType`, so a str such as `"tournament"` raises even though it equals a member's value. `team_a` and `team_b` must be exactly tuples, `confirmed_by` exactly a set or frozenset, `games` and each game in it exactly a tuple or list, each score exactly an int, `sequence` and `best_of` ints (not a `bool` or a float), `game_format` a `GameFormat`, and `played_at` a `datetime` or `None`. Inside the `GameFormat`, `scoring` must be a `ScoringType` (a str such as `"rally"` raises), `points_to` and `win_by` ints, and `cap` an int or `None`; a `bool` or a float is not accepted as an int, and an int subclass is. These are the rules of `GameFormat.validate`, which raises `ConfigError` for the same values when it is called directly.

A match that is not completed is never rated:

- `record` validates the match, then checks the `match_id` before the status: a `match_id` already processed or reserved gets `RejectionReason.DUPLICATE_MATCH_ID`. Otherwise it returns a result that is not counted, with `RejectionReason.MATCH_NOT_COMPLETED`. It moves no rating and does not mark the `match_id` processed, but it reserves the `match_id`, as for every rejected match (see "Quick start"). To relabel a forfeit as completed live, use a new `match_id`.
- `replay` accepts the row. It counts toward `matches_considered`, not `matches_counted`. A full replay gives each player the same ratings as a full replay of the ledger without those rows. In one ledger, a non-completed row and a completed row with the same `match_id` conflict (`LedgerConflictError`), so replace the row instead.
- As for any rejected row, a checkpoint tracks the row and its players. Resume raises `SnapshotError` for a new seed for a player named only in such a row.
- Replacing the row with a completed one under the same `match_id` is an edited row. For a row dated on or before a checkpoint, that needs a full replay (resume raises `LedgerConflictError` when given it).
- `prequential_predictions`, `evaluate`, `fit_scale`, and `fit_win_calibration` never predict it. The seed date limit and the default scheduled anchor come from completed rows only.

Rating a retirement on its finished games would change how ratings move. It is not done here. It would need a declared `Config` parameter backed by out-of-sample evaluation.

A status keeps a match from moving any rating, so a team could report a loss as a forfeit or an unfinished match. The engine cannot tell. The backend should verify a status as it verifies scores, and store which team forfeited or retired, which the engine does not record. Likewise, set `match_type` from organizer, league, or club provenance, and never let whoever submits a match choose a verified type (tournament, league, or rec_verified): the type sets the match's weight and decides whether it counts toward `established`.

The backend should also assign `match_id`s itself. A party that can choose a `match_id` can submit a match that gets rejected under it first, for example one that is not completed or not confirmed. Then the real match with that id never counts live, and `replay` raises `LedgerConflictError` for the pair. `DUPLICATE_MATCH_ID` does not say whether the id was counted or reserved.

## Snapshots and checkpoints

`RatingEngine.to_snapshot()` returns the engine's whole state as plain JSON data. `json.dumps(snapshot, allow_nan=False)` works with no custom encoder. `RatingEngine.from_snapshot(snapshot, cfg)` builds the engine back, from the dict or from `json.loads` of its text. Every value comes back with its type: an int stays an int. The same state always gives the same JSON text.

A snapshot of a replay is a checkpoint. `replay(matches, seeds, cfg=cfg, as_of=later, from_snapshot=snapshot)` resumes from it and gives the same result as a full replay to `later`. You can pass the whole ledger or only the rows dated after the checkpoint. Pass only seeds that are not in the checkpoint.

Take the checkpoint snapshot right after the replay, before any other call on the engine. Every engine method that changes state makes the snapshot one resume refuses: a live match, a seed, an account or external id link, a new player, or a new rating state. Reads (`player`, `state`, `player_summary`, the predictions, and `to_snapshot`) change nothing, so they keep the snapshot resumable. Changing objects the engine returns or its public attributes (for example `players`, rating states, or `processed_match_ids`) directly is not tracked, and makes the snapshot unsafe to resume.

When you pass the whole ledger, also pass `whole_ledger=True`. Resume then raises `SnapshotError` for any row the checkpoint saw that is missing from the ledger, which catches a match voided or deleted on or before the checkpoint date. `whole_ledger=True` without `from_snapshot` raises `SnapshotError`.

Resume raises instead of giving a different result:

- `SnapshotError` for a malformed snapshot, a snapshot taken under another `Config`, a snapshot that is not from a replay, a snapshot with live updates or any other change since its replay, an `as_of` before the checkpoint date, a row dated on or before the checkpoint date that the checkpoint did not see, or a seed for a player named in a row the checkpoint saw (even when every such row was rejected, so the player is not in the snapshot).
- `LedgerConflictError` for a row dated on or before the checkpoint date that differs from the row the checkpoint saw under that `match_id`, or a later row that reuses one of those ids.
- `PlayerError` for a seed whose player is already in the snapshot.
- `SnapshotError`, with `whole_ledger=True`, for a row the checkpoint saw that is missing from the ledger. It names every missing id, sorted.

The row checks run in this order: changed or reused rows (`LedgerConflictError`), then rows the checkpoint did not see, then (with `whole_ledger=True`) checkpointed rows that are missing.

Resume gives the same result as a full replay of the ledger and seeds its rows come from. It detects every row it is given that disagrees with the checkpoint. With `whole_ledger=True` it also detects checkpointed rows removed from the ledger. It cannot detect a seed that was withdrawn or corrected after the checkpoint, with or without `whole_ledger`. It cannot detect a late (backdated) row on or before the checkpoint date that you leave out. Without `whole_ledger=True`, it also cannot detect a row on or before the checkpoint date that was removed (voided) from the ledger, or an edited one that you leave out. A void, an edit, or a late row on or before the checkpoint date, and a seed withdrawn or corrected after the checkpoint, each need a full replay. Resume raises for such an edited or late row when you pass it, and for a void when you pass `whole_ledger=True`, but the fix is still a full replay. Store a match before the replay that covers its date.

A stored snapshot sets every rating when it is loaded. Give it the same write protection as the ratings themselves. `from_snapshot` checks its shape and the engine's rules, not that it is authentic.

Schema, version 8. Dates are `YYYY-MM-DD` text. Every object has exactly these keys, and `from_snapshot` rejects a missing key, an unknown key, or a value of the wrong type or out of range. It also rejects a state the engine cannot produce: an initial rating outside the rating bounds, an unplayed state with a played state's RD or with partners, opponents, or live updates, `matches_played` and `last_played` that disagree, more live updates or verified matches than matches, a player listed as their own partner or opponent, or an imported reliability with no import date. A nonzero `inherited_live_updates` is accepted only on a state derived from its parent, and only when the player has that parent state with at least as many live updates, the state has the parent state's `initial_source_date` and no imported reliability, external player id, or evidence reference, and, while the state is unplayed, its RD is at least `category_seed_rd` and its `rd_as_of` is set and no later than the parent state's. Every partner, opponent, and self-reported team member must be a player in the snapshot. A state's self-reported updates, `matches_played - verified_matches_played`, must agree with `self_reported_log`: at most the logged dates in its format that name the player, plus, for doubles under `category_feeds_parent`, the logged dates in the category formats. For a state with no `initial_source_date`, and for every state of a resumable snapshot counting only logged dates after its `initial_source_date`, an overall doubles state under `category_feeds_parent` with `max_doubles_partner_gap` set must count at least the logged doubles dates, and every other state must count exactly the logged dates in its format, plus, for doubles under `category_feeds_parent`, the logged dates in the category formats. The exact rule for a state with an `initial_source_date` holds only while `resumable` is true, which the snapshot itself sets. So a snapshot that changes only `verified_matches_played` from what the engine wrote does not load, with two limits. A snapshot that is not resumable does not record when each seed was set relative to the logged matches, so for a state with an `initial_source_date` there (an imported state, or a category state derived from one) only the upper bound is checked. And with `max_doubles_partner_gap` set under `category_feeds_parent`, an overall doubles state is checked against a range (at least the logged doubles dates, at most the upper bound), since the gap can reject a category match's doubles update, so relabeling a self-reported update that reached doubles from a category match still loads there. More rules catch edits to a second field. For each `self_reported_log` entry, take its latest date. Every player the entry names must either have a baseline dated on or after that date, which froze them in that match (the state's `initial_source_date` in the entry's format or, with no state stored there, under `category_feeds_parent` in a category format, the overall doubles state's), or have a played state in that format whose `last_played` is on or after that date and that records every teammate in `partners` and every player of the other team in `opponents`, each dated on or after that date, as a move in that match leaves. At least one named player must have no baseline on or after that date, since a match that froze every player is not counted or logged. In a resumable snapshot, a played state with an `initial_source_date` must have a `last_played`, and every `partners` and `opponents` date, after that date, since a replay adds every seed before any row and a row on or before a state's date freezes it. So, for example, a log entry moved to a player with no baseline on or after its latest date and no state in its format played on or after that date does not load, and neither does a resumable snapshot where a played state's `initial_source_date` is on or after its `last_played` or any of its `partners` or `opponents` dates. These rules check only the latest dates the state keeps: `last_played` and the latest date with each partner and opponent. A snapshot edited in several fields can still load. Examples: a snapshot that is not resumable, where a played state gets an `initial_source_date` before every logged date that moved it and a `verified_matches_played` raised to match, with an external `initial_source` or an `open_parent:doubles` one dated with its doubles state (a dated `open_provisional` state does not load, issue #97), since such a snapshot does not record when each seed was set relative to the logged matches; a snapshot that is not resumable with a state dated on or after matches that moved it, since the dated-state rules above apply only to resumable snapshots; a resumable snapshot with a state dated on or after an earlier match that moved it, with `verified_matches_played` raised to match, when its `last_played` and every `partners` and `opponents` date are still after the new date (for example, because it met the same partners and opponents again later), since those maps keep only the latest date; a log name swapped to a player who later played in that format with the same teammates and opponents, on or after the entry's latest date, with the verified counts adjusted to match, since the links keep only the latest date; a whole log entry deleted, with each named player's `verified_matches_played` raised to match, since the snapshot does not tie a match id to its match type; and edits that also rewrite the `partners` and `opponents` names or dates to match. A snapshot is checked for shape and invariants, not authenticity. Identities follow the seed and link rules: every id, source, and external id is exactly a `str` when a snapshot is passed in memory, `account_user_id` is null or a non-blank string, every `external_ids` source and id is a non-blank string, no `external_ids` source starts with `open_`, and no two players hold the same account or the same source and external id pair. Every state's `initial_source` is a non-blank string, and one that starts with `open_` must follow the reserved-name rules listed under `InvalidSeedError` above, checked under the snapshot's config (an `open_parent:` state may also be played; the RD rule applies only while it is unplayed). Every state's `initial_evidence_reference` is null or a non-blank string, and every state's `initial_external_player_id` is null or a non-blank string that the same player's `external_ids` maps `initial_source` to. Each `content_keys` value must be a processed match id, and no two keys may name the same id. No reserved match id may be a processed one, and every `ledger_digests` id must be a processed or reserved match id. Under `reject_content_duplicates=True`, every `possible_duplicates` key must be a reserved match id. Each `seed_sensitive_rejections` key must be a reserved match id that is not a `possible_duplicates` key, or a processed match id whose entry has `rating_format` `doubles` under `category_feeds_parent`, names only players in the snapshot, and names one player with a played category state that has one other named player as a partner and the other two as opponents, as a counted category match leaves. Its `players` must be sorted non-blank ids with no repeats, twice the format's team size. With no gap rule for its format (`max_singles_rating_gap` for singles, `max_doubles_partner_gap` for the others), only `BEFORE_IMPORTED_BASELINE` can be recorded, so every named player must have a state with an `initial_source_date` in that format or, with none stored, under `category_feeds_parent` in a category format, an overall doubles state with one. In a resumable snapshot, no date may be after `calculated_as_of`, no state may have a nonzero `live_updates_since_replay` or `inherited_live_updates`, every processed match id must be a `ledger_digests` id, every player with a played state and every player a `seed_sensitive_rejections` entry names must be in `ledger_player_ids`, and the replay counts must match `ledger_digests` and `processed_match_ids`. Counts are at most `2**63 - 1`. An `int` or `float` subclass in a state's numbers or the replay counts of a snapshot passed in memory is checked and stored as the plain `int` or `float` of its own value.

- `snapshot_version`: `8`. A version 1, 2, 3, 4, 5, 6, or 7 snapshot does not load. Run a full replay to make a new one. Version 8 adds `seed_sensitive_rejections`. Version 7 added no key: `reserved_match_ids` now holds the id of every match `record` rejected, not only those not completed. Version 6 added `verified_matches_played` to each state and `net_rating_created` to `replay_info`. Version 5 added `reserved_match_ids`. Version 4 added `inherited_live_updates` to each state. Version 3 added no key: it marked that each row digest in `ledger_digests` covers `Match.status`.
- `engine_version`: the package version that wrote it. Informational, not checked.
- `config_version`, `config_fingerprint`: of the `Config` it was taken under. `from_snapshot` checks both against the `Config` it is given.
- `calculated_as_of`: the date of the last replay, or `null`.
- `replay_info`: `null` when `calculated_as_of` is, otherwise `as_of`, `config_version`, `config_fingerprint`, `matches_considered`, `matches_counted`, and `net_rating_created` (rating format value to a finite float, one key for every format, sorted). Each total must be a float, not an int, and not a negative zero, so a resume continues from the exact value a full replay had. Store the snapshot so these values stay JSON floats: a store that rewrites `0.0` as `0` makes the snapshot fail to load. It must be `0.0` for every format when `matches_counted` is 0, and for a format in which no player has a played state.
- `players`: sorted by `id`. Each has `id`, `account_user_id` (text or `null`), `external_ids` (source to id), and `ratings` (rating format value to state). A state has every `RatingState` field: `rating`, `rd`, `matches_played`, `last_played`, `rd_as_of`, `initial_rating`, `initial_source`, `initial_source_date`, `initial_source_reliability`, `initial_external_player_id`, `initial_evidence_reference`, `live_updates_since_replay`, `partners`, `opponents` (these two map a player id to a date), `inherited_live_updates`, and `verified_matches_played` (at most `matches_played`). `inherited_live_updates` is the parent's live count when a category state was derived from overall doubles, and 0 for any other state. Only a state derived from its parent can have a nonzero value, which needs `category_feeds_parent` and an `initial_source` of `open_parent:` plus the parent's value.
- `processed_match_ids`: sorted.
- `reserved_match_ids`: sorted. The `match_id` of each match `record` considered and did not count, for any reason other than `DUPLICATE_MATCH_ID`. A later `record` call for a match with one of these ids gets `DUPLICATE_MATCH_ID`, unless it raises first (for example for an `as_of` earlier than the match date). No id repeats or is also in `processed_match_ids`. Under `reject_content_duplicates=True` every `possible_duplicates` key is a reserved id, since a rejected copy reserves its `match_id`. In a resumable snapshot every id is also a `ledger_digests` id, since a replay reserves only a row it considered. In any snapshot, live or resumable, every `ledger_digests` id is processed or reserved, since a replay counts or reserves every row it considers and no id is ever freed.
- `self_reported_log`: sorted by format, then teams. Each entry has `rating_format`, `teams` (two sorted lists of player ids), and `dates` in the order they were recorded.
- `content_keys`: sorted by key. Each key is the SHA-256 digest of a counted match's content (its date, its two teams, and its game scores), and each value is the `match_id` of the first match counted with that content. Later matches with the same content are checked against it.
- `possible_duplicates`: sorted by key. The `match_id` of each match flagged or rejected as a possible duplicate, to the `match_id` it repeats (its `possible_duplicate_of`). An entry never clears. A key never names itself and is never a `content_keys` value, and each value must be a `content_keys` value. Under the default config every key is a processed match id. Under `reject_content_duplicates=True` no key is, and every key is a reserved match id. In a resumable snapshot every key is also a `ledger_digests` id, under either config, since a replay records a copy only for a row it considered. A live snapshot can hold a rejected id that no replay saw.
- `ledger_digests`: `match_id` to the SHA-256 digest of every row a replay considered, kept across resumes. Resume uses them to check rows dated on or before the checkpoint.
- `ledger_player_ids`: sorted ids of every player named in those rows, counted or not. Resume refuses a seed for one of them.
- `seed_sensitive_rejections`: sorted by `match_id`. Each update `record` rejected for `BEFORE_IMPORTED_BASELINE`, `SINGLES_RATING_GAP`, or `DOUBLES_PARTNER_GAP`, live or in a replay, as `players` (the sorted ids of the match's players) and `rating_format` (the format of the rejected update: the match's own, whose `match_id` is reserved, or `doubles` for the doubles update of a counted category match, whose `match_id` is processed). `seed_external_rating` and `add_player` refuse a seed for a named player in that format or, under `category_feeds_parent`, its parent. An entry never clears.
- `resumable`: `true` only while the engine is exactly what a replay produced. Resume refuses a snapshot where it is `false`.
