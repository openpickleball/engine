# Changelog

All notable changes to the OPEN rating engine are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, a minor version may include breaking changes.

The engine is a demonstration. Its outputs are not OPEN ratings.

## [Unreleased]

### Added

- A "Public API" section in the README that lists every public name, with the note that the API may change in any 0.x release. Names not listed there, including everything reached only through `open_engine.engine` or `open_engine.winprob`, are internal. A test checks that the list equals `open_engine.__all__`.
- An exception hierarchy. `OpenEngineError` is the base, and every class is a `ValueError`, so `except ValueError` still works: `ConfigError` (configuration and game formats), `InvalidMatchError` (matches, teams, ids, game scores, `played_at`), `InvalidSeedError` (external and replay seeds), `PlayerError` (player ids, account and external identity links), `EvaluationError` (evaluation, calibration, and win probability arguments), and `LedgerConflictError`, now under `OpenEngineError`. Seeding can also raise `PlayerError` for player identities, such as a blank or repeated player id, or an account or external identity already linked to another player.
- `RejectionReason`, a string enum with one member per reason a match is not counted.
- `PlayerSummary`, the frozen dataclass `player_summary` returns.
- Docstrings on every public name and on the public methods of public classes. A test checks them.
- Engine snapshots and checkpoints. `RatingEngine.to_snapshot()` returns the engine's whole state as JSON-safe data (schema version 7, documented in the README), with sorted keys and lists so the same state gives the same text. `RatingEngine.from_snapshot(snapshot, cfg=None)` rebuilds the engine after checking every key and type, the ranges of ratings, RDs, reliabilities, and counts, the config version and fingerprint against `cfg`, and the engine's own rules for states and identities (an unplayed state has a seed RD and no partners, counts and dates agree, and a resumable snapshot holds nothing dated after its replay). It checks shape and these rules, not authenticity, so a stored snapshot needs the same write protection as ratings. `replay` takes new keyword arguments: `from_snapshot` resumes from a replay's snapshot and gives the same result as a full replay, with the whole ledger or only the rows after the checkpoint, and `whole_ledger=True` (only with `from_snapshot`, else `SnapshotError`) tells resume it has the whole ledger, so it raises `SnapshotError` naming any row the checkpoint saw that is missing (a voided or deleted row). Take the snapshot right after the replay: every engine method that changes state (a live match, a seed, an identity link, a new player or rating state) makes resume refuse it, and changing objects the engine returns directly is not tracked and makes the snapshot unsafe to resume. Resume raises instead of differing: `SnapshotError` for a snapshot not from a replay or changed since, an `as_of` before the checkpoint, a row on or before the checkpoint date that the checkpoint did not see, or a seed for a player the checkpoint's rows named; `LedgerConflictError` for a changed row on or before the checkpoint date or a later row that reuses its id; `PlayerError` for a seed already in the snapshot. Without `whole_ledger=True`, resume cannot see a voided row on or before the checkpoint, and given only the newer rows it cannot see an edited or backdated row on or before the checkpoint either. With or without it, resume cannot see a seed withdrawn or corrected after the checkpoint. Those need a full replay. A `whole_ledger` that is not a bool raises `SnapshotError`. This change does not alter the ratings a full replay gives for any ledger a full replay still accepts. The Fixed section lists the rows a full replay now rejects (issue #16).
- `SnapshotError`, an `OpenEngineError`, for a snapshot that cannot be loaded or resumed from (issue #16).
- `UnknownPlayerError`, a `PlayerError`, for a read of a player id with no player record. `RatingEngine.player`, `RatingEngine.state`, and `RatingEngine.player_summary` raise it (issue #23).
- `ReferenceDateError`, an `OpenEngineError`, for a `player_summary` call with no date to measure at, or with an `as_of` that is not a plain date (issue #17).
- `Config.established_reliability_threshold` (default 60.0) and `PlayerSummary.established`, a bool right after `imported_reliability`. It is `True` when `reliability` (OPEN-earned, as displayed, rounded to 1 place, at the summary's reference date) is at least the threshold and, since issue #59, the state has at least `Config.established_min_verified_matches` counted verified matches. `Config` raises `ConfigError` for a threshold below 0, above 100, or NaN. Imported reliability never counts. Under the default config an unplayed imported seed is not established (its earned reliability is at most 32.6). An established player who stops playing loses it as the reference date moves on. Under the defaults, a new player with no imported rating, playing one match a week with varied partners and opponents, becomes established after about 10 to 13 tournament, league, or recreational verified matches (10 tournament, 11 league, or 13 recreational verified matches of one game, fewer for best of 3), and after about twice as many against the same players. Since issue #58, with `Config.connectivity_reliability_cap` set, these counts are for a player whose network connectivity is connected. Self-reported matches raise reliability past the threshold after about 20 to 25 with varied players (never against the same players, because repeat matches are discounted and then rejected); since issue #59, established also needs a minimum of counted verified matches, so such a player is not established until they have it (see the `Config.established_min_verified_matches` entry). A player seeded from a recently captured imported rating starts at a lower RD (`Config.external_seed_rd`) and is established after about 3 to 4 tournament, league, or recreational verified matches. RD grows from the capture date, so an older import gives less of a head start, and a very old one none. The imported rating and its reliability value do not change the count. A rating that is not established is what external rating systems usually call provisional; OPEN's provisional live updates and the `open_provisional` source are different things. The threshold changes no rating and no `evaluate`, `prequential_predictions`, `fit_scale`, or `fit_win_calibration` output. It is separate from evaluation's eligibility rule (an imported baseline or `burn_in_matches` OPEN matches). The new field changes the default `Config().fingerprint()`. A snapshot made under an earlier default config fails `from_snapshot` under the new default config with a fingerprint mismatch, and replay records carry a different fingerprint (issue #18).
- `MatchResult.imbalance`: the mean team A delta plus the mean team B delta, from the unrounded changes, rounded to 5 places. Each delta is rounded on its own, so `imbalance` can differ from the same sum of the rounded deltas by up to 1.5e-5. It is 0.0 when both teams have the same mean K and no player is clamped or frozen, and for a match that did not count. It can be nonzero when the teams' mean K differ or a player is clamped or frozen. A value of 0.0 does not mean nothing was clamped or frozen: read `clamped` and `frozen` for that. A category match's `parent` result has its own value. The field comes after `clamped` and before `parent` (issue #14).
- `MatchResult.late`, a bool right after `imbalance`, default `False`. It is `True` for a counted match dated before a player's last match in that rating format, or before the date that player's rating in that format already reflects (for a category rating copied from overall doubles). Frozen players count. Live recording applies matches in arrival order, so the backend should check `late` and, for a category match, `parent.late`, and schedule a replay when either is `True`. It compares dates only, so a match on the same date is never late. It is `False` for a match that did not count and for every match a replay records. A category match's `parent` result has its own value, measured against the overall doubles dates (issue #19).
- A published policy for match performance: team A's share of all points across games, blended with the result by `Config.win_weight` (default 0.0, pure point share). A team can win and still lose rating when it wins by less than expected or wins a best of 3 (or 5) with fewer total points. There is no floor on a winner's change other than the rating range (`min_rating` to `max_rating`), and `win_weight = 1.0` scores the result only. The default changes only when out-of-sample evaluation supports another value. The policy is in the engine module docstring, the `Config` comment, and a new README section, with tests that pin it. It changes no rating (issue #20).
- `MatchResult.possible_duplicate_of`, the last field, default `None`. It names the earliest counted match with the same content as this one under another `match_id`: the same `played_on`, the same two teams as sets of players (either side may be team A), and the same game scores read from the same side. Match type, rating format, game format, `best_of`, `played_at`, `sequence`, and `confirmed_by` are left out. It is `None` when there is no such earlier match. Only a counted match and a match rejected as a possible duplicate carry it; it is `None` on every other result and on `parent`. The later match in processing order is the one flagged: arrival order live, ledger order in a replay (issue #21).
- `Config.reject_content_duplicates` (default `False`), a bool; any other value raises `ConfigError`. `False` does not reject a possible duplicate: it goes through the other checks and, if it counts, is flagged. `True` does not count it and returns `RejectionReason.POSSIBLE_DUPLICATE`. A real rematch on the same day between the same teams with the same scores is flagged too, or not counted under `True`. Reports that disagree on the date are not caught. The new field changes the default `Config().fingerprint()`, so a snapshot made under an earlier default config fails `from_snapshot` with a fingerprint mismatch. Under the default, every rating is the same as before (issue #21).
- `RejectionReason.POSSIBLE_DUPLICATE` (`"possible_duplicate"`), for a match rejected under `Config.reject_content_duplicates` (issue #21).
- Which report counts as the copy is set by processing order alone (arrival order live; ledger order in a replay, where, within a date, untimed rows come first by `sequence` then `match_id`, then timed rows by the UTC instant of `played_at`, then `sequence` and `match_id`), whatever the match type, rating format, or game format. Under `reject_content_duplicates=True` a weaker or relabeled copy (an untimed self-report of a timed tournament match, or a mixed doubles copy of a doubles match) can count while the stronger report is rejected, a category copy that counts first can keep the other row from updating its rating format, and live recording and a replay can keep different rows. Under the default the flagged row can be the stronger one. Use reject only when the backend trusts who files reports, and otherwise resolve flags in the backend. Under the default, a category copy of a doubles match can count twice in overall doubles, once directly and once through `parent`, whose `possible_duplicate_of` is `None`. Do not show `possible_duplicate_of` to whoever submitted the match: it names another report (issue #21).
- `RatingEngine.possible_duplicates`, a dict from the `match_id` of each match flagged or rejected as a possible duplicate to the `match_id` it repeats. An entry never clears, since its `match_id` is processed or, for a rejected copy, reserved (issue #76). `record` fills it live and in a replay, under both policies, so the backend can read the flags after a replay. Recording a rejected copy in it is a state change, so a snapshot taken after it is not resumable. The snapshot carries it as `possible_duplicates` (issue #21).
- `MatchStatus`, a public string enum: `COMPLETED` (`"completed"`), `FORFEIT` (`"forfeit"`), `RETIRED` (`"retired"`), and `INCOMPLETE` (`"incomplete"`) (issue #22).
- `Match.status`, the last field, default `MatchStatus.COMPLETED`, so a match built without it validates and rates as before. `Match.validate` raises `InvalidMatchError` for a status that is not a `MatchStatus` member (the plain text `"completed"` included), `games` that is not a tuple or list (for every status, so a completed match with `games=None` gets this message instead of "At least one game score is required"), a forfeit with any game, and a retired or incomplete match with a decided winner. A forfeit must have no games. A retired or incomplete match has zero or more finished games, each valid in its game format, and no decided winner, so in a best of 1 it has no games. Every other match check applies to every status (issue #22).
- `RejectionReason.MATCH_NOT_COMPLETED` (`"match_not_completed"`), for a match whose status is not completed (issue #22).
- A published policy for forfeits, retirements, and incomplete matches: they are never rated. `record` rejects such a match after the `match_id` check (a processed or reserved `match_id` gets `DUPLICATE_MATCH_ID`), moves no rating, and reserves its `match_id`: a later `record` call for a match with that id that does not raise returns `DUPLICATE_MATCH_ID` (see the Security entry for issue #73). `replay` accepts the row and counts it in `matches_considered` but not `matches_counted`. A full replay gives each player the same ratings as a full replay without it. As for any rejected row, a checkpoint tracks the row and its players, so resume raises `SnapshotError` for a new seed for a player named only in such a row. Replacing the row with a completed one under the same `match_id` is an edited row: for a row dated on or before a checkpoint it needs a full replay (resume raises `LedgerConflictError` when given it). `prequential_predictions` (and so `evaluate`, `fit_scale`, and `fit_win_calibration`) never predicts it, and takes its seed date limit and default scheduled anchor from completed rows only, so a seed dated after the last completed match raises `InvalidSeedError` whatever rows follow it, and a ledger with no completed match has no seed date check. No rating math changes. The backend should verify a status as it verifies scores, since a status keeps a match from moving any rating, and store which team forfeited or retired (issue #22).
- `Config.to_dict()` and `Config.from_dict()`. `to_dict` returns a new dict (enum keys and values as their strings, game length keys as strings, `allowed_game_formats` as a sorted list of `[scoring, points]` pairs, other values as they are). `from_dict` takes that data, also after a round trip through Python's `json` module, and returns an equal `Config` with the same fingerprint. An int and a float are different values to the fingerprint, so a store that rewrites `8.0` as `8` changes the config. `from_dict` needs exactly the keys `to_dict` gives and raises `ConfigError` for a missing or unknown key, a value it cannot convert, or a value `Config` rejects (issue #25).
- `Config` is hashable, so it can be a dict key or a set member. Equal configs hash equal. Since issues #68 and #70, `Config` rejects any field value JSON cannot hold, such as a `Decimal` or a non-finite float, so `hash`, `==`, and `fingerprint()` never raise on a built config (issue #25).
- `Config.established_min_verified_matches` (default 3), a whole number of at least 0; anything else (a negative int, a bool, a float, a str) raises `ConfigError`. It is in the fingerprint and in `to_dict` and `from_dict` (issue #59).
- `RatingState.verified_matches_played`, the last field, default 0: the counted tournament, league, and recreational verified matches that moved the state. It counts where `matches_played` counts, so a frozen player gains neither, a counted category match counts in its category and, when its overall doubles update counts, in doubles, and a category state derived from overall doubles starts at 0. Self-reported matches never count. A seed must have 0, else `InvalidSeedError` (issue #59).
- `ReplayInfo.net_rating_created`, the last field: per rating format, the net rating a replay's counted updates added to that pool (negative when they removed it), summed in ledger order from the unrounded changes. A category match adds to its format and, when `Config.category_feeds_parent` is on and its overall doubles update counts, to doubles. It has a key for every `RatingFormat` (0.0 where nothing counted) and is read-only. It defaults to all zeros, so a `ReplayInfo` built without it still works. A resume continues from the checkpoint's total and gives the same floats as a full replay. Live updates do not change it. Adding `team_size * imbalance` of each live result between replays gives an approximate running total (imbalance is rounded to 5 places); the next replay gives the exact total. The engine reports the total and does not limit it; a limit would discard evidence and needs out-of-sample evaluation first (issue #42).
- `NetworkConnectivity`, a public frozen dataclass, and `PlayerSummary.connectivity`, its last field: whether the player's pool connects to the wider network in that rating format, measured at the summary's reference date over `Config.diversity_window_days` from the partners and opponents stored in each rating state. It reports `pool_size`, `fringe_players`, `outside_players`, `outside_days`, `group_size`, `in_main_network`, and `connected`. A group is a set of players linked by contact, and a main network is a group with at least half as many players as the largest. A pool is a set of players linked by ties, where two players in contact are tied when they share at least `connectivity_min_shared_contacts` contacts and each of them is in contact with those shared players on at least `connectivity_min_contact_days` distinct dates. The pool's fringe is the players in contact with it whose contacts are all in the pool or in contact with it (drop-ins). A player is connected when they have a contact in the window, their group is a main network, and the pool with its fringe holds more than half the group or the pool has at least `connectivity_min_outside_players` other outside players on at least `connectivity_min_contact_days` distinct dates. A summary for a format the player has no state in is measured as if the unplayed state a seed would store were stored, so it is not connected. The measure is derived from stored state only, so the snapshot format does not change (still version 6) and a resume gives the same values as a full replay. The results are cached per format and reference date until the next state change, for the 16 most recent dates. The rule can be gamed through group sizes and can mark players in a real but smaller network as not connected; the module docstring and README list its limits (issue #58).
- `Config.connectivity_reliability_cap` (default `None`, off; else a number from 0 to 100), `Config.connectivity_min_shared_contacts` (default 4), `Config.connectivity_min_contact_days` (default 3), and `Config.connectivity_min_outside_players` (default 8), the last three positive ints (not bools). Other values raise `ConfigError`. They are in the fingerprint and in `to_dict` and `from_dict` (issue #58).

### Changed

- **Breaking:** `Config` checks every field's type, finiteness, and range when it is built, and raises `ConfigError` for each value it now rejects. A `bool` is never a number. Newly rejected: a wrong type in any scalar field (for example a str, `None`, a `bool`, or a `Decimal` where a number is expected, an int where a bool is expected, or a non-str `version`); a NaN, infinite, or too-large-for-a-float value in any number field, in a mapping value, or as a `game_length_weights` key; a float such as `7.0` in a whole-number field (the day counts, `diversity_target`, `self_reported_max_repeats`, `import_reliability_carry_matches`); `min_rating`, `max_rating`, or `default_rating` beyond `2**511` in magnitude (so `max_rating=1e308` raises); `rd_min` equal to `rd_max`, or an int and a float that are equal once converted, so `rd_max - rd_min` is 0.0; `rd_max` above `2**511`; a negative `rd_shrink_per_match`; `rd_growth_per_day` below 0 or above `2**511`, or above `2**500` as an int; a `game_count_bonus` above `2**511` as an int (these two int bounds exist because exact int arithmetic raises `OverflowError` where float arithmetic goes to infinity); a `match_weights` or `game_length_weights` value of 0 or less; a `game_length_weights` key below 1; a negative `game_count_bonus`; points in `allowed_game_formats` too large for a float; a K range whose largest K (`k_min + (k_max - k_min) * 1.0`, which can round just above `k_max`) times the largest match weight and `max_information_multiplier` is not finite in floats; two `game_length_weights` keys that name the same length; `replay_interval_days`, `diversity_window_days`, `self_reported_repeat_window_days`, or `import_reliability_max_age_days` above 3,652,058 (the days `timedelta` holds; a window that reaches back before `date.min` from a match or reference date still raises `OverflowError`, issue #92); and a negative `max_singles_rating_gap` or `max_doubles_partner_gap`. Before, some of these built and then raised `TypeError`, `ValueError`, `ZeroDivisionError`, or `OverflowError` later, in `fingerprint()` or on the first match, and an overflowing K step could turn a surprise of 0 into a jump to `max_rating`. With int match weights and multipliers near `2**511`, exact int arithmetic in rating code can still raise `OverflowError` or overflow the step (issue #93). `Config` now stores mapping keys and `allowed_game_formats` pairs as their own types: a `ScoringType` or `MatchType` key given as its str value, or an object equal to one, becomes the enum member, and an int subclass key or points value becomes the plain `int` of its own value (an overridden `__int__` is not used). The fingerprint of every config that built before and was JSON-safe stays the same, except for a key or points value whose `str()` differs from its value (such as a str or int subclass with its own `__str__`): it now gives the fingerprint of the plain enum member or int. Ratings do not change in those cases. `Config.from_dict` raises `ConfigError` instead of a bare `ValueError` for an int too large to print in its data. A config passed to `Config.from_dict` with `"k_min": "low"` now raises `ConfigError` with "k_min must be a finite number" instead of the wrapped `TypeError` message. Defaults do not change, `Config().fingerprint()` stays `17f2981186edf96c`, and no rating, prediction, or evaluation output changes for a config that still builds. The README "Config values" section lists the rules. Migration: fix any stored or hand-built config that now raises; store whole-number fields as ints, and use `rd_min < rd_max` (issues #68 and #70).
- **Breaking:** `replay` raises `ReferenceDateError` for an `as_of` that is not a plain `date`: a str, a naive or aware datetime, `None`, or any other type. A `date` subclass that is not a datetime is still accepted. It checks this first, before `whole_ledger`, `from_snapshot`, the ledger rows, and the seeds. Such an `as_of` used to reach the later checks, which most often failed with a bare `TypeError` or with whichever engine error came first. Some calls replayed and stored it as `calculated_as_of`, for example `replay([], as_of="2026-03-31")`; those now raise. Migration: pass a `datetime.date`. For a datetime, pass `.date()`. Parse a str with `date.fromisoformat` (issue #66).
- **Breaking:** `PlayerSummary.connectivity` has no default, so code that builds a `PlayerSummary` itself must pass it. The new `Config` fields change the default `Config().fingerprint()` to `17f2981186edf96c`, so a snapshot made under an earlier default config fails `from_snapshot` with a fingerprint mismatch, and a stored `Config.to_dict()` from before lacks the new keys, so `Config.from_dict` raises `ConfigError`. With `Config.connectivity_reliability_cap` set, `PlayerSummary.reliability` is at most the cap (shown rounded down to 1 place) for a player whose `connectivity.connected` is False, and `established` and the imported reliability carry compare against that displayed value. The default cap is `None`, so under the default config `reliability` and `established` are unchanged, and no rating, RD, K, prediction, `evaluate`, `prequential_predictions`, `fit_scale`, or `fit_win_calibration` output changes under any cap. Turning the cap on by default waits for out-of-sample review of real ledgers (issue #58).
- **Breaking:** seed and identity entry points reject blank and shared identities. `add_player`, `replay(seed_players=...)`, and `prequential_predictions` (both modes, and so `evaluate`, `fit_scale`, and `fit_win_calibration`) raise `InvalidSeedError` for a seed whose player id, `account_user_id` (when not `None`), external source, or external id is blank or whitespace only, and for a seed state whose `initial_rating` is not an int or finite float (not bool) or is outside `min_rating` and `max_rating`. Such a replay used to succeed, and `to_snapshot()` on it then raised `SnapshotError`. They raise `PlayerError` for a seed whose `account_user_id` or (source, external id) pair another player already holds: an existing player in `add_player`, an earlier seed in the same batch, or a checkpoint player on resume. The messages are the ones `link_account` and `attach_external_id` use. Every check runs before any state changes. `link_account` and `attach_external_id` raise `PlayerError` for a whitespace-only or non-str account, source, or external id, which used to be accepted; a whitespace account made `PlayerSummary.account_linked` `True`. `seed_external_rating` raises `PlayerError` when its snapshot has a non-empty `external_player_id` and that id or the source is whitespace only. An empty `external_player_id` still links nothing, and the provenance it stores is not checked. The issue #74 entry under Security replaces these two rules with `InvalidSeedError`. The same external id from two different sources is still accepted. A `RatingState` built with the dataclass default `initial_rating` (3.5) is now rejected as a seed under a config whose rating range excludes 3.5; `seed_provisional_rating` and `seed_external_rating` set it within the range. `RatingEngine.player`, `state`, `player_summary`, `link_account`, `attach_external_id`, `seed_provisional_rating`, and `seed_external_rating` raise `PlayerError` for a non-str player id instead of `AttributeError`. Seed identity checks for a batch (in `replay` and `prequential_predictions`) are a fixed number of set lookups per seed identity, so they do not slow down as the number of seeds grows. Ratings do not change for any input that is still accepted. Snapshot loading now follows these rules too, see the issue #61 entry (issue #52, also #44 and #45).
- **Breaking:** `RatingEngine.from_snapshot`, and so `replay(from_snapshot=...)`, raises `SnapshotError` naming the field for snapshot states no engine method produces. Any snapshot: an `account_user_id` that is blank or whitespace only, an `external_ids` source or id that is blank or whitespace only, two players with the same `account_user_id` or the same source and external id pair (the later player in the list is named), and a `partners` or `opponents` id or a `self_reported_log` team member that is not a player in the snapshot. A resumable snapshot: a nonzero `live_updates_since_replay`, a processed match id that is not a `ledger_digests` id, and a player with a played state who is not in `ledger_player_ids`. A stored snapshot holding one of these used to load and now fails. Every snapshot the engine's own methods produce still loads. `to_snapshot()` checks its own output the same way, so it now raises `SnapshotError` for these states when a caller sets them directly on public engine attributes, for example two players with the same `account_user_id` assigned into `engine.players`. No engine method produces them. The schema and `snapshot_version` do not change, and no rating changes. Resuming from a resumable snapshot with a live update count but no live match now fails at load with the `live_updates_since_replay` message instead of the resume message, and resuming from a resumable snapshot whose replay counts still match but which has a processed match id with no ledger digest (for example a digest key swapped for another id) now fails at load with the `processed_match_ids names ...` message instead of the resume message. A snapshot that is not resumable still gets the resume message (issue #61).
- **Breaking:** `Config.scale_by_scoring`, `win_calibration_by_scoring`, `match_weights`, and `game_length_weights` are read-only copies of the mappings passed in. Item assignment, `update`, `pop`, and the other dict changes raise `TypeError`, and changing the dict a config was built from no longer changes the config. A non-mapping value, a mapping value that is not a finite int or float (a `bool`, a string, a list, NaN, or infinity), or a `game_length_weights` key that is not an int (`"11"`, `11.0`, `True`) raises `ConfigError`. A string key used to share a fingerprint with the int key the engine reads. `allowed_game_formats` is stored as a `frozenset`; a value that is not a `set` or `frozenset`, such as a list, or an entry that is not a (scoring type, int) pair, raises `ConfigError`. Build a new config with `dataclasses.replace` instead of changing one (issue #25).
- **Breaking:** `Config` equality compares fingerprint payloads, so equal configs always have the same fingerprint and hash. Configs that used to compare equal with different fingerprints, such as `Config(k_min=0)` and `Config(k_min=0.0)`, are no longer equal. No config that still builds gets a new fingerprint: `Config()` still gave `c5bb49f7c37a013a` after that change; the later `established_min_verified_matches` field changes it.
- `RatingState.inherited_live_updates`, a new int field, default 0. It comes after `opponents`, so positional calls that pass `partners` or `opponents` keep their meaning; `verified_matches_played` (issue #59) now follows it as the last field. A category state (mixed, men's, or women's doubles) derived from overall doubles copies a rating that can hold live updates since the last replay. The field records how many the parent state had when the category state was derived, and never changes after that. It is 0 for every state not derived from its parent. `PlayerSummary.live_updates_since_recalculation` keeps its name and type but now reports `live_updates_since_replay + inherited_live_updates`, so a derived category state is labeled with the parent's live updates in its starting rating, before and after its first match. It used to report the state's own count only, which labeled such a state too low. A replay gives 0 for every state. No rating, RD, or reliability changes. ### Fixed

- A self-reported match given with `match_type` as its str value (`"self_reported"`), which `Match.validate` then accepted, skipped the confirmation rule, the repeat discount and limit, and the self-reported log, so it counted at full self-reported weight with no confirmation. `record` now compares the type by equality, so the str value gets every self-reported rule, exactly like `MatchType.SELF_REPORTED`. Ratings can change for such rows. Under the default config, an unconfirmed one no longer counts, a repeat is discounted and then rejected, and the row now counts toward later repeat checks. This is an integrity fix. Since issues #65 and #83, `Match.validate` rejects a str `match_type` with `InvalidMatchError`, so such a row no longer reaches `record` (see Changed).
- `fit_scale` and `fit_win_calibration` now raise `EvaluationError`, before any prediction work, when `low` is not less than `high`, `tolerance` is not finite and greater than 0, or `2 * low`, `2 * high`, or `(high - low) * 14` is not finite, so `low` and `high` must be finite and not near the float limit (issue #28). A `tolerance` of 0 or less could hang the search, and swapped or equal bounds could return a fit from a meaningless range. The search also ends when its bracket stops shrinking, so a positive `tolerance` below the float spacing near the fitted value no longer hangs. With the default tolerances, or any tolerance well above that spacing, the fits are the same as before.
- Evaluation, calibration, and win probability results are now the same on Python 3.11, 3.12, and 3.13 (issue #40). Python 3.12 changed the built-in `sum()` of floats to compensated summation, so on 3.11 a float sum could round differently in the last bit. The engine now adds floats with `math.fsum`, which is correctly rounded on every version. Ratings, RDs, and `ReplayInfo` do not change on any version: every float sum on the rating path adds one or two terms, which `sum()` and `math.fsum` round the same way. The exception is a `Config` whose rating range is so large that two ratings add up past the largest float: those sums gave `inf` and wrong expectations before, and now raise `OverflowError` (issue #70). Win probabilities (`game_win_probability`, `match_win_probability`, `predict_win_probability`, `PrequentialPrediction.win_probability_raw`), `evaluate` reports, `ScaleFit.profile`, and Brier scores can move in the last bit, mostly on 3.11 and rarely on 3.12 and later. A value rounded for display can change where that bit decides the rounding: in a synthetic test, one `evaluate` calibration bin's mean actual share moved from 0.6047 to 0.6048 on 3.11. A test pins exact replay, evaluation, and win probability output on every CI Python version.
- A `Config`'s mapping fields can no longer change after it is built (issue #25). They were plain dicts, so `cfg.match_weights[MatchType.LEAGUE] = 9` succeeded and changed `cfg.fingerprint()`, the provenance stored with each replay. The dict fields also made `Config` unhashable.
- `link_account`, `attach_external_id`, and `seed_external_rating` now run every check before they change anything. A call that raised for a new player id (an account or external identity already linked to another player, or a snapshot identity with no source) used to leave an empty player record behind and clear the snapshot's resumable mark. Now a call that raises leaves the engine as it was. Error types and messages, and what a successful call creates, are unchanged (issue #23). The issue #74 entry under Security changes the snapshot identity with no source case to `InvalidSeedError` ("External snapshot source must not be blank").
- A live match dated before a player's last match, or before the date a category rating copied from overall doubles already reflects, no longer moves `last_played`, `rd_as_of`, or partner and opponent dates back. Each now keeps the later date, and a new partner or opponent gets the match date. Before, inactivity RD growth ran again from the older date, so it counted twice, `last_played` (and with it `player_summary`'s default reference date) was wrong, and a partner or opponent seen recently could drop out of the rolling diversity window. The late match's own update is unchanged, and so is every match recorded in play order, so replay gives the same ratings as before. Live results still apply in arrival order; `MatchResult.late` flags these matches. Because dates never move back, a future-dated live match now holds its players' dates at that future date until the next replay, so their RD stops growing and their reliability stays high. The engine never reads the clock, so the backend must reject a match whose `played_on` is after the date it was submitted. A later honest match with those players that counts in the same rating format is flagged `late`, and for a category match `parent.late` covers the overall doubles rating (issue #19).
- Rows that repeat a `match_id` and differ only in the type of a member inside a list or set field (for example a game written as `[11, 1]` in one row and `[11, True]` in the other) now raise `LedgerConflictError` in `replay` and `prequential_predictions`, as the rule that every field matches in type and value says. They used to collapse to one row, because list and set fields were compared with `==` only (issue #16).
- Replay no longer shrinks old matches' updates. Recency decay scaled each update by the match's age at the replay date, so a replay disagreed with live recording of the same ledger, `evaluate(mode="live")` and `evaluate(mode="scheduled")` disagreed, a player whose matches were all long ago drifted back toward the default rating, and every recalculation shifted ratings even with no new matches (issue #13).
- `record` with a blank or whitespace-only player id, or one that is not a string (such as an int), no longer changes any rating. It used to update the players before the bad id, then raise before marking the match processed, so every retry moved those ratings again. It now raises `InvalidMatchError` before anything changes.
- `LedgerConflictError` survives pickling and copying with its message and `match_ids` intact. The message used to come back garbled.
- `game_win_probability`, `match_win_probability`, and `predict_win_probability` validate the `GameFormat` and raise `ConfigError` for an invalid one. Before, a `cap` at or below `points_to` silently returned a wrong probability, and `points_to=0` raised a bare `ValueError` from inside the math.
- A malformed game score (not a pair of scores) raises `InvalidMatchError` instead of a bare `ValueError` or `TypeError` from unpacking.

### Security

- Reliability can no longer be set without match results (issue #15). A seed passed to `add_player` or `replay` could carry any RD, partners, and opponents with zero matches (for example RD 0.10 and 20 partners gave reliability 100), `rd_override` let a caller pick a seed's RD, `external_reliability_maps_to_rd` turned an external score into OPEN RD, the headline summary reliability showed the imported value, a seed dated in the future froze every match before its date and kept its imported reliability shown (`replay` and `prequential_predictions` now reject it, and `player_summary` does not carry an import captured after its reference date, which with no `as_of` is the later of the last replay date and the player's last match (see the `player_summary` entry under Changed)), and a seed rating outside the rating bounds moved other players' ratings. Each is closed by the breaking changes above.
- **Breaking:** live `record` no longer counts a match that reuses the `match_id` of a match it rejected as not completed (issue #73). It used to leave that `match_id` free, so a completed match with the same id, even with other players, counted live, while `replay` of the same two rows raised `LedgerConflictError`. A party that could submit a forfeit and then a completed match under its id could move other players' ratings live in a way no replay would. `record` now reserves the `match_id` of every match it rejects with `MATCH_NOT_COMPLETED`, and every later `record` call for a match with that id that does not raise returns `DUPLICATE_MATCH_ID`. The reservation moves no rating and changes no count, content key, or possible duplicate. A live reservation sets the snapshot's `resumable` to `false`. To relabel a forfeit as completed, use a new `match_id`, as replay already required. The snapshot schema is version 5: a new key, `reserved_match_ids`, sorted. `from_snapshot` raises `SnapshotError` for a version 4 snapshot, and for `reserved_match_ids` that is missing, not a list, has an id that is not a non-blank str, repeats an id, or has an id in `processed_match_ids`, and, in a resumable snapshot, has an id that is not a `ledger_digests` id or (until issue #76 removed this rule) is a `possible_duplicates` key. Snapshots were never in a release, so version 4 snapshots were only written by unreleased builds of main. Run a full replay to make a new one. Replay ratings do not change for any ledger.
- **Breaking:** live `record` now reserves the `match_id` of every match it considers and does not count, whatever the `RejectionReason` (issue #76). It used to reserve only a match rejected as not completed (issue #73), so after any other rejection (`GAME_FORMAT_NOT_ACCEPTED`, `POSSIBLE_DUPLICATE`, `SELF_REPORTED_UNCONFIRMED`, `SELF_REPORTED_REPEAT_LIMIT`, `BEFORE_IMPORTED_BASELINE`, `SINGLES_RATING_GAP`, or `DOUBLES_PARTNER_GAP`) a different match with the same id could count live, while `replay` of the same two rows raised `LedgerConflictError`. That let a provisional rating move on a row the next replay refuses, and let a party that could reuse a rejected `match_id` move other players' ratings live. Now every later `record` call for a match with a rejected id that does not raise returns `DUPLICATE_MATCH_ID`, so a match never counts live under a `match_id` whose earlier row would make a replay of the same rows raise `LedgerConflictError`. The reservation moves no rating and changes no count or content key. A live rejection other than `DUPLICATE_MATCH_ID` sets the snapshot's `resumable` to `false`. A `possible_duplicates` entry never clears: a copy rejected under `reject_content_duplicates=True` keeps its id reserved, so it can no longer count later on its own and leave the map. The snapshot schema is version 7, with no new key: `reserved_match_ids` holds the id of every rejected match. `from_snapshot` raises `SnapshotError` for a version 6 snapshot; under `reject_content_duplicates=True` for a `possible_duplicates` key that is not a reserved id; and, in any snapshot, live or resumable, for a `ledger_digests` id that is neither processed nor reserved. The old rule that a reserved id in a resumable snapshot is never a `possible_duplicates` key is gone. Replay ratings do not change for any ledger. Migration: give a corrected resubmission a new `match_id` and keep the rejected row in the ledger unchanged. Resubmit only after a rejection that comes from the match itself (`GAME_FORMAT_NOT_ACCEPTED`, `SELF_REPORTED_UNCONFIRMED`, `MATCH_NOT_COMPLETED`), for example a self-reported match resubmitted after both teams confirm it, or a match corrected to an accepted game format. Do not resubmit after any other rejection: a replay can count the original row, and a copy under a new `match_id` could count too. A replay under a different `Config` can count rows rejected for game format or confirmation, so review resubmitted rows before such a replay. Run a full replay to replace stored version 6 snapshots.
- **Breaking:** a seed's external provenance must be its own and not blank (issue #74). A seed `RatingState` could name another player's (source, external id) pair in `initial_source` and `initial_external_player_id` without listing it in the seed's own `external_ids`, so the identity uniqueness check from issue #52 did not see it, and `add_player`, `replay(seed_players=...)`, and `prequential_predictions` accepted a second player carrying the first player's imported provenance. `add_player`, `replay(seed_players=...)`, and `prequential_predictions` (both modes, and so `evaluate`, `fit_scale`, and `fit_win_calibration`) now raise `InvalidSeedError`, before any state changes, for a seed state whose `initial_source` is not a str or is blank or whitespace only, whose `initial_external_player_id` is not a str or `None` or is blank or whitespace only, or whose `initial_external_player_id` is set while the seed's own `external_ids` does not map `initial_source` to it. A seed that does list the pair is covered by the issue #52 check, so it raises `PlayerError` ("This external identity is already linked to another player") when an existing player or an earlier seed in the same batch holds the pair. A seed that names another player's pair without listing it gets `InvalidSeedError`, not `PlayerError`, since the seed rules run first. `seed_external_rating` raises `InvalidSeedError` for a snapshot `source` that is blank or whitespace only and for an `external_player_id` that is `""` or whitespace only, before anything changes. It used to accept a blank or whitespace-only source when no external id was given (`None` or `""`) and store it as provenance, with an empty `external_player_id` stored too. With an external id, a blank or whitespace-only source raised `PlayerError`, as did a whitespace-only id. `external_player_id=None` still links nothing. These snapshot field checks run before the player id check, as the other snapshot field checks do, so a call with a blank player id and a blank source now raises `InvalidSeedError` instead of `PlayerError`. `RatingEngine.from_snapshot`, and so `replay(from_snapshot=...)`, raises `SnapshotError` naming the field for a state whose `initial_source` is blank or whitespace only, whose `initial_external_player_id` is `""` or whitespace only, or whose `initial_external_player_id` the same player's `external_ids` does not map `initial_source` to. A stored snapshot holding one of these used to load and now fails, for example one taken after `seed_external_rating` with `source="  "` or `external_player_id=""`. Every snapshot the engine's own methods produce from plain `str` and `dict` values still loads. `to_snapshot()` checks its own output the same way, so it raises `SnapshotError` for such a state when a caller sets it directly on public engine attributes. No engine method produces one from plain `str` and `dict` values; a `str` subclass that overrides `__eq__` or `strip`, or a `dict` subclass that overrides `get`, can pass the new checks and still give a snapshot that does not load (issue #96). The schema and `snapshot_version` do not change. Ratings do not change for any input that is still accepted. Migration: give every seed state a non-blank `initial_source`, and either list its `initial_external_player_id` in the same seed's `external_ids` under that source or set it to `None`. Pass `external_player_id=None`, not `""`, to `seed_external_rating` for a snapshot with no external id. For a stored snapshot that now fails, correct the seeds and run a full replay to make a new one.
- **Breaking:** `seed_external_rating` no longer replaces or creates a rating that carries OPEN history (issue #79). It raises `InvalidSeedError` ("Cannot replace a rating derived from OPEN overall doubles") for a stored category state derived from overall doubles (`initial_source` starting with `open_parent:`), even with `replace_unplayed_seed=True`. Such a state has `matches_played` 0, so the import used to replace a rating that came from OPEN doubles matches. It also raises `InvalidSeedError` ("Cannot seed a rating format in which OPEN matches have counted for this player") when a counted update in that format included the player, including one in which the player was frozen because it was on or before the imported capture date. For overall doubles, that includes the doubles update of a category match. A frozen player keeps `matches_played` 0, so a reseed used to pass, and a reseed with an earlier capture date changed whether the player was frozen in that match, so live ratings and a replay of the same ledger could disagree. This also covers a category format with no stored state when the player was frozen in a counted category match there. Under `category_feeds_parent`, it also raises `InvalidSeedError` when seeding overall doubles while a counted category match included the player, whatever the player's state in that category is, since a new doubles seed could change whether that match's doubles update counts (for example one rejected as before the imported baseline) or the state a replay starts the category from. This applies to a first doubles seed too. A match that did not count leaves no record of its players, so a reseed after one can still make live and replay disagree (issue #99). The engine finds such a match from the `partners` and `opponents` of the players who moved in it, so the check does not depend on `initial_source`, and no snapshot field changes. A refused call changes nothing. Seeding a category format with no stored state and no counted match in it is still allowed, even when the player has an overall doubles rating, and an unplayed seed with no counted match can still be replaced. `seed_external_rating` also raises `InvalidSeedError` for a `snapshot` that is not an `ExternalRatingSnapshot`, instead of `AttributeError`. Ratings, replay, and the snapshot schema do not change. Migration: import a corrected external rating before the player's first counted OPEN match in that format, or rebuild with `replay` from corrected seeds.
- **Breaking:** a snapshot's overall doubles count of self-reported updates must now equal the logged doubles and category matches when category matches feed doubles and `max_doubles_partner_gap` is unset (issue #84). Under `category_feeds_parent`, `matches_played - verified_matches_played` of an overall doubles state was checked only against a range: at least the self-reported doubles matches logged for the player, at most those plus the logged category matches. So a stored snapshot that relabeled a self-reported update that reached doubles from a category match as verified still loaded, for example one where a player's doubles state with one self-reported doubles match and one self-reported mixed doubles match had `verified_matches_played` raised from 0 to 1. Under `category_feeds_parent` with `max_doubles_partner_gap` unset, a counted category match's doubles update is rejected only when every player is frozen in doubles, so a doubles state that is not frozen moves in every logged doubles and category match that names the player. `RatingEngine.from_snapshot`, and so `replay(from_snapshot=...)`, now raises `SnapshotError` for an overall doubles state with no `initial_source_date`, or any overall doubles state of a resumable snapshot counting only logged dates after its `initial_source_date`, whose count differs from that total, when `category_feeds_parent` is on and `max_doubles_partner_gap` is unset. A count below the total but within the old range now fails with "must equal the self-reported doubles and category matches logged for this player"; a count outside it fails with the same messages as before. `to_snapshot()` checks its own output the same way, so it raises for such a state when a caller sets it directly on public engine attributes. Still a range: with `max_doubles_partner_gap` set, since the gap can reject a category match's doubles update and the snapshot does not record which ones it rejected; and an imported doubles state in a snapshot that is not resumable, which keeps only the upper bound, since such a snapshot does not record when each seed was set relative to the logged matches. The exact rule for an imported doubles state applies only while `resumable` is true, which the snapshot itself sets. A snapshot edited in other fields as well, such as `matches_played`, `initial_source_date`, `resumable`, or `self_reported_log`, can still load (see the snapshot schema section of the README). The schema and `snapshot_version` 7 do not change. Ratings do not change. Migration: a stored snapshot that now fails was edited or is not from the engine; rebuild it with a full replay.

## [0.3.0.dev0] - 2026-11-15

The first dev release, published to TestPyPI.

### Added

- `scripts/check_wheel.py`, which fails unless a wheel holds only the `open_engine` modules, `py.typed`, and one `openpickleball_engine-<version>.dist-info` directory, which must contain `METADATA`, `WHEEL`, and `RECORD`. Every module and `py.typed` must be present, and repeated names and other directory entries fail. CI's `package` job and the release build run it after `check_sdist.py`.
- Tests that the README quick start runs and that the README install line pins the package version.
- `twine` in the `dev` extra, so contributors can run `twine check --strict` as CI does.
- `LedgerConflictError`, a `ValueError` raised by `replay` and `prequential_predictions` (and so by `evaluate` and `fit_scale`) when ledger rows share a `match_id` but differ. Its `match_ids` attribute is the sorted tuple of every conflicting id.
- CI builds the package and runs `scripts/check_sdist.py`, which fails when the source distribution has an unexpected top-level entry.
- CI reports branch coverage of `src/open_engine` on every supported Python version. The `dev` extra now includes `pytest-cov`; run `pytest --cov` for the same report locally.
- A release workflow (`.github/workflows/release.yml`). Pushing a `v*` tag reruns the test workflow (`test.yml`) on the tagged commit, checks that the commit is on `main`, builds the sdist and wheel once, and publishes them to TestPyPI through Trusted Publishing, with no stored upload token. `docs/releasing.md` lists the one-time setup and the release steps.
- `scripts/check_release.py`, which fails unless a release tag is exactly `v` plus the version of the built sdist and wheel, and `dist/` holds nothing else.
- A test that `Config.version` equals `__version__`.

### Changed

- **Breaking:** Python 3.11 or later is required. Python 3.10 is end of life. CI tests 3.11, 3.12, and 3.13.
- The version is set in one place, `src/open_engine/_version.py`. `open_engine.__version__`, the `Config.version` default, and the build read it from there.
- `Config.version` and `__version__` are `0.3.0.dev0`. This changes every `Config.fingerprint()`.
- The source distribution now ships only `src/`, `tests/`, `scripts/`, `examples/`, `README.md`, `LICENSE`, `CHANGELOG.md`, and `pyproject.toml` (plus the `PKG-INFO` and `.gitignore` that hatchling adds). Untracked top-level files and directories (such as local tool output) and repo-only paths such as `CLAUDE.md`, `docs/`, and `.github/` are no longer bundled. Untracked files that are not gitignored inside the shipped directories still ship, and those under `src/open_engine/` also ship in the wheel. The wheel is otherwise unchanged.
- `fit_scale` compares unrounded MSE; `ScaleFit.profile` reports unrounded values.
- CI's `package` job installs `build`, `hatchling`, and `twine` from a hash-pinned lock (`.github/requirements/release.txt`), builds with `--no-isolation`, and runs `twine check --strict`, the same install and build steps the release workflow uses.
- The engine now type-checks under `mypy --strict`, and CI runs `mypy src` on every supported Python version. `ledger_order` was annotated as returning `tuple[date, time, int, str]` (its return type changes again in the breaking entry below), and `RatingEngine.player_summary` as returning `dict[str, Any]`. Runtime behavior is unchanged.
- **Breaking:** `Match.played_at` must be timezone-aware and convertible to UTC. `Match.validate()` and `ledger_order` raise `ValueError` for a naive value or one outside the range UTC can represent.
- **Breaking:** matches still sort by `played_on` first. Within one day, `ledger_order` now orders timed matches by the UTC instant of `played_at` instead of its local clock time, places untimed matches before timed ones (a timed match at local midnight used to tie with them), and returns `tuple[date, int, datetime, int, str]`. This changes the replay order, and so the ratings, for some ledgers that mix time zones on one day.
- **Breaking:** `replay` and `prequential_predictions` (and so `evaluate` and `fit_scale`) validate every ledger row before replaying, including rows after `as_of`. An invalid row now raises wherever it sits in the input.

### Fixed

- `replay` and `prequential_predictions` no longer depend on input order when the ledger repeats a `match_id`. Rows with the same `match_id` collapse to one, so `ReplayInfo.matches_considered` counts them once, only when every field matches in type and value, with `played_at` compared by its UTC instant and UTC offset. Any other repeat raises `LedgerConflictError`, including values equal under `==` but of different types (such as `best_of=3` and `best_of=3.0`) and two readings of a repeated wall time in a daylight saving fold.

## 0.2.0 - 2026-11-15

0.2.0 was never tagged or published.
