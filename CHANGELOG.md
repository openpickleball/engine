# Changelog

All notable changes to the OPEN rating engine are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, a minor version may include breaking changes.

The engine is a demonstration. Its outputs are not OPEN ratings.

## [Unreleased]

### Added

- A "Public API" section in the README that lists every public name, with the note that the API may change in any 0.x release. Names not listed there, including everything reached only through `open_engine.engine` or `open_engine.winprob`, are internal. A test checks that the list equals `open_engine.__all__`.
- An exception hierarchy. `OpenEngineError` is the base, and every class is a `ValueError`, so `except ValueError` still works: `ConfigError` (configuration and game formats), `InvalidMatchError` (matches, teams, ids, game scores, `played_at`), `InvalidSeedError` (external and replay seeds), `PlayerError` (player ids, account and external identity links), `EvaluationError` (evaluation, calibration, and win probability arguments), and `LedgerConflictError`, now under `OpenEngineError`. Seeding can also raise `PlayerError` when the player id or the external identity is not valid.
- `RejectionReason`, a string enum with one member per reason a match is not counted.
- `PlayerSummary`, the frozen dataclass `player_summary` returns.
- Docstrings on every public name and on the public methods of public classes. A test checks them.
- Engine snapshots and checkpoints. `RatingEngine.to_snapshot()` returns the engine's whole state as JSON-safe data (schema version 4, documented in the README), with sorted keys and lists so the same state gives the same text. `RatingEngine.from_snapshot(snapshot, cfg=None)` rebuilds the engine after checking every key and type, the ranges of ratings, RDs, reliabilities, and counts, the config version and fingerprint against `cfg`, and the engine's own rules for states and identities (an unplayed state has a seed RD and no partners, counts and dates agree, and a resumable snapshot holds nothing dated after its replay). It checks shape and these rules, not authenticity, so a stored snapshot needs the same write protection as ratings. `replay` takes new keyword arguments: `from_snapshot` resumes from a replay's snapshot and gives the same result as a full replay, with the whole ledger or only the rows after the checkpoint, and `whole_ledger=True` (only with `from_snapshot`, else `SnapshotError`) tells resume it has the whole ledger, so it raises `SnapshotError` naming any row the checkpoint saw that is missing (a voided or deleted row). Take the snapshot right after the replay: every engine method that changes state (a live match, a seed, an identity link, a new player or rating state) makes resume refuse it, and changing objects the engine returns directly is not tracked and makes the snapshot unsafe to resume. Resume raises instead of differing: `SnapshotError` for a snapshot not from a replay or changed since, an `as_of` before the checkpoint, a row on or before the checkpoint date that the checkpoint did not see, or a seed for a player the checkpoint's rows named; `LedgerConflictError` for a changed row on or before the checkpoint date or a later row that reuses its id; `PlayerError` for a seed already in the snapshot. Without `whole_ledger=True`, resume cannot see a voided row on or before the checkpoint, and given only the newer rows it cannot see an edited or backdated row on or before the checkpoint either. With or without it, resume cannot see a seed withdrawn or corrected after the checkpoint. Those need a full replay. A `whole_ledger` that is not a bool raises `SnapshotError`. This change does not alter the ratings a full replay gives for any ledger a full replay still accepts. The Fixed section lists the rows a full replay now rejects (issue #16).
- `SnapshotError`, an `OpenEngineError`, for a snapshot that cannot be loaded or resumed from (issue #16).
- `UnknownPlayerError`, a `PlayerError`, for a read of a player id with no player record. `RatingEngine.player`, `RatingEngine.state`, and `RatingEngine.player_summary` raise it (issue #23).
- `ReferenceDateError`, an `OpenEngineError`, for a `player_summary` call with no date to measure at, or with an `as_of` that is not a plain date (issue #17).
- `Config.established_reliability_threshold` (default 60.0) and `PlayerSummary.established`, a bool right after `imported_reliability`. It is `True` when `reliability` (OPEN-earned, as displayed, rounded to 1 place, at the summary's reference date) is at least the threshold. `Config` raises `ConfigError` for a threshold below 0, above 100, or NaN. Imported reliability never counts. Under the default config an unplayed imported seed is not established (its earned reliability is at most 32.6). An established player who stops playing loses it as the reference date moves on. Under the defaults, a new player with no imported rating, playing one match a week with varied partners and opponents, becomes established after about 10 to 13 tournament, league, or recreational verified matches (10 tournament, 11 league, or 13 recreational verified matches of one game, fewer for best of 3), and after about twice as many against the same players. Self-reported matches need about 20 to 25 with varied players and never get there against the same players, because repeat matches are discounted and then rejected. A player seeded from a recently captured imported rating starts at a lower RD (`Config.external_seed_rd`) and is established after about 3 to 4 tournament, league, or recreational verified matches. RD grows from the capture date, so an older import gives less of a head start, and a very old one none. The imported rating and its reliability value do not change the count. A rating that is not established is what external rating systems usually call provisional; OPEN's provisional live updates and the `open_provisional` source are different things. The threshold changes no rating and no `evaluate`, `prequential_predictions`, `fit_scale`, or `fit_win_calibration` output. It is separate from evaluation's eligibility rule (an imported baseline or `burn_in_matches` OPEN matches). The new field changes the default `Config().fingerprint()`. A snapshot made under an earlier default config fails `from_snapshot` under the new default config with a fingerprint mismatch, and replay records carry a different fingerprint (issue #18).
- `MatchResult.imbalance`: the mean team A delta plus the mean team B delta, from the unrounded changes, rounded to 5 places. Each delta is rounded on its own, so `imbalance` can differ from the same sum of the rounded deltas by up to 1.5e-5. It is 0.0 when both teams have the same mean K and no player is clamped or frozen, and for a match that did not count. It can be nonzero when the teams' mean K differ or a player is clamped or frozen. A value of 0.0 does not mean nothing was clamped or frozen: read `clamped` and `frozen` for that. A category match's `parent` result has its own value. The field comes after `clamped` and before `parent` (issue #14).
- `MatchResult.late`, a bool right after `imbalance`, default `False`. It is `True` for a counted match dated before a player's last match in that rating format, or before the date that player's rating in that format already reflects (for a category rating copied from overall doubles). Frozen players count. Live recording applies matches in arrival order, so the backend should check `late` and, for a category match, `parent.late`, and schedule a replay when either is `True`. It compares dates only, so a match on the same date is never late. It is `False` for a match that did not count and for every match a replay records. A category match's `parent` result has its own value, measured against the overall doubles dates (issue #19).
- A published policy for match performance: team A's share of all points across games, blended with the result by `Config.win_weight` (default 0.0, pure point share). A team can win and still lose rating when it wins by less than expected or wins a best of 3 (or 5) with fewer total points. There is no floor on a winner's change other than the rating range (`min_rating` to `max_rating`), and `win_weight = 1.0` scores the result only. The default changes only when out-of-sample evaluation supports another value. The policy is in the engine module docstring, the `Config` comment, and a new README section, with tests that pin it. It changes no rating (issue #20).
- `MatchResult.possible_duplicate_of`, the last field, default `None`. It names the earliest counted match with the same content as this one under another `match_id`: the same `played_on`, the same two teams as sets of players (either side may be team A), and the same game scores read from the same side. Match type, rating format, game format, `best_of`, `played_at`, `sequence`, and `confirmed_by` are left out. It is `None` when there is no such earlier match. Only a counted match and a match rejected as a possible duplicate carry it; it is `None` on every other result and on `parent`. The later match in processing order is the one flagged: arrival order live, ledger order in a replay (issue #21).
- `Config.reject_content_duplicates` (default `False`), a bool; any other value raises `ConfigError`. `False` does not reject a possible duplicate: it goes through the other checks and, if it counts, is flagged. `True` does not count it and returns `RejectionReason.POSSIBLE_DUPLICATE`. A real rematch on the same day between the same teams with the same scores is flagged too, or not counted under `True`. Reports that disagree on the date are not caught. The new field changes the default `Config().fingerprint()`, so a snapshot made under an earlier default config fails `from_snapshot` with a fingerprint mismatch. Under the default, every rating is the same as before (issue #21).
- `RejectionReason.POSSIBLE_DUPLICATE` (`"possible_duplicate"`), for a match rejected under `Config.reject_content_duplicates` (issue #21).
- Which report counts as the copy is set by processing order alone (arrival order live; ledger order in a replay, where, within a date, untimed rows come first by `sequence` then `match_id`, then timed rows by the UTC instant of `played_at`, then `sequence` and `match_id`), whatever the match type, rating format, or game format. Under `reject_content_duplicates=True` a weaker or relabeled copy (an untimed self-report of a timed tournament match, or a mixed doubles copy of a doubles match) can count while the stronger report is rejected, a category copy that counts first can keep the other row from updating its rating format, and live recording and a replay can keep different rows. Under the default the flagged row can be the stronger one. Use reject only when the backend trusts who files reports, and otherwise resolve flags in the backend. Under the default, a category copy of a doubles match can count twice in overall doubles, once directly and once through `parent`, whose `possible_duplicate_of` is `None`. Do not show `possible_duplicate_of` to whoever submitted the match: it names another report (issue #21).
- `RatingEngine.possible_duplicates`, a dict from the `match_id` of each match flagged or rejected as a possible duplicate to the `match_id` it repeats. An entry stays until that `match_id` later counts with no twin, which only a match rejected under `reject_content_duplicates=True` can do. `record` fills it live and in a replay, under both policies, so the backend can read the flags after a replay. Recording a rejected copy in it is a state change, so a snapshot taken after it is not resumable. The snapshot carries it as `possible_duplicates` (issue #21).
- `MatchStatus`, a public string enum: `COMPLETED` (`"completed"`), `FORFEIT` (`"forfeit"`), `RETIRED` (`"retired"`), and `INCOMPLETE` (`"incomplete"`) (issue #22).
- `Match.status`, the last field, default `MatchStatus.COMPLETED`, so a match built without it validates and rates as before. `Match.validate` raises `InvalidMatchError` for a status that is not a `MatchStatus` member (the plain text `"completed"` included), `games` that is not a tuple or list (for every status, so a completed match with `games=None` gets this message instead of "At least one game score is required"), a forfeit with any game, and a retired or incomplete match with a decided winner. A forfeit must have no games. A retired or incomplete match has zero or more finished games, each valid in its game format, and no decided winner, so in a best of 1 it has no games. Every other match check applies to every status (issue #22).
- `RejectionReason.MATCH_NOT_COMPLETED` (`"match_not_completed"`), for a match whose status is not completed (issue #22).
- A published policy for forfeits, retirements, and incomplete matches: they are never rated. `record` rejects such a match after the `match_id` check (a processed `match_id` still gets `DUPLICATE_MATCH_ID`) and changes nothing, so a later completed match with that id can still count live. The engine does not check that it is the same match: different players count too. `replay` accepts the row and counts it in `matches_considered` but not `matches_counted`. A full replay gives each player the same ratings as a full replay without it. As for any rejected row, a checkpoint tracks the row and its players, so resume raises `SnapshotError` for a new seed for a player named only in such a row. Replacing the row with a completed one under the same `match_id` is an edited row: for a row dated on or before a checkpoint it needs a full replay (resume raises `LedgerConflictError` when given it). `prequential_predictions` (and so `evaluate`, `fit_scale`, and `fit_win_calibration`) never predicts it, and takes its seed date limit and default scheduled anchor from completed rows only, so a seed dated after the last completed match raises `InvalidSeedError` whatever rows follow it, and a ledger with no completed match has no seed date check. No rating math changes. The backend should verify a status as it verifies scores, since a status keeps a match from moving any rating, and store which team forfeited or retired (issue #22).
- `Config.to_dict()` and `Config.from_dict()`. `to_dict` returns a new dict (enum keys and values as their strings, game length keys as strings, `allowed_game_formats` as a sorted list of `[scoring, points]` pairs, other values as they are). `from_dict` takes that data, also after a round trip through Python's `json` module, and returns an equal `Config` with the same fingerprint. An int and a float are different values to the fingerprint, so a store that rewrites `8.0` as `8` changes the config. `from_dict` needs exactly the keys `to_dict` gives and raises `ConfigError` for a missing or unknown key, a value it cannot convert, or a value `Config` rejects (issue #25).
- `Config` is hashable, so it can be a dict key or a set member. Equal configs hash equal. A scalar field holding a value JSON cannot hold, such as a `Decimal`, makes `hash`, `==`, and `fingerprint()` raise `TypeError` (issue #68 adds type checks) (issue #25).

### Changed

- **Breaking:** seed and identity entry points reject blank and shared identities. `add_player`, `replay(seed_players=...)`, and `prequential_predictions` (both modes, and so `evaluate`, `fit_scale`, and `fit_win_calibration`) raise `InvalidSeedError` for a seed whose player id, `account_user_id` (when not `None`), external source, or external id is blank or whitespace only, and for a seed state whose `initial_rating` is not an int or finite float (not bool) or is outside `min_rating` and `max_rating`. Such a replay used to succeed, and `to_snapshot()` on it then raised `SnapshotError`. They raise `PlayerError` for a seed whose `account_user_id` or (source, external id) pair another player already holds: an existing player in `add_player`, an earlier seed in the same batch, or a checkpoint player on resume. The messages are the ones `link_account` and `attach_external_id` use. Every check runs before any state changes. `link_account` and `attach_external_id` raise `PlayerError` for a whitespace-only or non-str account, source, or external id, which used to be accepted; a whitespace account made `PlayerSummary.account_linked` `True`. `seed_external_rating` raises `PlayerError` when its snapshot has a non-empty `external_player_id` and that id or the source is whitespace only. An empty `external_player_id` still links nothing, and the provenance it stores is not checked (issue #74). The same external id from two different sources is still accepted. A `RatingState` built with the dataclass default `initial_rating` (3.5) is now rejected as a seed under a config whose rating range excludes 3.5; `seed_provisional_rating` and `seed_external_rating` set it within the range. `RatingEngine.player`, `state`, `player_summary`, `link_account`, `attach_external_id`, `seed_provisional_rating`, and `seed_external_rating` raise `PlayerError` for a non-str player id instead of `AttributeError`. Seed identity checks for a batch (in `replay` and `prequential_predictions`) are a fixed number of set lookups per seed identity, so they do not slow down as the number of seeds grows. Ratings do not change for any input that is still accepted. Snapshot loading is unchanged and still accepts shared or blank identities; issue #61 tracks matching it to these rules (issue #52, also #44 and #45).
- **Breaking:** `Config.scale_by_scoring`, `win_calibration_by_scoring`, `match_weights`, and `game_length_weights` are read-only copies of the mappings passed in. Item assignment, `update`, `pop`, and the other dict changes raise `TypeError`, and changing the dict a config was built from no longer changes the config. A non-mapping value, a mapping value that is not a finite int or float (a `bool`, a string, a list, NaN, or infinity), or a `game_length_weights` key that is not an int (`"11"`, `11.0`, `True`) raises `ConfigError`. A string key used to share a fingerprint with the int key the engine reads. `allowed_game_formats` is stored as a `frozenset`; a value that is not a `set` or `frozenset`, such as a list, or an entry that is not a (scoring type, int) pair, raises `ConfigError`. Build a new config with `dataclasses.replace` instead of changing one (issue #25).
- **Breaking:** `Config` equality compares fingerprint payloads, so equal configs always have the same fingerprint and hash. Configs that used to compare equal with different fingerprints, such as `Config(k_min=0)` and `Config(k_min=0.0)`, are no longer equal. No config that still builds gets a new fingerprint: `Config()` still gives `c5bb49f7c37a013a`.
- `RatingState.inherited_live_updates`, a new int field, default 0. It is the last field, after `opponents`, so positional calls that pass `partners` or `opponents` keep their meaning. A category state (mixed, men's, or women's doubles) derived from overall doubles copies a rating that can hold live updates since the last replay. The field records how many the parent state had when the category state was derived, and never changes after that. It is 0 for every state not derived from its parent. `PlayerSummary.live_updates_since_recalculation` keeps its name and type but now reports `live_updates_since_replay + inherited_live_updates`, so a derived category state is labeled with the parent's live updates in its starting rating, before and after its first match. It used to report the state's own count only, which labeled such a state too low. A replay gives 0 for every state. No rating, RD, or reliability changes. A seed (`add_player`, `replay`, and `prequential_predictions`) with an `inherited_live_updates` that is not an int, or not 0, raises `InvalidSeedError`. The snapshot schema is version 4: each state has an `inherited_live_updates` key. `from_snapshot` raises `SnapshotError` for a version 3 snapshot, a missing key or a value that is not a nonnegative int, a nonzero value on a state not derived from its parent (one needs `category_feeds_parent` and an `initial_source` of `open_parent:` plus the parent's value), a nonzero value with no parent state or above the parent state's `live_updates_since_replay`, a nonzero value on a state whose `initial_source_date` differs from the parent state's or that has an `initial_source_reliability`, `initial_external_player_id`, or `initial_evidence_reference`, a nonzero value on an unplayed state with an RD below `category_seed_rd` or an `rd_as_of` that is null or after the parent state's, and a nonzero value in a resumable snapshot. Resume refuses a snapshot with a nonzero value, as it refuses one with live updates. Snapshots were never in a release, so version 3 snapshots were only written by unreleased builds of main. They no longer load; run a full replay to make a new one (issue #23).
- **Breaking:** `RatingEngine.player`, `RatingEngine.state`, and `RatingEngine.player_summary` no longer create anything. For a player id with no player record they raise `UnknownPlayerError` (`player_summary` after its `ReferenceDateError` checks), and a blank id still raises `PlayerError`. They used to create an empty player, and `state` and `player_summary` stored a rating state for a format the player had none in, so a lookup of a mistyped id added a player and a read cleared the snapshot's resumable mark. For a known player with no state in the format, `state` returns, and `player_summary` reports, the starting state the player's first match in that format would use if played now (a category state derived from overall doubles where that applies, else a provisional default), without storing it. That returned state is a new object each call, so changing it changes nothing. Reads now keep a replayed engine resumable. A player or state is created on purpose by `add_player`, `seed_provisional_rating`, `seed_external_rating`, `link_account`, `attach_external_id`, or a counted `record` (and so `replay`), which still create as before. An id named only in uncounted rows, or in rows after a replay's `as_of`, has no player record, so `player_summary` and `state` now raise `UnknownPlayerError` for it where they used to return a provisional default. Apart from the snapshot schema change in the `RatingState.inherited_live_updates` entry (version 3 snapshots no longer load, and snapshots are version 4 with an `inherited_live_updates` key in each state), replay, resume, and evaluation results do not change for any ledger and snapshot that worked before. Reads that used to create a player or rating state no longer do, so later calls see the engine as it was before the read. For example, the first match in a category format after a read of that missing format now rates as it would have without the read, as a replay does, and a later `seed_external_rating` without `replace_unplayed_seed`, or `add_player` for that id, no longer finds a state or player the read created. Those reads also no longer clear the resumable mark (issue #23).
- Snapshot schema version 3 changed no key, but each row digest in `ledger_digests` now covers `Match.status`, so resuming from a version 2 checkpoint would raise a misleading `LedgerConflictError` for any row given to it dated on or before the checkpoint. `from_snapshot` raises `SnapshotError` for a version 2 snapshot instead. Snapshots were never in a release, so version 2 snapshots were only written by unreleased builds of main. Run a full replay to make a new one (issue #22).
- Snapshot schema version 2 added `content_keys` (the content digest of each counted match, mapped to the `match_id` of the first match counted with it, so a loaded or resumed engine still catches a later duplicate) and `possible_duplicates`. `from_snapshot` raises `SnapshotError` for a version 1 snapshot, and for `content_keys` that is not an object, has a key that is not 64 lowercase hex characters, has a value that is not a processed match id, or names one id under two keys, and for `possible_duplicates` that is not an object, has a key or value that is not a non-blank str, has a value that names its own key, has a key that is a `content_keys` value, has a value that is not a `content_keys` value, has a key that is not a processed match id under the default config or is one under `reject_content_duplicates=True`, or, in a resumable snapshot, has a key that is not a `ledger_digests` id. Snapshots were never in a release, so version 1 snapshots were only written by unreleased builds of main. They no longer load; run a full replay to make a new one (issue #21).
- **Breaking:** `player_summary` measures inactivity, RD, and reliability at a reference date. With no `as_of`, it is now the later of the last replay date (`calculated_as_of`) and the player's last match. It used to be the player's own last RD update, or today, so a player who stopped playing kept the same reliability however late the replay was. Now a stale player is measured at the replay date and loses reliability, and shows a wider RD, as replays move forward. A player with live matches since the replay is measured at their last match. Players in one engine can be measured at different dates. With no `as_of` on an engine that was never replayed, it raises `ReferenceDateError`, so pass `as_of` on a live engine. An `as_of` that is not a plain date (a str, or a datetime) also raises `ReferenceDateError`; a datetime used to be accepted for an unplayed provisional state, and a str raised `TypeError` after creating state. Both checks come before the player id is checked. An explicit `as_of` still wins, but an `as_of` earlier than the player's last match does not rebuild past state: RD and partner variety stay as of the stored state. `imported_reliability` uses the same reference date. An unplayed import is now measured at the replay date by default, not its capture date, so it stops being carried once it is older than `import_reliability_max_age_days` at that date, and an unplayed import captured after the last replay is not shown. `reliability(state, cfg, as_of)` now requires `as_of`, and calling it without one raises `TypeError`. The engine no longer reads the wall clock anywhere (issue #17).
- **Breaking:** `RatingEngine.predict` is now `predict_point_share` and `RatingEngine.win_probability` is now `predict_win_probability`, with the same arguments and, for valid player ids, the same results. The old names are gone.
- **Breaking:** `clone_player`, `inflated_rd`, `player_k`, and `information_multiplier` are no longer exported from `open_engine`. They stay in `open_engine.engine` as internal helpers. `recency_multiplier` is no longer exported either, and is removed (see below).
- **Breaking:** `player_summary` returns a `PlayerSummary` instead of a dict. Other than the reliability fields (see the next entry), fields keep their names and values (`initial_source_reliability` now comes before `initial_source_date`, which changes the key order of `dataclasses.asdict`), but `rating_format` is a `RatingFormat`, `reliability` is always a float, and `last_played`, `initial_source_date`, and `calculated_as_of` are `date` objects or `None` instead of ISO strings. `dataclasses.asdict` gives a dict, but its dates need converting before JSON.
- **Breaking:** `PlayerSummary.reliability` is always OPEN-earned reliability. It used to show the imported external reliability while it was carried. The carried value is now in a new field, `imported_reliability`, right after `reliability`: the imported reliability as a float while it is carried (captured on or before the reference date and fresh within `import_reliability_max_age_days`, fewer than `import_reliability_carry_matches` OPEN matches, and, rounded to 1 place, higher than the earned value), otherwise `None`. The `reliability_basis` and `open_reliability` fields are removed (issue #15).
- **Breaking:** `seed_external_rating` no longer takes `rd_override`; passing it raises `TypeError`. `Config.external_reliability_maps_to_rd` is removed, so `Config(external_reliability_maps_to_rd=...)` raises `TypeError`. A seeded state's RD is always `Config.external_seed_rd`, whatever the snapshot's reliability, so an external score never becomes OPEN RD. `Config.fingerprint()` changes for every config, since the field is no longer hashed (issue #15).
- **Breaking:** `add_player`, `replay(seed_players=...)`, and `prequential_predictions` (and so `evaluate`, `fit_scale`, and `fit_win_calibration`) check every seed against the seed rules and raise `InvalidSeedError` for one that breaks them, naming the player (and the format, for a rule on one rating state), before any state changes (`prequential_predictions` checks every seed up front, in both modes, even for an empty ledger, and raises `PlayerError` for a repeated seed id as `add_player` does). The rules: a seed is a `Player` with a `str` id, its `ratings` are a dict, every key is a `RatingFormat`, and every value is a `RatingState`; its `external_ids` are a dict of `str` to `str` and its `account_user_id` is a `str` or `None`; `rating`, `rd`, and an imported reliability are ints or finite floats (not bool), the counts are ints, `partners` and `opponents` are dicts, and the dates are dates. A seed or field of the wrong type, or a huge int, raises `InvalidSeedError`, not `TypeError`, `AttributeError`, or `OverflowError`. A seed has no matches, `last_played`, partners, opponents, or live updates, and its rating is within `min_rating` and `max_rating`. A provisional seed has RD `new_player_rd`, no `rd_as_of`, and no imported reliability. An imported seed, or a category seed derived from one, has RD `external_seed_rd` or `max(external_seed_rd, category_seed_rd)`, `rd_as_of` equal to `initial_source_date`, and an imported reliability that is `None` or between 0 and 100. Seeds are checked against the config they are added under. `replay` also rejects a seed whose `initial_source_date` is after `as_of`, and `prequential_predictions` one dated after its last completed ledger match; `add_player` and `seed_external_rating` have no reference date and make no date check. A played state can no longer be restored through `add_player`; rebuild it with `replay`. `seed_external_rating` checks its `rating_format` (a `RatingFormat`, not a str) and its snapshot with the same type rules before anything changes, raising `InvalidSeedError` for a rating format or one of these snapshot fields of the wrong type, so every state it seeds passes them: `captured_on` must be a `date` (not a `datetime`), `source` a `str`, `external_player_id` a `str` or `None`, `rating` an int or finite float (not bool) within the rating bounds, and `reliability` `None` or an int or finite float (not bool) between 0 and 100; a datetime `captured_on`, a bool rating or reliability, or a str `rating_format` used to be accepted (issue #15).
- **Breaking:** `MatchResult.reason` is a `RejectionReason`, or `None` when the match counted, instead of free text. `MatchResult.rating_format` is a `RatingFormat` on every result, including rejections before any rating work, instead of a string that could be empty. `rating_format` is now required and comes second (`counted`, `rating_format`, `reason`), and `reason` defaults to `None` instead of `""`, so code that builds a `MatchResult` must pass `rating_format` and, if it uses positions, follow the new order.
- **Breaking:** errors that were plain `ValueError`s are now the classes above. A `GameFormat` used for win probability is validated first, so an invalid format raises `ConfigError`. That includes `win_by=0`, which used to raise the `ValueError` that is now `EvaluationError`.
- **Breaking:** match and player ids must be non-empty strings that are not only whitespace. `Match.validate` raises `InvalidMatchError` for any other `match_id` or player id, and for a game that is not a pair of scores. Blank match ids already raised. These used to be accepted:
  - Player ids that are blank, whitespace-only, or not strings, in a row after `as_of` or in a rejected row. Ledgers with such rows used to replay.
  - Ids that are bytes. `record` used to count those matches.
  - Blank player ids in `predict_point_share` and `predict_win_probability`, which used to return a value.

  Such rows now raise in `record`, `replay`, and `prequential_predictions` (and so in `evaluate`, `fit_scale`, and `fit_win_calibration`). Every ledger that still replays gives the same ratings.
- **Breaking:** replay recency decay is removed. `Config.recency_half_life_days` is gone, so `Config(recency_half_life_days=...)` raises `TypeError`, and the `recency_multiplier` helper is gone. A replay now gives the same ratings as recording the same ledger live in ledger order, and the replay date no longer changes any update. Inactivity still widens RD through `inflated_rd`. Under the old default (a 365-day half-life), any counted match older than the replay date now has a larger `MatchResult.effective_weight`, so replayed ratings and RDs can change. A config that used to set `recency_half_life_days=None` gives the same ratings without the field. `Config.fingerprint()` changes for every config, since the field is no longer hashed.
- **Breaking:** each player now moves by their own K: `sign * K * effective_weight * surprise`. The shared match K (the mean K of all players) and the split of a team's change by K share are removed. Each player's step now depends only on their own K. A partner's or opponent's K no longer changes it: before, a player's step grew when the opponents' mean K was above their own team's and shrank when it was below. Team average movement is no longer always zero-sum: the team with the higher mean K can move more, and `MatchResult.imbalance` reports the net. Deltas are unchanged in a match where both teams have the same mean K, counting every player (including when every player has the same K). Ratings can change for a ledger with any match whose team mean K differ (issue #14).
- Because team movement is not zero-sum, matches between high-K and low-K players can add rating to the pool or remove it. Colluding accounts can exploit this: a new account can gain rating by beating a low-K account again and again, or lose rating faster on purpose. `MatchResult.imbalance` is the per-match signal the backend should total and monitor. Mitigation will be tracked in a follow-up issue.
- **Breaking:** `RatingFormat`, `MatchType`, and `ScoringType` are `StrEnum`s, so `str()` and f-strings give the value (`"doubles"`, not `"RatingFormat.DOUBLES"`). Comparison with the value, `repr`, pickling, and `Config.fingerprint()` are unchanged.
- **Breaking:** `Match.validate` raises `InvalidMatchError` for a `played_on` that is not a plain `date` (a `datetime`, a str, `None`, or any other type) and for a game score that is a `bool`. A `datetime` `played_on` could count, and then a comparison with a plain `date` raised `TypeError`: a later `record` with a plain-date `played_on` for one of its players, `player_summary` for one of its players, or a `replay` with a plain-date `as_of`. A str `played_on` raised `TypeError` in `replay` and `AttributeError` in `record`. A bool score was read as its int value (`True` as 1), so a match such as `(11, True)` could count. Such rows now raise `InvalidMatchError` in `record`, `replay`, and `prequential_predictions` (and so in `evaluate`, `fit_scale`, and `fit_win_calibration`) before any state changes, wherever they sit in the ledger. `record` also raises `InvalidMatchError` for an `as_of` that is not a plain `date`, checked right after the match. It used to return any rejection that comes before the date check (such as `DUPLICATE_MATCH_ID` or `MATCH_NOT_COMPLETED`), count the match with a falsy `as_of` such as `0` or `""` as if none was given, and otherwise raise `TypeError`. Every ledger that still replays gives the same ratings (issue #24).

### Fixed

- Evaluation, calibration, and win probability results are now the same on Python 3.11, 3.12, and 3.13 (issue #40). Python 3.12 changed the built-in `sum()` of floats to compensated summation, so on 3.11 a float sum could round differently in the last bit. The engine now adds floats with `math.fsum`, which is correctly rounded on every version. Ratings, RDs, and `ReplayInfo` do not change on any version: every float sum on the rating path adds one or two terms, which `sum()` and `math.fsum` round the same way. The exception is a `Config` whose rating range is so large that two ratings add up past the largest float: those sums gave `inf` and wrong expectations before, and now raise `OverflowError` (issue #70). Win probabilities (`game_win_probability`, `match_win_probability`, `predict_win_probability`, `PrequentialPrediction.win_probability_raw`), `evaluate` reports, `ScaleFit.profile`, and Brier scores can move in the last bit, mostly on 3.11 and rarely on 3.12 and later. A value rounded for display can change where that bit decides the rounding: in a synthetic test, one `evaluate` calibration bin's mean actual share moved from 0.6047 to 0.6048 on 3.11. A test pins exact replay, evaluation, and win probability output on every CI Python version.
- A `Config`'s mapping fields can no longer change after it is built (issue #25). They were plain dicts, so `cfg.match_weights[MatchType.LEAGUE] = 9` succeeded and changed `cfg.fingerprint()`, the provenance stored with each replay. The dict fields also made `Config` unhashable.
- `link_account`, `attach_external_id`, and `seed_external_rating` now run every check before they change anything. A call that raised for a new player id (an account or external identity already linked to another player, or a snapshot identity with no source) used to leave an empty player record behind and clear the snapshot's resumable mark. Now a call that raises leaves the engine as it was. Error types and messages, and what a successful call creates, are unchanged (issue #23).
- A live match dated before a player's last match, or before the date a category rating copied from overall doubles already reflects, no longer moves `last_played`, `rd_as_of`, or partner and opponent dates back. Each now keeps the later date, and a new partner or opponent gets the match date. Before, inactivity RD growth ran again from the older date, so it counted twice, `last_played` (and with it `player_summary`'s default reference date) was wrong, and a partner or opponent seen recently could drop out of the rolling diversity window. The late match's own update is unchanged, and so is every match recorded in play order, so replay gives the same ratings as before. Live results still apply in arrival order; `MatchResult.late` flags these matches. Because dates never move back, a future-dated live match now holds its players' dates at that future date until the next replay, so their RD stops growing and their reliability stays high. The engine never reads the clock, so the backend must reject a match whose `played_on` is after the date it was submitted. A later honest match with those players that counts in the same rating format is flagged `late`, and for a category match `parent.late` covers the overall doubles rating (issue #19).
- Rows that repeat a `match_id` and differ only in the type of a member inside a list or set field (for example a game written as `[11, 1]` in one row and `[11, True]` in the other) now raise `LedgerConflictError` in `replay` and `prequential_predictions`, as the rule that every field matches in type and value says. They used to collapse to one row, because list and set fields were compared with `==` only (issue #16).
- Replay no longer shrinks old matches' updates. Recency decay scaled each update by the match's age at the replay date, so a replay disagreed with live recording of the same ledger, `evaluate(mode="live")` and `evaluate(mode="scheduled")` disagreed, a player whose matches were all long ago drifted back toward the default rating, and every recalculation shifted ratings even with no new matches (issue #13).
- `record` with a blank or whitespace-only player id, or one that is not a string (such as an int), no longer changes any rating. It used to update the players before the bad id, then raise before marking the match processed, so every retry moved those ratings again. It now raises `InvalidMatchError` before anything changes.
- `LedgerConflictError` survives pickling and copying with its message and `match_ids` intact. The message used to come back garbled.
- `game_win_probability`, `match_win_probability`, and `predict_win_probability` validate the `GameFormat` and raise `ConfigError` for an invalid one. Before, a `cap` at or below `points_to` silently returned a wrong probability, and `points_to=0` raised a bare `ValueError` from inside the math.
- A malformed game score (not a pair of scores) raises `InvalidMatchError` instead of a bare `ValueError` or `TypeError` from unpacking.

### Security

- Reliability can no longer be set without match results (issue #15). A seed passed to `add_player` or `replay` could carry any RD, partners, and opponents with zero matches (for example RD 0.10 and 20 partners gave reliability 100), `rd_override` let a caller pick a seed's RD, `external_reliability_maps_to_rd` turned an external score into OPEN RD, the headline summary reliability showed the imported value, a seed dated in the future froze every match before its date and kept its imported reliability shown (`replay` and `prequential_predictions` now reject it, and `player_summary` does not carry an import captured after its reference date, which with no `as_of` is the later of the last replay date and the player's last match (see the `player_summary` entry under Changed)), and a seed rating outside the rating bounds moved other players' ratings. Each is closed by the breaking changes above.

## [0.3.0.dev0] - 2026-11-15

The first dev release, published to TestPyPI.

### Added

- `scripts/check_wheel.py`, which fails unless a wheel holds only the `open_engine` modules, `py.typed`, and one `openpickleball_engine-<version>.dist-info` directory, which must contain `METADATA`, `WHEEL`, and `RECORD`. Every module and `py.typed` must be present, and repeated names and other directory entries fail. CI's `package` job and the release build run it after `check_sdist.py`.
- Tests that the README quick start runs and that the README install line pins the package version.
- `twine` in the `dev` extra, so contributors can run `twine check --strict` as CI does.
- `LedgerConflictError`, a `ValueError` raised by `replay` and `prequential_predictions` (and so by `evaluate` and `fit_scale`) when ledger rows share a `match_id` but differ. Its `match_ids` attribute is the sorted tuple of every conflicting id.
- CI builds the package and runs `scripts/check_sdist.py`, which fails when the source distribution has an unexpected top-level entry.
- CI reports branch coverage of `src/open_engine` on every supported Python version. The `dev` extra now includes `pytest-cov`; run `pytest --cov` for the same report locally.
- A release workflow (`.github/workflows/release.yml`). Pushing a `v*` tag reruns the test workflow (`test.yml`) on the tagged commit, checks that the commit is on `main`, builds the sdist and wheel once, and publishes them to TestPyPI through Trusted Publishing, with no stored upload token. `docs/releasing.md` lists the one-time setup and the release steps.
- `scripts/check_release.py`, which fails unless a release tag is exactly `v` plus the version of the built sdist and wheel, and `dist/` holds nothing else.
- A test that `Config.version` equals `__version__`.

### Changed

- **Breaking:** Python 3.11 or later is required. Python 3.10 is end of life. CI tests 3.11, 3.12, and 3.13.
- The version is set in one place, `src/open_engine/_version.py`. `open_engine.__version__`, the `Config.version` default, and the build read it from there.
- `Config.version` and `__version__` are `0.3.0.dev0`. This changes every `Config.fingerprint()`.
- The source distribution now ships only `src/`, `tests/`, `scripts/`, `examples/`, `README.md`, `LICENSE`, `CHANGELOG.md`, and `pyproject.toml` (plus the `PKG-INFO` and `.gitignore` that hatchling adds). Untracked top-level files and directories (such as local tool output) and repo-only paths such as `CLAUDE.md`, `docs/`, and `.github/` are no longer bundled. Untracked files that are not gitignored inside the shipped directories still ship, and those under `src/open_engine/` also ship in the wheel. The wheel is otherwise unchanged.
- `fit_scale` compares unrounded MSE; `ScaleFit.profile` reports unrounded values.
- CI's `package` job installs `build`, `hatchling`, and `twine` from a hash-pinned lock (`.github/requirements/release.txt`), builds with `--no-isolation`, and runs `twine check --strict`, the same install and build steps the release workflow uses.
- The engine now type-checks under `mypy --strict`, and CI runs `mypy src` on every supported Python version. `ledger_order` was annotated as returning `tuple[date, time, int, str]` (its return type changes again in the breaking entry below), and `RatingEngine.player_summary` as returning `dict[str, Any]`. Runtime behavior is unchanged.
- **Breaking:** `Match.played_at` must be timezone-aware and convertible to UTC. `Match.validate()` and `ledger_order` raise `ValueError` for a naive value or one outside the range UTC can represent.
- **Breaking:** matches still sort by `played_on` first. Within one day, `ledger_order` now orders timed matches by the UTC instant of `played_at` instead of its local clock time, places untimed matches before timed ones (a timed match at local midnight used to tie with them), and returns `tuple[date, int, datetime, int, str]`. This changes the replay order, and so the ratings, for some ledgers that mix time zones on one day.
- **Breaking:** `replay` and `prequential_predictions` (and so `evaluate` and `fit_scale`) validate every ledger row before replaying, including rows after `as_of`. An invalid row now raises wherever it sits in the input.

### Fixed

- `replay` and `prequential_predictions` no longer depend on input order when the ledger repeats a `match_id`. Rows with the same `match_id` collapse to one, so `ReplayInfo.matches_considered` counts them once, only when every field matches in type and value, with `played_at` compared by its UTC instant and UTC offset. Any other repeat raises `LedgerConflictError`, including values equal under `==` but of different types (such as `best_of=3` and `best_of=3.0`) and two readings of a repeated wall time in a daylight saving fold.
